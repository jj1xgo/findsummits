## 1. 目的・位置づけ

本書は `docs/50_UT.md`（単体テスト）・`docs/60_IT.md`（結合テスト）・`docs/70_ST.md`（システムテスト）の3ファミリを横断して律する常駐文書（`docs/CLAUDE.md` 採番ルールの00番台=共通・常駐）であり、各テストレベルの定義・役割分担・自動/手動の分担・テスト環境・開始基準・合否判定基準を一元的に定める。個別のテストケース・テスト手順は各ファミリの本体文書（`50_UT.md`・`60_IT.md`・`70_ST.md`）に記述し、本書への参照で重複を避ける。

## 2. テストレベル定義と役割分担

| レベル | 対象・スコープ | 検証しない範囲 | 対応ドキュメント |
|---|---|---|---|
| UT（単体テスト） | 関数単位の内部ロジックと、1 本のプログラムの中の関数のつながり（関数と共通部品の一覧は [HLD 3 章](30_HLD.md#3-プログラム構造)、細部は LLD） | プログラムの境界をまたぐ受け渡し（ITの責務） | `50_UT.md`（未作成） |
| IT（結合テスト） | [HLD 3 章](30_HLD.md#3-プログラム構造)が定める結合のつなぎ目（プログラムの境界をまたぐ受け渡し）。内部結合と外部結合の 2 段で行う。用語の定義は [HLD 1 章](30_HLD.md#1-用語定義) | 個々の関数の内部ロジックの正しさ（UTの責務）、SOTA申請要件全体の充足（STの責務） | `60_IT.md`（未作成） |
| ST（システムテスト） | [`20_SRS.md`](20_SRS.md) のFR/NFRレベル・[`10_URD.md`](10_URD.md) のURレベルのエンドツーエンド検証（環境構築から成果物生成までの一気通貫を含む） | 関数の内部ロジックとプログラムの中のつながり（UTの責務）、プログラムの境界をまたぐ受け渡し（ITの責務） | `70_ST.md` |

各レベルの合格は下位レベルの合格を前提としない独立検証とする（UTが通っていてもITで初めて発見される結合不整合、ITが通っていてもSTで初めて発見される要件充足不備がありうるため）。上位レベルの開始基準にも、下位レベルの合格は含めない。開始基準が下位レベルに求めるのは、実行して結果を記録したことだけである（[5.6](#56-開始基準)）。

IT は、内部結合のつなぎ目を確かめてから、外部結合のつなぎ目を確かめる。食い違いが出たときに、原因のある境界を絞りやすいためである。つなぎ目の一覧と ID の正本は、[HLD 3 章](30_HLD.md#3-プログラム構造)の各節の「結合のつなぎ目」である（[ADR-HLD-001](decisions/ADR-HLD-001-program-structure-chapter-and-two-tier-it.md)）。システムの外へ出す成果物の中身は ST で確かめる。

## 3. テスト戦略

### 3.1 自動テストと手動確認の役割分担

- **C解析エンジン・Pythonスクリプト**: 自動テストを既定とする（`make test_mesh_analyze`・`make test_analyze` 等でテストをビルドし、ビルドしたテストを実行する。この仕組みを UT/IT で拡張する）。期待値の決め方は [3.3](#33-期待値の根拠) に従う
- **HTMLビューア等のWebUI**: 申請書 XLSX・サミット一覧（申請内容反映版）・申請エビデンス ZIP など、ブラウザ内で生成する成果物の中身（出力する行・セル値・除外の反映・同梱ファイル）は、固定した入力（中心データと表示・編集状態）から生成して自動で照合する。地図の描画と対話操作は対象環境のブラウザで手動確認する
- 手動確認を行う際は、開発サーバー起動手順（該当する場合）・自動テストとの役割分担・前提状態（ログイン等、本プロジェクトでは該当なし）を都度明記する

### 3.2 実データ依存の扱い

- 地理院タイル等の外部データ取得に依存するテストは、ローカルキャッシュ（`$DATA_DIR/tiles/`）を用いてネットワーク非依存で再現可能な範囲を優先する
- ネットワーク取得自体の検証（[FR-001](20_SRS.md#fr-001-標高タイル事前取得)・[NFR-004](20_SRS.md#nfr-004-アクセスマナー) 等）は、正常な取得とアクセス条件（User-Agent・リクエスト間隔・並列数）を実際の地理院タイルサーバーに対して少数のタイルで確認する（[UR-010](10_URD.md#ur-010) の利用規約遵守を含めて実挙動を確認する必要があるため）。少数のタイルで確認するのは取得機能とアクセス条件の個別検証に限る。全国分の取得を要する試験（処理時間の測定、クリーン環境からの一気通貫確認等）は各テストケースが定める範囲で実サーバーから取得する。実行頻度は各テストケース側で定める
- 過多・一時利用不可の応答、タイムアウト、通信断などの異常系は、実サーバーでは狙って起こせず、起こそうとするとアクセスマナーに反する。これらは応答を制御できる手元の模擬サーバーで再現する

### 3.3 期待値の根拠

- 正しさを確かめる試験は、仕様から導いた期待値と照合する。期待値の根拠（手計算・一次資料・既知の地形を作った試験入力など）は、テスト対象の出力とは独立に用意して記録する
- 同一入力に対する出力比較（前回出力との一致。[NFR-003](20_SRS.md#nfr-003-再現性決定論的出力)）は再現性と回帰の検出に使い、正しさの根拠にはしない
- 既知の地形を作った試験入力による境界の確認（プロミネンス閾値ちょうど・同標高頂部・近接峰・窓外コル等）は UT/IT が担う。全国実データの基準セットによる確認は ST が担う（[`70_ST.md`](70_ST.md) の検出網羅性の基準セット）

### 3.4 テストを先に書く進め方

- 対象は製品のコードである。[HLD 2.8.2](30_HLD.md#282-ディレクトリ構成) の製品区分（`src/` の C4 の C++、`scripts/` の C1・C2・C3・C5・C6 の Python と bash）と、C7・C8 のブラウザ側の JavaScript を含む。これらを新しく書くときと挙動を変えるときは、UT を先に書き、対象の挙動がまだ無いか期待と違うために失敗することを確かめてから実装する。実装の後、同じテストが通ることを確かめる
- IT も、期待値を仕様（SRS・HLD）から導ける場合は先に書く
- 欠陥を直すときは、欠陥を再現して失敗するテストを先に書いてから直す
- 期待値は [3.3](#33-期待値の根拠) に従って仕様から導く。先に書いたテストを、実装の出力に合わせて書き換えない。仕様が誤っていたときは、仕様を直してからテストを直す。テストの側の誤り（期待値の導き方、試験入力の作り方）は、仕様から導き直し、根拠を記録して直す
- 対象外: 現在のプロトタイプ（`src/*.c`、`scripts/` の現行のスクリプト、`tests/` 直下の試作の `test_*.c`）、開発用の道具（`tools/`）、調査用の試作、`analysis/`、`docs/mockup/`、仕様を持たない使い捨てのスクリプト。[3.1](#31-自動テストと手動確認の役割分担) で手動確認とする地図の描画と対話操作も除く。対象外のコードを製品のコードに取り込むときは、テストを先に書いてから取り込む
- この進め方は、HLD・LLD に沿って製品のコードを書き始めるときから当てる。テストの枠組みとテストのしかたは、それまでに [HLD 2.8.5](30_HLD.md#285-未決事項と後続) の 2（C4 の C++、Python、C3 の bash）と 9（C7・C8 の JavaScript）で選ぶ
- 理由: 実装より先に仕様から期待値を書けば、[3.3](#33-期待値の根拠) の「出力とは独立に用意する」を守れる。後から書くと、実装の出力を期待値に写しやすい。テストが狙った理由で一度失敗するのを見ておけば、何も確かめていないテストを見分けられる
- 却下: テストを実装の後に書いてよいとする案（上の写しを防げない）。先に書くことを推奨にとどめる案（守られたかを確かめる基準にならない）

## 5. 開始基準・合否判定・完了基準

### 5.1 exit criteria

各テストレベルの完了基準:

- **UT/IT**: 対象範囲の全テストケースが合格すること、または不合格のケースごとに [5.3](#53-既知欠陥の許容基準)、未実施のケースごとに [5.4](#54-未実施ケースの扱い) の許容判断が記録済みであること
- **ST**: `70_ST.md` 第1部の全FR/NFRテストケースおよび第2部の全UR妥当性確認シナリオが合格すること、または不合格のケースごとに [5.3](#53-既知欠陥の許容基準)、未実施のケースごとに [5.4](#54-未実施ケースの扱い) の許容判断が記録済みであること
- 全レベル共通で、不合格・未実施はその結果のまま記録する。許容判断があっても合格へ書き換えない

### 5.2 カバレッジ粒度の正本

`70_ST.md` 等の個別テスト文書がテストケースのカバレッジ観点（NODATA・境界値・同値分割等）をどの粒度で明示するかは、本節を正本とする（個別テスト文書側は本節への参照のみとし、重複記述しない）。

既定方針: リスクの高いFR/NFRは複数の境界値ケースを厚めに書き、その他は代表ケース1件を最低限の目安とする。リスクが高いとは、境界値・sentinel値の扱いが複雑なもの（例: [FR-003](20_SRS.md#fr-003-標高デコードnodata-処理) のNODATA(-9999m)・海面下負値・符号変換境界値の扱い、[FR-006](20_SRS.md#fr-006-コル検出プロミネンス計算) の `key_col_resolved`/`col_lat`/`col_lon` sentinel値の組み合わせ）と、誤ったときの影響が大きいもの（申請内容の誤り・ピークの検出漏れ・利用者の判断データの消失）をいう。

代表ケースで済ませる FR/NFR も、その要件に必須の挙動と主な異常系（停止・警告して続行等）にテストケースが対応しているかを確かめ、足りなければケースを追加する。

### 5.3 既知欠陥の許容基準

既知欠陥を承知で次へ進む判断（許容判断）は、テスト結果とは別に、対象ケース・欠陥の issue・理由とともに記録する。テスト結果の不合格はそのまま残す。

- 重大度が「低」（`priority:低` 相当）かつ回避策がある既知欠陥は、issue 登録済みであることを条件に許容判断できる
- 重大度が「中」以上の既知欠陥は、原則として完了を妨げる。許容判断にはユーザー承認を要し、承認も記録に含める

### 5.4 未実施ケースの扱い

前提（基準データ・外部サービス・実行環境等）がそろわず実施できなかったケースは、欠陥の重大度では判断できないため、[5.3](#53-既知欠陥の許容基準) とは別に扱う。未実施のまま次へ進む判断は、未実施の理由、確かめられていない要件とその影響、代わりに確かめたこと（あれば）、承認者、再実施の条件を記録し、ユーザー承認を要する。未実施の結果はそのまま残す。

### 5.5 テスト結果の記録

各テストの結果は、ケースID・対象の版（commit）・入力・設定・結果・証跡を最低限記録する。ブラウザを使う試験はブラウザの種類と版、localStorage 等の保存状態も記録する。

正式な実行（[5.6](#56-開始基準)）は、1 回ごとに次の記録を残す。1 回の実行の記録は、Issue か文書の 1 か所にまとめる。各記録は、書いた後に書き換えず、補足と訂正は追記する（[開発ガイド §4](03_development.md#4-フェーズゲート) のフェーズゲートの記録と同じ）。Issue と文書のどちらに置くかは、本書では定めない（メンテナの置き場は [AGENTS.md「個人運用の補足」](../AGENTS.md#個人運用の補足)）。

| 記録 | 書くとき | 最低限の中身 |
|---|---|---|
| 実行の開始記録 | 実行を始める前 | 確かめた日、テスト対象の版（commit）、[5.6](#56-開始基準) の開始基準の各項目を満たしたこと、方針からのずれ（あれば。テスト環境が [4](#4-テスト環境) と違うなど）、下位レベルを実行した版と不合格・未実施のケース ID（[5.6](#56-開始基準) が求めるとき）、判定の対象のケースの集合（[5.1](#51-exit-criteria) の対象範囲。UT/IT は対象範囲のケース、ST は第 1 部と第 2 部の全ケース。集合は作業者の判断では変えない。変わるのは、[5.7](#57-中断と再開) の改訂でケースが増減したときだけ）と、その中で実行しないケースとその理由（実行しないケースは未実施として [5.4](#54-未実施ケースの扱い) に従う） |
| ケースの開始記録 | テスト文書が求めるケースを始める前 | テスト文書が定める項目（[`70_ST.md`](70_ST.md) の[検出網羅性の基準セットと判定手順](70_ST.md#382-検出網羅性の基準セットと判定手順)など） |
| 中断と再開 | 中断したとき、再開するとき | [5.7](#57-中断と再開) が求める項目。改訂でケースが増減したときは、再開の記録に新しい判定の対象の集合と、増減したケース ID を書く |
| 各ケースの結果 | ケースを実行したとき | 本節の最初の段落の項目と、テスト文書がそのケースに求める項目。大きな証跡はリポジトリの外に置き、置き場と内容のハッシュを書く |
| 欠陥 | ケースが不合格のとき（不合格の結果は先に残し、欠陥への参照は、欠陥を記録した後に追記する） | [開発ガイド §7.2](03_development.md#72-欠陥の扱い) に従って記録した欠陥への参照。欠陥の記録には、ケース ID、テスト対象の版と条件、期待した結果と実際の結果、証跡の置き場を書く |
| 完了報告 | 実行を終えるとき | 方針からのずれ（あれば）、ケースごとに完了の判定に使う結果（中断の後に実行し直したものはその結果、[5.7](#57-中断と再開) で引き継いだものは引き継いだ結果とその理由、中断せずに同じ版で複数回実行したものはすべての結果を残してどれかが不合格なら不合格。一時的な障害が明らかなときは、その理由を記録し、テスト環境が使えなくなったこととして [5.7](#57-中断と再開) の中断と再開で扱う）、それで数えた合格・不合格・未実施のケースの件数、[5.1](#51-exit-criteria) の完了基準の判定、[5.3](#53-既知欠陥の許容基準)・[5.4](#54-未実施ケースの扱い) の許容判断 |

途中の状況（実行済み・合格・不合格・未実施の件数）は、必要なときに追記する。各テスト文書は、ケースの開始記録のように、ケースごとに要る記録の項目だけを定める。

- 理由: 1 回の実行の開始・中断・結果・完了を 1 か所にまとめれば、どの版と条件での結果かを後から辿れる。追記だけにすれば、不合格を合格へ書き換えていないことを確かめられる（[5.1](#51-exit-criteria)）。ケースの開始記録を実行の開始記録と分けるのは、書く時期（実行の始めか、各ケースの始めか）と中身（開始基準を満たしたことか、照合のために事前に固定したものか）が違うためである
- 却下: 状況報告・完了報告・実行ログを別々の文書にする案（1 回の実行の記録が散らばり、個人の開発では書く手間が見合わない）。ケースの開始記録を実行の開始記録に含める案（ケースごとに始める時期が違うと、書いた記録を後から書き換えることになる）

### 5.6 開始基準

各テストレベルの正式な実行（[5.1](#51-exit-criteria) の完了基準で判定するために、対象範囲のテストケースを実行すること）は、次の開始基準（entry criteria）をすべて満たしてから始める。満たしたことは、確かめた日と対象の版（commit）とともに、実行の開始記録（[5.5](#55-テスト結果の記録)）に残す。[3.4](#34-テストを先に書く進め方) でテストを実装より先に書いて動かすことと、テストケースを書くことは、開始基準を待たない。各テストケースの前提条件（[`70_ST.md`](70_ST.md) の「前提条件」の列など）は、ケースごとに満たす状態であり、開始基準とは別に扱う。

| レベル | テストの基になる文書 | テスト文書 | 下位レベル |
|---|---|---|---|
| UT | `40_LLD.md` のステータスが「確定」 | `50_UT.md` のステータスが「確定」 | なし |
| IT | [`30_HLD.md`](30_HLD.md) のステータスが「確定」 | `60_IT.md` のステータスが「確定」 | IT の対象のプログラムごとに、UT の正式な実行を終え、実行したケースが 1 件以上あり、全ケースの結果（合格・不合格・未実施）を記録してある |
| ST | [`20_SRS.md`](20_SRS.md) と [`10_URD.md`](10_URD.md) のステータスが「確定」 | [`70_ST.md`](70_ST.md) のステータスが「確定」 | IT の内部結合と外部結合のそれぞれで、正式な実行を終え、実行したケースが 1 件以上あり、全ケースの結果（合格・不合格・未実施）を記録してある（IT の対象のプログラムの UT は、IT の開始基準で確かめてある） |

全レベルに共通して、次も満たす。

- テスト対象の版（commit）を 1 つに決め、その版でテスト対象とそのレベルのテストのビルドが通る
- [4](#4-テスト環境) のテスト環境と、実行するテストケースが使う試験データ（[3.2](#32-実データ依存の扱い) のローカルキャッシュと、[3.3](#33-期待値の根拠) の期待値の根拠を含む）がそろっている。試験データを用意できないケースは、未実施として記録し、残りのケースで始めてよい（完了の判定では [5.4](#54-未実施ケースの扱い) に従う）

下位レベルの結果に不合格か未実施が残っていても、上位レベルを始めてよい。ただし、上の表の単位（IT は対象のプログラムごと、ST は IT の内部結合と外部結合のそれぞれ）で、全ケースが未実施（実行 0 件）のものがあるときは、下位レベルを実行したと言えず、切り分けに使う結果も無いので、始めない。上位レベルを始めるために、下位レベルの不合格と未実施に [5.3](#53-既知欠陥の許容基準)・[5.4](#54-未実施ケースの扱い) の許容判断は要らない（許容判断は、各レベルの完了の判定で要る）。下位レベルを実行した版がテスト対象の版と違うとき、または下位レベルに不合格か未実施が残っているときは、その版とケース ID を実行の開始記録に書く。

- 理由: CTFL シラバス v4.0.1 の 5.1.3 は、テストレベルごとに開始基準と完了基準を定めるとする。同じシラバスの 2.2 は、順次型の開発モデルでは前の段階の完了基準が次の段階の開始基準の一部になることが多いとする（この 2 か所は、シラバスの原文で確かめた〔2026-10-07〕。[SOURCES「開発プロセスの参照規格」](../ref/SOURCES.md#開発プロセスの参照規格)）。本書は [2](#2-テストレベル定義と役割分担) で各レベルを独立検証としたので、下位レベルからは合格ではなく、実行して記録したことだけを入れる。下位レベルの不合格を知ったうえで上位レベルを始めれば、上位レベルで不合格が出たときに、原因が下位レベルの既知の不合格かを切り分けやすい。下位レベルを実行した版を上位レベルの版にそろえることは求めない。そろえると、上位レベルの途中で欠陥を直して版を変えるたびに、下位レベルから実行し直すことになる。版の違いは記録して、切り分けに使う。基になる文書とテスト文書の確定を入れるのは、実行の途中で期待値の根拠が変わらないようにするためである
- 却下: 下位レベルの完了基準（[5.1](#51-exit-criteria)）を満たすことを開始基準にする案（下位レベルの不合格と未実施のそれぞれに [5.3](#53-既知欠陥の許容基準)・[5.4](#54-未実施ケースの扱い) の許容判断が済むまで上位レベルを始められず、[2](#2-テストレベル定義と役割分担) の独立検証とも合わない）。下位レベルに触れない案（下位レベルの結果を切り分けに使えない）

### 5.7 中断と再開

正式な実行の途中で、次のどれかが起きたときは、実行を中断する。

- 基になる文書かテスト文書で、期待値・手順・合否判定基準を変える改訂をした
- テスト対象（製品のコード、テストコード）、試験データ、設定を変えた。commit の有無によらない（リポジトリの外に置く試験データと、追跡しない設定の変更も含む）
- テスト環境か試験データが使えなくなった
- そのほか、[5.6](#56-開始基準) の開始基準のどれかを満たさなくなった

期待値・手順・合否判定基準を変えない文書の改訂（誤字や書式の直し、文書だけの commit を含む）は、中断の理由にしない。中断した日、理由、それまでに実行したケースの ID を [5.5](#55-テスト結果の記録) の記録に書く。

再開するときは、開始基準を改めて確かめて記録する。中断したレベルのケースのうち、中断の前に実行したものは、新しい版・文書・環境で実行し直す。中断の理由の影響を受けないと判断したケースは、判断の理由を記録して結果を引き継いでよい。再開しない実行は、残りのケースを未実施として記録して終える。下位レベルは実行し直さなくてよい（[5.6](#56-開始基準) は下位レベルを実行した版を問わない）。ただし、上位レベルのケースが下位レベルのケースの結果をそのまま合否に使うとき（[`70_ST.md`](70_ST.md) で UT・IT に移したケースを ST が参照する場合など）は、その結果がテスト対象の版のものであることを要する。違うときは、下位レベルのそのケースを実行し直すか、上位レベルのケースを未実施とする。

- 理由: 結果は対象の版と入力・設定とともに記録する（[5.5](#55-テスト結果の記録)）ので、途中で版や基になる文書が変わると、1 回の実行の中に条件の違う結果が混ざる。中断と再開の条件を開始基準に結び付ければ、別の基準を持たずに済む。全国のデータを使う ST のように実行に時間がかかるケースを毎回すべて実行し直さずに済むよう、影響を受けないケースは理由を記録して引き継げるようにする

## 6. テストケースID命名の大枠

テストケースIDは `<レベル>-<対象>-<連番>` の形式を共通規則とする。

| レベル記号 | 対象記法 | 例 |
|---|---|---|
| `UT` | LLD のモジュール名（LLD の ID LLD-<モジュール名> の名前） | `UT-decode_elevation-01` |
| `IT` | HLD 3 章の結合のつなぎ目の ID（内部結合は `C<N>-I<連番>`、外部結合は `C<N>-E<連番>`） | `IT-C5-I1-01` |
| `ST` | 対象FR/NFR番号、またはUR番号 | `ST-FR-001-01`、`ST-UR-008-01` |

- 連番は 2 桁（`01` から）。`ST` の対象の番号は 3 桁（`FR-001`）。
- 手動で行うケースは、ID の直後に `（手動）` を付ける。`tools/lint_trace.py` は、テストのコードの実装の確認からこのケースを外す。

詳細な命名規則・記述テンプレート（前提条件・手順・期待結果・合否判定基準の構成）は各ファミリの本体文書（`50_UT.md`・`60_IT.md`・`70_ST.md`）に委ねる。
