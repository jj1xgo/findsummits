## 1. 目的と記述規約

### 1.1 目的・スコープ

本書は単体テスト（UT）のテストケースを定める。単体テストは、関数単位の内部の動きと、1 本のプログラムの中の関数のつながりを確かめる（[テスト方針書 §2](02_test_policy.md#2-テストレベル定義と役割分担)）。ケースの上位は詳細設計書（LLD、[`40_LLD.md`](40_LLD.md)）のモジュールで、ほかのモジュールから呼ぶ関数の名前は概要設計書（HLD）の [3 章](30_HLD.md#3-プログラム構造)を、内部の関数の名前・型・メッセージの文面・ファイルへの割り付けは LLD を正本とし、本書では書き写さずにリンクで指す。プログラムの境界をまたぐ受け渡しは結合テスト（IT）の仕様書 [`60_IT.md`](60_IT.md) で、システムの外へ出す成果物の中身はシステムテスト（ST）の仕様書 [`70_ST.md`](70_ST.md) で確かめる。

テストレベル定義・開始基準・合否判定基準・カバレッジの粒度・結果の記録は、[`02_test_policy.md`](02_test_policy.md) を正本とし、本書では重複して書かない。本書は LLD の段で作り、LLD の各モジュールの節の「UT 候補」の小節からケースを起こす（[ADR-LLD-001](decisions/ADR-LLD-001-lld-format-module-granularity-and-t2-timing.md) の Decision 8）。今は 2.1 共通部品と 3.1 `preprocess_boundaries` を置いてある。ほかのモジュールの節は、LLD から移すときに足す。

### 1.2 テストケース記述規約

- **テストケースID命名規則**: [テスト方針書 §6](02_test_policy.md#6-テストケースid命名の大枠) の共通規則に従い、`UT-<モジュール名>-<連番>` とする（`UT-common-001`）。モジュール名は LLD の ID（`LLD-<モジュール名>`）の名前、連番は 3 桁で `001` から振る。手動のケース（合否が人の知覚や読解そのもので決まるケース。[テスト方針書 §3.1](02_test_policy.md#31-自動テストと手動確認の役割分担)）は、ID の直後に `（手動）` を付ける。
- **章立て**: 2 章以降は LLD の §2 以降と同じ番号にし、LLD のモジュールの節 N.M のケースを本書の N.M に置く（LLD 2.1 の `LLD-common` は本書の 2.1）。UT 候補を持たない横断の節（LLD の 2.2〜2.6）は置かない。モジュールを本書へ移したら、LLD のそのモジュールの「UT 候補」の小節は、本書の同じ番号の節への参照の 1 文にし、表を残さない（表の行が残っていないこと、本書の同じ番号の節へのリンクがあること、ケースがその節の下にあることを `make lint` が照らす。[開発ガイド 6.2](03_development.md#62-検査)）。
- **記述テンプレート**: 各モジュールの節は、ID・確かめること・前提条件・手順・期待結果・合否判定基準の 6 列の表に、1 ケース 1 行で書く。
  - 確かめること: そのケースが確かめる挙動を短く書く。
  - 前提条件: テストを起こす前・対象を呼ぶ前に、テストのコードが整える物と状態（共通の準備の名前、置くファイルとディレクトリ、設定ファイルの中身、呼ぶ前に差し替える物）。
  - 手順: 対象の呼び方と渡すもの、子のプロセスの試験用のプログラムの中で行うこと（`start_log` の後の差し替えや、子を起こす順を含む）。
  - 期待結果: 正しい実装で得られる出力と状態。
  - 合否判定基準: 期待結果のうちテストのコードが照合するものと、比べ方。期待結果のすべてを一致で照らすときは「期待結果のすべてと一致」と書く。
- **共通の準備**: 1 つのモジュールの多くのケースが使う準備は、そのモジュールの節の前置きに名前を付けて書き、前提条件の列から名前で指す。ケースに固有の準備は、名前の後に書く。
- **番号だけで指す読み方**: 節の中で番号だけで指すとき（`UT 18`、表の中の `04 の (a)`）は、連番を数として読む（`UT 18` はその節のモジュールの `-018`）。モジュール名を省いた ID（`UT-079`、`UT-060・063`）は、その節のモジュールのケースを指す。LLD の本文の番号だけの参照も、移した後は同じ読み方で本書のケースを指す。
- **上位の文書の節を指す書き方**: LLD の節は `LLD の [2.4](40_LLD.md#24-言語ごとに別に実装する式のテストベクトル)` の形（「LLD の」をリンクの外に置き、リンクの文字列は節の番号だけ）で指す。HLD の節も `HLD の [2.3.2](30_HLD.md#232-設定ファイル)` の形で指す（リンクの文字列を番号だけにすると、`make lint` がリンク先の見出しの番号と照らす）。本書の 1.2 と LLD の 1.2 のように、番号だけでは取り違えるので、LLD と HLD の節を番号だけで書かない。
- **カバレッジ粒度**: [テスト方針書 §5.2](02_test_policy.md#52-カバレッジ粒度の正本) に従う。モジュールごとのケースの選び方の理由は、そのモジュールの節の前置きに書く。
- **期待値の記録**: 各ケースの期待結果は、前提条件と手順に書いた入力から LLD と上位の文書に従って導き、実行の前に記録する。製品の出力から写さない（[テスト方針書 §3.3](02_test_policy.md#33-期待値の根拠)）。
- **結果の記録**: 各ケースの結果は[テスト方針書 §5.5](02_test_policy.md#55-テスト結果の記録) の項目で記録する。
- **IT から移したケースの置き換え**: [`60_IT.md` の §5](60_IT.md#5-st-から移したケースの対応表) の「UT（`50_UT.md` で作る）」の行は、IT の対応表の行を起点に置き換える。モジュールを本書へ移すときに、その行ごとに、ST のケース（[`70_ST.md`](70_ST.md)）の前提条件・手順・期待結果・合否判定基準を読み、それを満たす UT のケースを移すモジュールのケースから選ぶ（LLD は ST のケース ID を書いていないことが多い）。満たすケースがすべて本書にそろったら、その行の 2 列目を、それらのケースの ID のコード表記を `・` で並べたものに置き換える。ほかのモジュールのケースも要る行は、そのモジュールを移すまで置き換えない。満たすケースが LLD のどのモジュールにも無いと分かったら、置き換えずに持ち主に報告する。

## 2. 共通部品と横断

### 2.1 共通部品

対象は LLD の [2.1](40_LLD.md#21-共通部品) の `LLD-common`。期待結果の記号（CF1〜CF7・A1〜A5・R1〜R3）は LLD の [2.1.4](40_LLD.md#214-メッセージ文面)、記号（G1〜G7・L1〜L3）は LLD の [2.2](40_LLD.md#22-ログとメッセージの文面) が定める。

すべて自動（合否をテストのコードが判定できる）。`start_log` を呼ぶケースと `acquire_lock` を呼ぶケースは、すべて子のプロセス（`subprocess` で、テストを動かしている Python〈`sys.executable`〉に `-c <試験用の短いプログラム>` を付けて起動し、`scripts/` を import の探索先に入れる。`start_log` に渡す `Config` は、子のプロセスの中で `load_config` で読むので、各ケースの前に、`data_dir` と `log_dir` を絶対パスで書いた設定ファイルを置く）で動かし、終了コード・標準出力・標準エラー出力・ログファイルを親のテストが読んで確かめる（`start_log` は `sys.exit`・`sys.excepthook`・シグナルのハンドラ・`atexit` を差し替えたままにし、2 回目の呼び出しは `RuntimeError` になるので、テストのランナーと同じプロセスで呼ばない）。ログファイルに書けない場面は、子のプロセスの試験用のプログラムの中で、`start_log` の後に `common._state.file` を、`write` が `OSError(errno.ENOSPC)` を上げる物に差し替えて起こす（終わりの行だけを失敗させるときは、`_finish_log` が書く直前に差し替わるよう、`atexit.register` で差し替えの処理を `start_log` の後に登録する。`atexit` は登録の逆順に動くので、差し替えが先に動く）。結合テスト（IT）の仕様書 `60_IT.md` の §5 の対応表で「UT（`50_UT.md` で作る）」とした行に、共通部品に当たるものは無い。HLD を書く段で[#202](https://github.com/jj1xgo/findsummits/issues/202)「LLD と IT を書くときに、UT と IT の候補を割り当てる」に挙がった UT 候補のうち共通部品に当たるのは、同じ名前のログファイル（`UT-common-020`）、ログファイルに書けなくなったとき（`UT-common-022`）、終わりの行だけ書けなかったとき（`UT-common-023`）の 3 つ。`start_log` を呼ばずに `sys.exit` で止まるケース（`load_config`・`read_mesh_arg`・`read_mesh_list_file` の誤り）は、`sys.exit` がまだ差し替えられていないので、同じプロセスで `SystemExit` を捕まえて、終了コードと標準エラー出力を確かめてよい。ログファイルの行の期待は、先頭の時刻と空白を除いた文面で書く。`start_log` を呼ぶと標準出力に L1・L2 の行が時刻なしで出るので、標準出力の期待にはこれらも含める。

表の前提条件の列の共通の準備は次の 2 つ。ケースに固有の準備は、その後に書く。

- **同じプロセス**: テストを動かしているプロセスの中で、対象の関数を直接呼ぶ。設定ファイルを使うケースは、ケースごとに一時のディレクトリを作り、その下に設定ファイルを書いて絶対パスを渡す（`data_dir`・`log_dir` を書くときは、一時のディレクトリの下の絶対パスにする）。止まるケースは `SystemExit` を捕まえて終了コードを読み、標準出力と標準エラー出力は差し替えて捕まえる（`contextlib.redirect_stdout`・`redirect_stderr`）。
- **子のプロセス**: 上に書いた子のプロセスの形で動かす。子に渡す設定ファイルは、親が一時のディレクトリに置く（`data_dir` と `log_dir` を、一時のディレクトリの下の絶対パスで書く）。子の試験用のプログラムは、`StartTime.now()` と `load_config` を呼んでから（ケースが書かなければ、`keys` は `data_dir` と `log_dir`、`required` は `data_dir`）、手順の列のケースの処理をする。`start_log` は、手順の列が書く位置で 1 回だけ、`start_log(<config の log_dir>, config, '<試験用の名前>', sys.argv[1:], start)` の形で呼ぶ（手順の列が `start_log` の位置を書いていないケースは、ケースの処理の最初に呼ぶ。`UT-common-024` はそのケースの手順のとおり）。

## 3. CMP1 行政区域前処理

### 3.1 `preprocess_boundaries`

対象は LLD の [3.1](40_LLD.md#31-preprocess_boundaries) の `LLD-preprocess_boundaries`。期待結果の記号のうち、BA1〜BA4・BZ1・BZ2・BL1〜BL5・BW1・BV1〜BV8・BF1〜BF4 は LLD の [3.1.4](40_LLD.md#314-メッセージ文面)、CF1・R1 は LLD の [2.1.4](40_LLD.md#214-メッセージ文面)、G1・L1〜L3 は LLD の [2.2](40_LLD.md#22-ログとメッセージの文面) が定める。

すべて自動（合否をテストのコードが判定できる）。この節の共通の準備は次の 4 つ（2.1 の同じ名前の準備とは別のもの）。止まるケースの期待結果の「メッセージ」は、標準エラー出力の行の文面（LLD の [2.2](40_LLD.md#22-ログとメッセージの文面)・LLD の [2.1.4](40_LLD.md#214-メッセージ文面)・LLD の [3.1.4](40_LLD.md#314-メッセージ文面) の文面に値を入れたもの）。ログファイルの行の期待結果は、先頭の時刻と空白を除いた文面。

- **同じプロセス**: テストのプロセスの中で `scripts/` を import の探索先に入れて `import preprocess_boundaries` し、関数を直接呼ぶ（`start_log` を呼ばない。`log_info` などは画面にだけ出る）。止まるケースは `SystemExit` を捕まえて終了コードを読み、標準出力と標準エラー出力は `contextlib.redirect_stdout`・`redirect_stderr` で捕まえる。一時のディレクトリ `<tmp>` をケースごとに作り、`tempfile.tempdir` を `<tmp>/t`（作っておく）に差し替える（作業用のディレクトリの残りを見るため。ケースの後に元に戻す）。1 つのケースの中で入力を何通りか試すとき（(a)(b)… に分けたケースなど）は、入力ごとに `<tmp>` の下の置き場（`<tmp>/b`・`<tmp>/data` など）を消して作り直し、前の入力の残りを持ち越さない（同じ名前のディレクトリを `os.makedirs` で 2 度作って失敗しないため）。
- **小さな N03**: 次の 67 フィーチャの FeatureCollection（UTF-8 の JSON。`properties` には `N03_001`〜`N03_005`・`N03_007` の 6 つのキーを置き、書かないものは `null`）。各フィーチャの幾何は、ポリゴンを 1 つ持つ `MultiPolygon` で、ポリゴンは外側の環だけの矩形 `[[w, s], [e, s], [e, n], [w, n], [w, s]]`（反時計回り）。
  - 地域のフィーチャ 60: HLD の [4.17.2](30_HLD.md#4172-処理の流れ) の対応表の `i` 行目（0 から）ごとに 1 つ。`JA8` の行は `N03_001` が `北海道`・`N03_002` が表の名前、ほかは `N03_001` が表の名前。`N03_004` は `市` と `i` の 2 桁（`市00`）、`N03_007` は `9` と `i` の 4 桁（`90000`）。矩形は `w = 120 + 0.2 × (i mod 10)`、`s = 25 + 0.2 × floor(i / 10)`、`e = w + 0.1`、`n = s + 0.1`。ただし根室振興局の行は `w = 147.5`、`s = 44.8`、`e = 147.6`、`n = 44.9`（メッシュ `6747` の中）。
  - 北方領土のフィーチャ 7: `k` = 0〜5 について、`N03_001` が `北海道`・`N03_002` が `根室振興局`・`N03_004` が `村` と `k`（`村0`）・`N03_007` が `1695 + k` を 0 で埋めた 5 桁（`f'{1695 + k:05d}'`。`01695`〜`01700`）で、矩形は `w = 148.1 + 0.1 × k`、`s = 45.5`、`e = w + 0.05`、`n = 45.55`（メッシュ `6848` の中）。7 つ目は `01695` の 2 つ目のフィーチャ（`N03_004` は `村0`）で、矩形は `w = 147.1`、`s = 44.8`、`e = 147.15`、`n = 44.85`（メッシュ `6747` の中。`6747` は根室振興局の矩形も持つので、除外メッシュにならない）。
