# ドキュメント管理ルール

docs/ 配下および `ref/SOURCES.md` を編集・作成するときはこのファイルのルールに従う。

## ベースラインドキュメント採番ルール

`docs/` 配下のベースラインドキュメント（常駐 + ステージ別）は、10 番台カテゴリ方式で採番する。

| 範囲 | カテゴリ | 本体ファイル |
|---|---|---|
| 00 ～ 09 | 共通（常駐） | `00_GLOSSARY.md`、`01_environment.md` 等 |
| 10 ～ 19 | ユーザー要件定義書（URD）ファミリ | `10_URD.md` |
| 20 ～ 29 | ソフトウェア要件仕様書（SRS）ファミリ | `20_SRS.md` |
| 30 ～ 39 | 概要設計（HLD）ファミリ | `30_HLD.md` |
| 40 ～ 49 | 詳細設計（LLD）ファミリ | `40_LLD.md` |
| 50 ～ 59 | 単体テスト（UT）ファミリ | `50_UT.md` |
| 60 ～ 69 | 結合テスト（IT）ファミリ | `60_IT.md` |
| 70 ～ 79 | システムテスト（ST）ファミリ | `70_ST.md` |
| 80 ～ 89 | 運用フェーズ（OPS）ファミリ | `80_OPS.md` |
| 90 ～ 99 | 予備（予定外） | カテゴリ未確定の暫定配置 |

- **対象**: `docs/` 配下の常駐 + ステージ別ドキュメント。`ADR-*.md`・`research/`・`figures/`・`mockup/`・`ref/SOURCES.md` は対象外
- **本体は X0**、**付随ドキュメントは X1〜X9**（例: `20_SRS.md` 本体、`21_SRS_RTM.md` 等）
- カテゴリ未確定のドキュメントは **90 番台**に暫定配置し、確定後に該当カテゴリへリネームする
- リネーム時は参照箇所を全て更新する（`grep` で旧パス残存ゼロを確認）

## 各ステージの成果物

各ステージの成果物は上記採番表の本体ファイル（`10_URD.md` 〜 `80_OPS.md`）として `docs/` に作成する。
例外は実装フェーズ（COD）のみで、成果物は `src/*.c`・`scripts/*.py`（docs 対象外）。

常駐ドキュメント（ステージ不問）:

- `docs/00_GLOSSARY.md` — 用語集（全文書から参照）
- `docs/01_environment.md` — 環境定義
- `docs/02_test_policy.md` — テスト方針書（UT/IT/ST横断のテストレベル定義・開始基準・合否判定基準・テスト計画・テストの記録）
- `docs/03_development.md` — 共通開発規則の詳細（依存管理・検証・フェーズゲート・バージョン・要求の追跡・課題とレビュー）
- `ref/SOURCES.md` — 参照資料の出典一覧
- `docs/decisions/ADR-*.md` — アーキテクチャ決定記録（ADR）
- `docs/decisions/research/` — ADR 決定前の設計調査資料

`docs/` は devel・main 両ブランチに含める。

## モックアップの扱い

`docs/mockup/`（`viewer_mockup.html` ＋ `summits_data.js`）は HTML ビューアの UI を確定させる
プロトタイプ（紙芝居レベル）。**正は仕様書（SRS/HLD/LLD）**であり、モックアップは権威ではなく
仕様と同期させる参照物（仕様優先原則を維持）。

- モックアップ更新時は、**観測可能挙動を SRS、実装具体値（配色・サイズ・パラメータ・z-index・
  レイアウト等）を HLD/LLD** へ反映要否判断する。HLD/LLD 未作成の段階では HLD 相当の UI 具体値は
  モックアップが暫定保持し、HLD/LLD 起票時に抽出する。
- 埋め込みサンプルデータ（例示フィーチャ）は仕様ではないため、仕様反映の対象外。
- モックアップは作業用ビューアと同じテンプレート構成（HTML + データファイル）にサンプルデータを与えたものとし、
  データの差し替えでローカル確認する。共通化と昇格の方法は HLD（[ADR-URD-019](decisions/ADR-URD-019-public-viewer-served-from-evidence-geojson.md)）。

## GLOSSARY と SOURCES の役割分担

| ファイル | 役割 | 書くこと | 書かないこと |
|---|---|---|---|
| `docs/00_GLOSSARY.md` | 用語の概念定義（What） | 「〇〇とは何か」の説明。必要に応じて仕様リンクや SOURCES へのリンク | 利用規約 URL・帰属表示義務の詳細 |
| `ref/SOURCES.md` | 出典・利用規約の詳細（Where/How） | 取得元 URL・利用規約 URL・帰属表示義務・利用形態 | 概念の説明 |

**更新ルール**:

- 新しいデータソース（地図タイル・参照ファイル等）を追加するときは **両方** を更新する
- 利用規約 URL や帰属表示義務の変更は SOURCES のみ更新すれば良い
- GLOSSARY の説明文に規約詳細を書かず、SOURCES へのリンクで委ねること
- 各セクション冒頭の注釈（`利用規約・出典の詳細は ref/SOURCES.md を参照`）を維持すること

## 外部I/F・ユーザー入力・内部データ・内部トランザクションの分類ルール

| 分類 | 定義 | 主な例 |
|---|---|---|
| 外部I/F | システム境界の外に存在するもの、またはユーザーが外部で利用するためにシステムが出力する成果物 | 国土地理院タイルサーバー・申請書 XLSX・標高地形図 PNG |
| ユーザー入力 | ユーザーがツールに与える入力 | コマンド引数・HTML ビューア上のユーザー入力・N03 行政区域 ZIP |
| 内部データ | システムが生成・管理するもの（メモリ・一時ファイル・永続キャッシュ・ブラウザ永続化を含む） | ローカルキャッシュ・FR 間中間データ・per-mesh CSV・N03 前処理済み GeoJSON・localStorage 編集内容 |
| 内部トランザクション | 特定の解析処理のスコープ内でのみ有効で、処理完了時に破棄される値（永続化されず、後続フェーズや他の解析からは参照されない） | [FR-002](20_SRS.md#fr-002-dem-階層フォールバック)/[FR-003](20_SRS.md#fr-003-標高デコードnodata-処理) 間の生 RGB / 標高値（小規模）、[FR-004](20_SRS.md#fr-004-33メッシュ結合解析オーケストレーション) 出力の解析範囲標高グリッド・[FR-005](20_SRS.md#fr-005-ピーク候補検出) 出力のピーク候補リスト・[FR-006](20_SRS.md#fr-006-コル検出プロミネンス計算) 出力のピーク候補・コル情報リスト（大規模だがスコープローカル） |

- SRS §6「外部インターフェース仕様」には **外部I/F のみ** を記載する
- ユーザー入力は SRS §7、内部データは SRS §8 に記載する
- 内部トランザクションは [§8.1](20_SRS.md#81-内部データ一覧)（内部データ一覧）の対象外。発生する FR の入出力欄に発生元 FR を明示する
- **各 FR の入出力テーブルは、該当する全外部I/F を列挙する**（実行時取得・キャッシュ再利用を問わない）。生成 FR が出力する成果物の実行時 I/F は、その実行時挙動を定義する FR に集約する

## ドキュメントフォーマット標準

各文書のヘッダーテーブル:

```text
| 項目 | 内容 |
|---|---|
| 作成日 | YYYY-MM-DD |
| 最終更新日 | YYYY-MM-DD |
| ステータス | ドラフト / 確定 |
```

- バージョン番号は記載しない（git で管理）
- 本文冒頭に目次（Markdown アンカーリンク）を設ける
- 用語定義は冒頭 blockquote ではなく番号付きセクション「N. 用語定義」として記載する
- 用語集の[開発プロセス用語](00_GLOSSARY.md#開発プロセス用語)の「開発ステージ」と「設計判断記録」の表にある略語（今は URD・SRS・HLD・LLD・COD・UT・IT・ST・OPS・ADR）は、各文書の本文の初出で、日本語名を先に書いて併記する（例: `結合テスト（IT）`）。日本語名はその表の「説明」の最初の語で、文書を指すときはその文書の題の名前でもよい（例: `概要設計書（HLD）`、`システムテスト仕様書（ST）`）。略語の説明としての英語の正式名は用語集だけに書く（資料の原題は除く）。対象は `docs/` の番号付き文書（用語集を除く）、本書、`ref/SOURCES.md` で、ADR は対象外。題名の行（題名で併記していても、本文の初出は別に併記する）、見出し、ヘッダーテーブル、目次、追跡の宣言の行、行頭の太字の項目名、コードスパン、フェンスのコードブロック、ファイル名・パス、識別子の一部（`ADR-SRS-037`、`ST-FR-001-01` など）、リンク先は初出に数えない。ヘッダーテーブル以外の表のセルは本文として数える。初出がリンクの文字列の中なら、日本語名と略語をリンクの前に出し、リンクの文字列からは略語と `§` を外す（`SRS §3.3` は `3.3` にする。例: `ソフトウェア要件仕様書（SRS）の [3.3](20_SRS.md#33-フェーズ分割)`）。斜線の並び（`HLD/LLD`）なら、各略語に日本語名を添えて「・」で並べる
- 外部資料への参照は本文中にインライン注記のみ（例: `（参照: [SOURCES.md](../ref/SOURCES.md)）`）。別途「参照資料」セクションは作らない
- 他 FR/UR/NFR/セクションへの参照は Markdown リンクで記述する（例: `[FR-004](#fr-004-33メッシュ結合解析オーケストレーション)`）。本文中の参照箇所のみが対象で、処理フロー俯瞰図・ステータス欄・見出しタイトルは対象外。テストケースID等、FR/NFR/UR番号を含む複合識別子（例: `ST-FR-001-01`）はコードスパン（バッククォート）で囲み、BARE-REF検知（`make lint-md` 検査D）の誤検知対象から除外する
- 入出力テーブルの「形式」欄はファイル形式・データ型のみを記載する。特性記述（解像度・色分け・データ範囲等）は「備考」欄に記載する

## 参照する規格

`docs/` の文書と開発のプロセスは、開発プロセスと文書の構成について、[ADR-OPS-002](decisions/ADR-OPS-002-reference-standards-and-intended-deviations.md) に記録した国際規格を参照する（意味は [用語集「参照規格」](00_GLOSSARY.md#参照規格)）。データ形式・座標系・通信・数値表現の規格（ISO 8601、RFC 7946、EPSG など）は、この節の対象外とする。

- 規格に対して「準拠」と書かない（規格の要求をすべて満たすとは主張しない）。規格以外の文書や規則に従う意味の「準拠」は、この対象外とする。
- 開発プロセスや文書の構成の国際規格を名指しするときは、ADR-OPS-002 の版で書く。
- 規格との違いを見つけたら、ADR-OPS-002 の Decision 4 に従い、直すか、意図して保つ形として表に足すか、確かめられないことを記録して保留するかを決める。
- 規格の目録（URL・確認日）は [SOURCES](../ref/SOURCES.md#開発プロセスの参照規格) に置き、文書ごとに書かない。

## SRS 機能要件（FR）記述規約

`docs/20_SRS.md` の機能要件は以下の規約に従って記述する。

- **データ辞書への一元定義**: 入出力データ・設定可能項目はデータ辞書セクションで一元定義し、FR本文では参照名を使う。設定可能項目は「デフォルト値と許容範囲」のみSRSに記述し、渡し方（CLI引数/設定ファイル/環境変数）はHLDに委ねる
- **統一テンプレート**: 全FRを「概要/入力/出力/処理/異常系」の構造で記述する
- **任意入力+デフォルト動作での表現**: 「引数有無による挙動変化」を実装依存の分岐記述（モード名等）で書かず、「データ名・任意/必須・デフォルト値・制約」として表現する
- **実装方式はHLDへ**: config.ini・CLI引数・環境変数の受け渡し形式、HTTPステータス・リトライ条件、exit code等の具体値はSRSに書かず、抽象表現（「設定可能項目として取得する」等）に留める
- **データ辞書の拡張手順**: 未定義データ項目を発見したら該当セクション（外部I/F→§6／ユーザー入力→§7／内部データ→§8／設定可能パラメータ→[§2.2.1](20_SRS.md#221-設定可能項目)）に追加してからFR側で引用する。粒度はユーザーが認識できる単位とし、ピクセル単位等の詳細はHLDに委ねる。派生形補語（リスト・単一ピクセル等）は辞書側に書かずFRの入出力テーブルで補う

## HLD と LLD の書き分け

HLD（`30_HLD.md`）は、§2 に横断の規約、§3 にプログラム構造、§4・§5 に FR/NFR ごとの処理方式を書き、§6 に要求追跡マトリクスを置く（[ADR-HLD-001](decisions/ADR-HLD-001-program-structure-chapter-and-two-tier-it.md)、[ADR-HLD-002](decisions/ADR-HLD-002-hld-chapter-order-program-structure-first.md)、[ADR-HLD-005](decisions/ADR-HLD-005-hld-traceability-matrix-and-program-table.md)）。§2.11 に、ステークホルダーと関心事、関心事とビューポイントごとに答える節の対応を置く（[ADR-HLD-003](decisions/ADR-HLD-003-stakeholders-concerns-and-views-section.md)）。§2 には全体に共通する決まりだけを置き、FR に固有の異常系の場面とメッセージに含める内容、FR に固有の手順は §4 の各節に置く（[ADR-HLD-004](decisions/ADR-HLD-004-hld-section-boundaries-and-item-references.md)）。

| 書くもの | 置き場所 |
|---|---|
| プログラムの一覧、プログラムごとの入力・処理・出力、関数の一覧（名前・役割・受け取るものと返すもの）、共通部品、結合のつなぎ目 | HLD §3 |
| 処理の中身（手順、異常系、設計判断） | HLD §2・§4・§5（§3 からは手順の番号で指し、写さない） |
| 関数ごとの細部（型、内部のデータの持ち方、メッセージの文面、ファイルへの割り付け） | LLD |

- プログラムと関数の名前は HLD §3 で確定する。LLD・コード・テストは同じ名前を使い、変えるときは HLD を先に直す。
- UT は LLD に、IT は HLD §3 の結合のつなぎ目に対応する（[テスト方針書 §2](02_test_policy.md#2-テストレベル定義と役割分担)）。
- この章の並びを最終形とし、§4・§5 を付随文書へ移さない（[ADR-HLD-002](decisions/ADR-HLD-002-hld-chapter-order-program-structure-first.md)）。
- HLD に節を足すか、節の受け持ちを変えるときは、§2.11.2 の関心事の表の「答える節」と §2.11.3 の表と照らし、古くなる行を直す（[ADR-HLD-003](decisions/ADR-HLD-003-stakeholders-concerns-and-views-section.md)）。

## HLD の記号の書き方

HLD（`30_HLD.md`）で同じ決定を複数の箇所に書き写すと、直したときに追従が漏れる。記号（C・D）は番号だけでは意味が伝わらない。次のとおり書く。

- 1 つの決定の中身（式・値・手順・理由）は、その節の本文か「設計判断」の小節の D の定義のどちらか 1 か所にだけ書く。もう一方とほかの節は、節へのリンクと D の番号と題で指し、中身を書き写さない。今ある写しは、各節の spec-panel の周回で直す。
- D の定義は `- D45（題）: 本文` の形で書く。題はバッククォートを除いて 30 字以内にし、付録 A の表にも同じ題で載せる。
- 本文で D を指すときは、定義と同じ題を必ず添える（`D45「標高を求める手順は 4.4 に置き、広域解析も使う」`）。観点を絞って指すときは、題の後に括弧で書く。定義の題の中、付録 A の行、見出し、コード表記、「」の中は対象外。
- 題を変えるときは、定義・付録 A・本文の参照をそろえて直す。
- コンポーネント（C1〜C8）は、見出しから次の見出しまでの本文で、それぞれの C を最初に出すときに名前を添える（`C4（地形解析エンジン）`）。名前は [SRS §3.2](20_SRS.md#32-主要コンポーネント構成) の名前から「コンポーネント」を除いた形にする。表の行、見出し、追跡の宣言（`- **担当コンポーネント**:` など）、コード表記、リンクの文字列、「」の中、D と K の定義の題の中は数えず、名前も添えない。表計算のセル番地（`C3` など）と、`C1〜C8` のような範囲の書き方の端は、コンポーネントの参照ではないので名前を添えない。注記の括弧が続くときは `C4（地形解析エンジン。広域）` とまとめる。
- 「処理の流れ」と「未決事項と後続」の番号付きの項目を指すときは、節へのリンクに番号と項目の題を添える（`[4.8.2](#482-処理の流れ) の 4「代表行を選ぶ」`）。いくつかを並べるときは `の 2「題」・5「題」` と、各番号に題を添えて `・` でつなぎ（`と` や括弧の注記で切ると、後ろの番号は照合されないので lint が止める）、続いた範囲は題を添えずに `の 1〜5` と書く。小節の 2 つ目からの箇条は、名前を添えて `の「名前」の 3「題」` と指す。字下げした下位の項目を指すときは、親の項目に題を添えて `の 4「題」の 2` と書く（[ADR-HLD-004](decisions/ADR-HLD-004-hld-section-boundaries-and-item-references.md)）。
- 指される項目は、頭に題を置く（`4. **代表行を選ぶ**。本文`）。題の直後は「。」か、本文の続き（全角の丸括弧、矢印 `→`、コロン `：`）にする。題はバッククォートを除いて 30 字以内にする。指されない項目には題を置かなくてよい。題を変えるときは、項目と参照をそろえて直す。
- 1 つの小節に番号付きの箇条を 2 つ以上置くときは、2 つ目からの箇条のすぐ前に `**名前**` で始まる段落を置く。指される箇条は字下げしない。
- 未決事項の項目は、解決しても消さず、番号を振り直さない（解決した項目は「→ 節 で決めた」の形に縮める）。手順を足して番号が変わるときは、参照の番号と題を直す。
- 項目の題は `make lint`（`tools/lint_docs.py` の検査G）が照合する。字下げした下位の項目の番号と、HLD の外の文書からの参照は照合しない。番号の後に数を表す語が続くもの（`の 5 種類`）は参照として数えない。
- D の題は `make lint`（`tools/lint_docs.py` の検査F）が照合する。C の名前は照合しない。

## 追跡の宣言

各要素は見出しのすぐ下（最初の下位見出しより前）に、自分の上位を太字ラベルの箇条書きで宣言する。宣言が対応関係の正で、
`make lint`（`tools/lint_trace.py`）が照合する。目的と検査は [開発ガイド「6. 要求の追跡と整合」](03_development.md#6-要求の追跡と整合)。

| 段 | 置き場所 | 書式 |
|---|---|---|
| SRS | 各 FR/NFR 見出しの直下 | `- **対応 UR**: [UR-008](10_URD.md#ur-008)` |
| HLD | §2〜§5 の各節見出し（`###`）の直下 | `- **対応 SRS**: [FR-001](20_SRS.md#fr-001-標高タイル事前取得)` と `- **担当コンポーネント**: C2` |
| LLD | 各モジュール見出しの直下 | `- **ID**: LLD-<モジュール名>`、`- **対応 HLD**: [4.1](30_HLD.md#41-fr-001-標高タイル事前取得)`、`- **ファイル**:` の後にコード表記のパスを `・` で並べる |
| コード | 各ソース | `// trace: LLD-<モジュール名>`（C/C++）、`# trace: LLD-<モジュール名>`（Python・bash） |
| テストのコード | 各テスト | `trace: <テストケース ID>` |

- HLD の「対応 SRS」には FR/NFR のほか SRS の節（`[SRS §3.2](20_SRS.md#32-主要コンポーネント構成)` の形）も書ける。上位が無い節は `なし（横断の設計）` と書く。
- HLD の「担当コンポーネント」は [SRS §3.2](20_SRS.md#32-主要コンポーネント構成) のコンポーネント ID を `・` で並べる。全体にわたる節は `全体` と書く。
- HLD の §3（プログラム構造）の節は、コンポーネントごとに 1 つ（3.N が C<N>）と共通部品（3.9）である。コンポーネントの節の「対応 SRS」には、そのコンポーネントのプログラムが実現する FR（[HLD 2.2.4](30_HLD.md#224-srs-の-frnfr-との対応) の FR の表。食い違うと T4 が止める）を書き、NFR は書かない。共通部品の節は `なし（横断の設計）` と書く。「担当コンポーネント」には、その節のコンポーネントを書く。§3 の宣言は、FR/NFR を「対応 SRS」に持つ節があるかの検査（T3）には数えない（処理方式の節 §2・§4・§5 が要る）。
- HLD 末尾の[要求追跡マトリクス](30_HLD.md#6-要求追跡マトリクス)は、§2・§4・§5 の節の宣言から組み立てる（✅ は担当コンポーネントの和で、`全体` は全コンポーネントに数える。§3 の節は数えない）。食い違うと T4 が止める（[ADR-HLD-005](decisions/ADR-HLD-005-hld-traceability-matrix-and-program-table.md)）。
- LLD の「対応 HLD」には、§3 の節と、処理の正本である §4・§5 の節を `・` で並べられる（`[3.5](30_HLD.md#35-c5-統合突合)・[4.8](30_HLD.md#48-fr-008-per-mesh-csv-統合)`）。LLD が確定した後は、§3〜§5 のどの節にも、それを指すモジュールが要る（T3）。
- LLD の ID 名はモジュール名にし、UT の ID（`UT-<モジュール名>-NN`）と揃える。
- コードとテストのコードの `trace:` は、コメント（`//`・`#`・`/*`・`*` で始まるもの）に書く。C/C++ と Python は行末のコメントも数え、bash は行頭の `#` の行だけを数える。1 つのコメントに複数の ID を `,` で並べられる（`// trace: UT-a-01, UT-a-02`）。文字列リテラルの中は数えない。
- テスト文書で手動で行うケースは、ID の直後に `（手動）` を付ける。
- SRS の FR/NFR を足す・消すときは、[SRS §9](20_SRS.md#9-検証) の検証の表の行も同じ変更で足す・消す。検証方法は[用語集「要求の検証」](00_GLOSSARY.md#要求の検証)の決め方で決める（[ADR-SRS-070](decisions/ADR-SRS-070-requirement-verification-section.md)）。
- SRS の NFR を足す・消すときは、[SRS §5](20_SRS.md#5-非機能要件) の品質特性の表も同じ変更で直す（[ADR-SRS-071](decisions/ADR-SRS-071-nfr-quality-characteristics-mapping.md)）。

## ADR 管理ルール

**いつ作るか**: アーキテクチャ上の重要な判断（実装方針・技術選択・スコープ決定）をしたとき。

**命名規則**: `docs/decisions/ADR-{STAGE}-NNN-kebab-case-description.md`

- `{STAGE}` は `URD` / `SRS` / `HLD` / `LLD` / `COD` / `UT` / `IT` / `ST` / `OPS` の 9 種類
- 判断の中身が最も自然に属するステージを選ぶ（上流側で決められるなら上流を優先）
- `NNN` は 3 桁連番で **ステージごとに独立**
- 既存 ADR の番号は維持。新規は各ステージの現状最大値 + 1 から採番（`ls docs/decisions/ | grep ADR-{STAGE}` で最大値を確認して +1）
- 詳細は `docs/00_GLOSSARY.md` の「ADR 命名規約」を参照

**フォーマット**:

```markdown
| 状態 | 採用・実装済み / 採用・未実装 / 検討中 / 却下 |
| 決定日 | YYYY-MM-DD |

## Context
## Decision
## Alternatives
## Consequences
```

**参照ルール**:

- ADR は自己完結した文書とする
- 参照可能なファイル: `docs/` 配下・`ref/` 配下・ルートの `AGENTS.md`・`README.md`
- **内部トラッカーID（`ISSUE-XXX`/`BUG-XXX`）を docs に書かない**。経緯は日付・文脈・ADR へのリンクで残す。違反は `make lint-md`（検査C）で検出される
- **`mgmt/` への参照は禁止**（廃止済みのディレクトリのため参照先が存在しない）
- 詳細な調査資料が必要な場合は `docs/decisions/research/` に置き ADR から参照する

**調査資料（research/）**:

- ADR の意思決定に至る検討過程・比較分析・上位モデル（Fable/Opus）相談内容等を記録する
- 内容は生の検討資料として整形不要
- 命名: `docs/decisions/research/<説明的な名前>.md`

**URD/SRS との相互参照**:

- URD のスコープ外・制約の根拠が ADR にある場合は URD からリンクを付ける
