# ADR-SRS-076: SRS の概要・台帳・追跡の写し漏れを直し、起動時の指定の形を HLD に委ねる

| 項目 | 内容 |
|---|---|
| 状態 | 採用・実装済み |
| 決定日 | 2026-10-12 |

---

## Context

2026-10-12 に、改訂した多視点のレビュー（spec-panel）で、ソフトウェア要件仕様書（SRS）の §1〜3 と §5〜10 を見直した（[#204](https://github.com/jj1xgo/findsummits/issues/204)）。照らした相手は URD、§4 の各 FR、[ADR-OPS-002](ADR-OPS-002-reference-standards-and-intended-deviations.md) である。次の食い違いが見つかった。どれも要求の中身ではなく、同じ決定を写した箇所の間の食い違いである。

1. [FR-011](../20_SRS.md#fr-011-申請書-xlsx-生成)・[FR-012](../20_SRS.md#fr-012-サミット一覧申請内容反映版生成)・[FR-019](../20_SRS.md#fr-019-html-ビューア機能仕様)・[FR-020](../20_SRS.md#fr-020-公開用ビューア配信)・[FR-021](../20_SRS.md#fr-021-申請エビデンス-zip-生成) の入力表は、CDN から実行時に取るライブラリを種別「外部I/F」で載せている。2026-09〜10 の FR の見直しで入力表に足したときに（[FR-012](../20_SRS.md#fr-012-サミット一覧申請内容反映版生成) は [ADR-SRS-073](ADR-SRS-073-align-srs-wording-with-hld-decisions.md) で足した）、[§6.1](../20_SRS.md#61-外部if一覧) の外部I/F一覧には足していなかった。[§2.2](../20_SRS.md#22-データ辞書) は、FR のデータ名を §6〜8 で定義した名称にするとしている。
2. [§7.1](../20_SRS.md#71-ユーザー入力一覧) の SOTA 既存サミット GeoJSON の提供方法が「`$DATA_DIR/ref/` 直下」で、[§7.2.5](../20_SRS.md#725-sota-既存サミット-geojsongeojson_vn) の `$DATA_DIR/ref/geojson_v{N}/` と違っていた。
3. [§3.1](../20_SRS.md#31-システムコンテキスト) の外部成果物の箇条に、§6.1 と §3.1 の図が挙げる標高地形図・作業用 HTML ビューア・サミット一覧（突合後）・除外判断 JSON が無かった。[§3.2](../20_SRS.md#32-主要コンポーネント構成) の申請書生成 UI の主要入出力に、除外判断ファイルと除外判断 JSON が無かった。統合・突合の主要入力は「SOTA リスト CSV」で、§7 の名称と違っていた。
4. 「対応 UR」の区切りは「, 」だが、[UR-015](../10_URD.md#ur-015) を足した 6 か所（[FR-011](../20_SRS.md#fr-011-申請書-xlsx-生成)・[FR-012](../20_SRS.md#fr-012-サミット一覧申請内容反映版生成)・[FR-019](../20_SRS.md#fr-019-html-ビューア機能仕様)・[FR-020](../20_SRS.md#fr-020-公開用ビューア配信)・[FR-021](../20_SRS.md#fr-021-申請エビデンス-zip-生成)・[NFR-003](../20_SRS.md#nfr-003-再現性決定論的出力)）に「、」が混ざっていた。
5. [§7.2.1](../20_SRS.md#721-1次メッシュコードリスト) が、[FR-023](../20_SRS.md#fr-023-解析パイプライン制御) は日本全土1次メッシュコードリストを直接読まないと書いていた。[ADR-SRS-060](ADR-SRS-060-fr023-reads-mesh-lists-for-precondition.md) は、起動前提条件の検査のために読むように改めている。
6. [FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) は、突合済み統合 GeoJSON の `metadata` に出典（`attribution`・`source_url`・`license_url`）を付け、[UR-011](../10_URD.md#ur-011) を実現している（[ADR-URD-014](ADR-URD-014-gsi-tile-attribution-policy.md)）。しかし、[FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) の「対応 UR」と [§10](../20_SRS.md#10-要求追跡マトリクス) に [UR-011](../10_URD.md#ur-011) が無かった。§10 は成果物の生成を直接の寄与に数えている。
7. [§7.1](../20_SRS.md#71-ユーザー入力一覧) と §7.2.1 は、1次メッシュコードリストの渡し方を「コマンドライン引数（単一コードまたはファイルパス）」と書いていた。[文書管理ルール「SRS 機能要件（FR）記述規約」](../CLAUDE.md#srs-機能要件fr記述規約)は、CLI 引数などの受け渡し形式を概要設計書（HLD）に委ねる。[HLD 2.4](../30_HLD.md#24-cli-引数とメッシュ範囲の指定) は、コマンドの区分とメッシュ範囲の指定の形を定めている。

## Decision

1. §6.1 に、ライブラリ（Leaflet・SheetJS・JSZip）の入力の行（No.13）を足す。使用 FR は上の 5 つとする。各 FR の入力表は、使うライブラリを括弧の中に挙げる今の書き方のままにする。
2. §7.1 の SOTA 既存サミット GeoJSON の提供方法を `$DATA_DIR/ref/geojson_v{N}/` に直す。
3. §3.1 の外部成果物に 4 つを足し、§3.2 の申請書生成 UI に除外判断ファイル（入力・任意）と除外判断 JSON（出力）を足す。統合・突合の主要入力を「SOTA サミットリスト CSV」に直す。
4. 「対応 UR」の区切りを「, 」にそろえる。
5. §7.2.1 を、ADR-SRS-060 のとおり「省略したときの範囲は下流 FR の既定値に委ね、日本全土1次メッシュコードリストは起動前提条件の検査にだけ読む」に直す。
6. [FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) の「対応 UR」と §10 の [FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) の行に [UR-011](../10_URD.md#ur-011) を足す。
7. 1次メッシュコードリストとフェーズ指定オプションは「起動時に指定する」と書き、コマンドライン引数であることと指定の形は HLD 2.4 に委ねる。単一のコードでも、コードを並べたファイルでも範囲を指定できることは、利用者に見える入力の形として §7.2.1 に残す。[FR-023](../20_SRS.md#fr-023-解析パイプライン制御) の入力表の「コマンドライン引数として転送する」も「転送する」にする。

要求の中身と範囲は変えない。

## Alternatives

- **(a) 7 を今のままにする**: §7.1 の表は「提供方法 / 形態」の列を持ち、フェーズ指定オプションも構文を HLD に委ねているので、「コマンドライン引数」を提供方法の分類と読むこともできる。持ち主は、受け渡しの形を SRS に書かない規約にそろえることを選んだ。
- **(b) 1 の行を追加せず、ライブラリを §3.4 の外部システムとしてだけ扱う**: FR の入力表がすでに外部I/F として載せており、規約のとおり §6 の名称に寄せる方が直す箇所が少ない。
- **(c) 6 を追跡せず、[UR-011](../10_URD.md#ur-011) は [FR-012](../20_SRS.md#fr-012-サミット一覧申請内容反映版生成)・019・020・021 だけで実現するとみなす**: [FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) は出典の metadata を自分で作って [UR-011](../10_URD.md#ur-011) を実現しているので、後に続く FR だけを追跡するのでは足りない（ほかの FR は、metadata を写すもの、固定の出典の文面を持つもの、地図の帰属表示を出すものがあり、すべてがその metadata を写すのではない）。作る FR を追跡から外すと、[UR-011](../10_URD.md#ur-011) を変えたときに [FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) が見落とされる。

## Consequences

- SRS の §3.1・§3.2・§6.1・§7.1・§7.2.1・§7.2.6・§10、[FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定)・011・012・019・020・021・023、[NFR-003](../20_SRS.md#nfr-003-再現性決定論的出力) を直した。ツールの振る舞いは変わらない。
- システムテスト仕様書（ST）の [§5](../70_ST.md#5-urカバレッジ表) の [UR-011](../10_URD.md#ur-011) の行に [FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) を足し、出典の `metadata` を確かめるケースとして `ST-FR-009-24` を挙げた。`ST-FR-009-24` の期待結果に、`attribution`・`source_url`・`license_url` が SRS の固定値であることを足した（期待値の `EXP-APP` は、もとからこの 3 項目を含む）。
- HLD 2.4.3 は §7.2.1 を参照して「4 桁の数字ならメッシュコード、それ以外はファイルのパス」と定めており、§7.2.1 が範囲の指定の形を残すので、HLD は直さない。
