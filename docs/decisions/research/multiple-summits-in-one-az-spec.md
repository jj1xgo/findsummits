## 1. 目的と合意済みの方針

検出ピークのアクティベーションゾーン（AZ）に複数の現役 SOTA 登録が入ったとき、
登録を取り落としたり、存続対象を恣意的に選んだりせず、担当者が確認できるようにする。

2026-09-21 にメンテナが選択した方針は「全件を要確認にし、その組の申請を保留して続行」。
仕様案は Codex が作り、Claude（Opus、読み取り専用）がレビューする。
以下のフィールド名・波及範囲は、その方針を具体化した提案であり、まだ SRS の確定仕様ではない。

今回の成果物は仕様の決着である。地形解析・突合コードの実装と、担当者が保留を解除して申請へ
回す UI・判断の永続化は別作業とする。後者が未実装でも、全件の確認・無関係な候補の申請を可能にする。

## 2. 現行仕様の問題

[FR-009](../../20_SRS.md#fr-009-sotaリスト突合match_status-判定) の「マッチング一意性」には、
次の異なる主張が混在している。

- 異なる採用ピークの AZ が互いに素なら、1 登録座標の AZ 帰属先は高々 1 ピークである。
- 1 つの AZ 内の登録件数が高々 1 件であることは、それからは導けない。

前者の幾何学的説明を維持し、後者の「数学的に存在しない」という主張を削除する。
登録座標は解析ピークとは異なる外部入力であり、異なる SummitCode の座標が同じ AZ に入ることを許す。
重複の検出だけでは、誤座標・二重登録などの原因や、残すべきコードまでは確定しない。

現在の出力は、ピークに 1 個の既存コードを付与し、そのコードをコル・ポリゴン・接続線にも使用する。
[行集約モデル](../ADR-SRS-045-summit-xlsx-row-aggregation-model.md) も AZ 内既存サミット 1 件を前提とする。
したがって一意性の文章の訂正だけでは不十分で、未決着の組をコード選択なしで表現する必要がある。

## 3. 判定と保留範囲

### 3.1 AZ 内登録件数

突合対象は従来どおり JA プレフィックスの現役レコードとし、廃止済みレコードは含めない。
各ピークについて、AZ 内の異なる SummitCode の件数を数える。同じ座標でもコードが違えば別件とする。
本提案の入力前提は SummitCode が一意の CSV とする。同一コードの複数行・相反する座標の処置は
別の入力品質論点であり、この提案では先勝ち等の新たな採用規則を設けない。SRS の入力前提にもこの範囲を明記する。

| AZ 内件数 | ピークの `match_status` | AZ 内既存サミットの `match_status` | 申請カテゴリ |
|---|---|---|---|
| 0 | 従来の `new` / `dominant` 判定 | 該当なし | 従来どおり |
| 1 | `matched` | `matched` | `band_change` / `no_change` |
| 2 以上 | `ambiguous`（追加） | 全件 `ambiguous`（追加） | ピーク・登録全件とも `review` |

`ambiguous` は「AZ の幾何学的な対応先はあるが、存続する登録コードが一意に定まらない」を意味する。
全ゾーン外の孤立を意味する `unmatched` とは区別する。標高・登録日・入力順・コード順による存続選択は行わない。
保留ピークは新設候補ではないため、仮サミットコードも採番しない。

### 3.2 AZ 外の削除候補への波及

[主ピーク特定](../ADR-SRS-043-matched-peak-as-delete-reference.md) は、従来の候補集合と
プロミネンス・緯度・経度による選択規則を維持する。`ambiguous` ピークも候補に含める。
AZ に属する既存サミットの判定を先に確定し、AZ 外の削除候補だけについて主ピークを選ぶ。

- 選ばれた主ピークが `ambiguous` なら、その削除候補も同じ組として `category=review` にする。
  幾何学的な判定結果 `summit.match_status=delete` は保持するが、削除申請は出力しない。
- 他の候補ピークに自動で付け替えない。曖昧なピークを除外してから主ピークを選び直すことも行わない。
- 選ばれた主ピークが通常の `matched` / `dominant` なら、従来どおり `category=delete` とする。
  別の `ambiguous` ピークの delete 判定ゾーンにも入るという理由だけでは保留しない。
- AZ が 1 登録だけを持つ通常の `matched` ピークと、その従属削除候補には影響を与えない。

保留単位は「複数登録のある 1 ピーク、その AZ 内登録全件、そのピークが主ピークに選ばれた AZ 外削除候補」。
単なる delete 判定ゾーンの重なりから他のピークへ保留を連鎖させない。

## 4. 出力契約

### 4.1 共通の確認用属性

GeoJSON の全フィーチャと、両サミット一覧 XLSX に以下を追加する。

| 属性 | 値・意味 |
|---|---|
| `review_reason` | `multiple_summits_in_az`（複数登録ピークとその AZ 内登録・地形フィーチャ）、`ambiguous_parent`（その主ピークに従属する AZ 外削除候補と接続線）、`unmatched`（従来の孤立サミット）、通常時は空文字 |
| `review_group_id` | 同一の保留単位を結ぶ識別子。孤立 `unmatched` と通常時は空文字 |

`review_group_id` は `az:` に AZ 内登録の SummitCode を文字列昇順で `|` 連結したものを続ける。
例: `az:JA/XX-001|JA/XX-002`。従属する AZ 外削除候補のコードは識別子の構成要素に含めない。
入力順に依存せず、同じ AZ 内コード集合から同じ値を得る。異なる保留単位は同じ登録を共有しない。
この識別子は当該成果物内の結合に用い、入力データ変更後の担当者判断を引き継ぐ永続キーとはしない。

### 4.2 GeoJSON の保留単位

- ピーク Point は 1 個。`match_status=ambiguous`、`category=review` とする。
  `summit_code`・`summit_name`・`summit_name_jp` は空文字とし、任意の既存登録を代表として転記しない。
  `peak_elev`・`prominence`・`stability`・`key_col_resolved`・`points`・`analysis_count`・`expected_count` を保持する。
  `municipality`・`region_name` もピーク自身の座標から取得する。
  `is_band_change_candidate` は GeoJSON では `null`、`rationale` は空文字とする。
- コル Point・AZ / delete 判定ゾーン Polygon・ピーク→コル LineString は、通常の生成条件で保持する。
  `category=review` と、ピークの確認用属性を継承する。親参照用 `summit_code` は空文字。
- AZ 内登録は 1 登録につき summit Point を 1 個保持し、既存コード・名称・登録値をそのまま残す。
  `match_status=ambiguous`、`category=review`、`rationale` は空文字。
- AZ 外の保留削除候補も summit Point を保持し、既存コード・名称・登録値をそのまま残す。
  `match_status=delete`、`category=review`、`review_reason=ambiguous_parent` とする。
  `review_group_id` は主ピークと同じ値とする。
  `dominant_peak_code` は空文字、`dominant_peak_dist_m` は実際の主ピークまでの距離を保持する。
  存続コードを確定できないため、通常の削除根拠テンプレートを生成せず `rationale` は空文字とする。
- ピーク→各 AZ 内登録、およびピーク→各保留削除候補の `coord_diff` LineString を全件保持する。
  両線とも `category=review`、`match_status=ambiguous`（発点ピークの値）、親参照用 `summit_code` は空文字とし、
  `review_reason` は終点サミットの値、`review_group_id` はピークと同じ値とする。

保留単位内の親ピーク・コル・ポリゴン・線・既存登録の関連付けは `review_group_id` を使う。
従来の通常クラスタは `summit_code` による対応付けを維持する。
同座標の異なる登録は summit Point の `summit_code` で区別し、同じ幾何の接続線が重なっても登録を落とさない。
登録側の `municipality` / `region_name` は各登録座標、コル側はコル座標から取得する従来規則を維持する。

### 4.3 XLSX の行集約

`merged_summit.xlsx` と `merged_summit_revised.xlsx` は同じ行・カラム規則を使う。
保留組は summit Point が行を生み、ピーク・コル・ポリゴン・線は追加行を生まない。

| 行の種類 | 行数 | `match_status` | `peak_*` / コル・解析属性 | `sota_*` | `dominant_*` |
|---|---|---|---|---|---|
| AZ 内の複数登録 | 既存登録数 N | `ambiguous` | 対応ピーク・コルの値を各行に反復 | 各登録自身 | 空欄 |
| その主ピークに従属する AZ 外削除候補 | 保留削除候補数 M | `delete` | 空欄 | 各登録自身 | コードは空欄、距離は保持 |
| 従来の孤立サミット | 1 登録 1 行 | `unmatched` | 空欄 | 各登録自身 | 空欄 |

全行 `category=review` とし、確認用属性を対応 summit Point から転記する。
コード・名称・日本語名・市区町村・地域名は行の主語である既存サミット自身から取得する。
AZ 内複数登録行の `points`・`stability`・`key_col_resolved`・`col_margin_px`・`analysis_count`・
`expected_count` は対応ピーク・コルから取得し、`area_complete` は従来の AZ 完結フラグを反復する。
AZ 外保留削除候補・孤立サミットのこれらの解析属性は空欄とする。
全 review 行の `is_band_change_candidate` は空欄にする。推定標高が登録標高と異なっても変更申請にしない。
GeoJSON の `null` は XLSX では空セルに変換する。ファイル形式間の表現差であり、判定値の違いではない。
通常の new/dominant に対する既存仕様の「空欄」の具体的な GeoJSON 表現を本提案で変更する意図はない。

`ambiguous_parent` 行から主ピークの属性を調べるときは、同じ `review_group_id` を持つ
AZ 内複数登録行を参照する。どの登録行にも同じピーク・コル属性が反復されているため、
`dominant_peak_code` が空でも一覧 XLSX 単体で照合できる。

2 登録と 1 保留削除候補なら 3 行となる。ピークの反復記載は比較用の解析情報であり、
両登録をともに正常存続と認定する意味を持たない。ピークのみの架空サミット行は増やさない。

## 5. ビューアと申請

- 作業用・公開用とも、既存の「要確認」フィルターで保留単位の地形・全登録・接続線を表示する。
  5 カテゴリを維持し、6 番目のカテゴリは作らない。
- ピークの表示名は「要確認ピーク」と座標。popup には複数登録のため申請保留中であること、
  AZ 内コード一覧と、主ピーク依存によって保留された AZ 外コード一覧を区別して表示する。
  個別サミットの popup にも保留理由と同じ組の登録を確認する手段を設ける。
- 既存コード・名称の検索は各 summit Point に到達する。親ピークとの対応付け、ピーク↔コル移動は
  `review_group_id` で行い、空の `summit_code` を共通キーとして複数組を混同しない。
- 保留組には山岳名・rationale の編集 UI と申請への採用操作を設けない。
  過去の localStorage 編集値があっても、`category=review` を申請対象へ変えたり、
  現行の要確認表示・登録情報を上書きしたりしない。
- [FR-011](../../20_SRS.md#fr-011-申請書-xlsx-生成) は引き続き `add` / `delete` / `band_change` のみを出力。
  保留組から追加・変更・削除行を生成しない。無関係な組の出力は続行する。
  申請書のエクスポート時には、複数登録の組数・保留登録件数と、それらが申請対象外であることを警告表示する。
- [FR-021](../../20_SRS.md#fr-021-申請エビデンス-zip-生成) の `review.geojson` に保留単位全体を含める。
  `delete.geojson` など他のカテゴリへ保留フィーチャを重複出力しない。両一覧 XLSX には保留登録全件を含める。

担当者が確認後に削除申請へ回す経路・採否永続化を追加する際は、本提案の保留理由と組単位の関係を入力とする。
今回、保留解除まで自動化したと扱わない。現段階の申請は、保留組を除いたドラフトである。

## 6. 停止条件と観測

複数登録の組数・登録件数自体では停止しない。`unmatched` 件数しきい値には混ぜない。
これは「大量発生は必ず正常」という判断ではない。過大な AZ 等の解析不備が複数登録として現れる可能性はあり、
そのすべてを既存の不備ゲートが検出する保証もない。複数登録の正常時分布を未実測の段階で、
根拠のない停止しきい値を追加せず、警告・組数と内訳の記録・申請からの除外を採る。
初回全国解析での分布と原因の確認を再検討トリガーとし、件数ゲートの要否は実測後に決める。
その間、大量の保留は検出・提示できるが、それだけで異常終了しないという制約を採用判断に含める。
既存の AZ / delete 判定ゾーン不完結・コル未確定・孤立件数しきい値超過の不備ゲートは維持する。
`category=review` になったピークも全ピーク対象の不備検査から除外しない。
他の不備があれば全件評価後に両確認用成果物を出力して停止し、ビューア生成は従来どおりスキップする。

ログに、複数登録の組数、AZ 内登録件数、主ピーク依存による保留件数を別々に記録する。
組ごとのピーク座標・AZ 内コード一覧・保留削除候補一覧を出力し、成果物の同一組と照合可能にする。
ログの組順は `review_group_id` 昇順、組内のコード一覧は SummitCode 昇順とする。
両 XLSX の保留組の行は従来の通常行・孤立 review 行の後に置き、組間は `review_group_id` 昇順、
組内は AZ 内登録→保留削除候補の順にし、それぞれ `summit_code` 昇順にする。既存行同士の相対順は変えない。
GeoJSON の保留単位内はピーク→コル→AZ→delete 判定ゾーン→ピーク・コル線→AZ 内登録と各接続線→
保留削除候補と各接続線の順にし、登録はコード昇順とする。生成条件を満たさないコル等は飛ばす。
保留単位は既存の通常フィーチャ・孤立 summit の後に `review_group_id` 昇順で並べる。
これらを入力順によらず固定し、[NFR-003](../../20_SRS.md#nfr-003-再現性決定論的出力) を維持する。

初回全国解析では、入力リストの基準日・ソフトウェア版・解析対象範囲と上記件数を記録し、
実例の有無・原因を確認する。未実施の実件数を仕様の根拠にしない。
全国解析の実測は実装後の確認事項とし、この仕様案の完成条件とは分ける。

## 7. 受入例

以下を [ST](../../70_ST.md) の突合・一覧・ビューア・申請・ZIP の各検証へ反映する。
この表は期待結果であり、現在のプロトタイプで実行済みの結果ではない。

| 条件 | 期待結果 |
|---|---|
| AZ 内に現役登録 0 件 / 1 件 | 従来の判定・申請行・採番を維持する |
| 同一 AZ 内に現役登録 2 件、登録標高が同値でも異なってもよい | 全件 ambiguous/review。片方を選ばず、一覧は 2 行、申請は 0 行 |
| 同一 AZ 内に現役登録 3 件 | 全件を保持し、一覧は 3 行、申請は 0 行 |
| 異なるコードの登録座標が完全一致 | 異なる 2 登録として保持する。コード検索・一覧で双方を確認できる |
| 同じ AZ 内に現役 1 件・廃止済み 1 件 | 現役 1 件として通常 matched。保留組を作らない |
| 複数登録ピークが AZ 外削除候補の主ピークに選ばれる | その候補は delete/review、理由 ambiguous_parent。距離と組参照を残し、削除申請は 0 行 |
| AZ 外削除候補が通常ピークと保留ピークの両 delete 判定ゾーン内にある | 従来の主ピーク選択を先に適用し、選ばれた主ピークが保留のときだけ保留する |
| 通常 matched ピークの AZ 内 1 件・AZ 外削除候補 1 件 | 通常の削除申請を生成する。保留組の追加による取りこぼしを起こさない |
| 独立した保留組が 2 組ある | 空の親 summit_code で混同せず、各組でフィルター・popup・ピーク↔コル移動が成立する |
| 複数登録多数、孤立 unmatched はしきい値以下、他の不備なし | 続行する。複数登録は孤立件数しきい値に含めない |
| 保留ピークの area_complete=false または key_col_resolved=false | review でも不備ゲートで停止。GeoJSON/XLSX は出力する |
| 孤立 unmatched がしきい値超過 | 複数登録の有無によらず既存ゲートで停止する |
| 保留組と通常の追加・変更・削除候補が混在 | 申請は通常分のみ。警告に保留件数を表示。ZIP・両一覧には保留全件と地形参照を残す |
| 入力の列挙順を入れ替えて再実行 | 組識別子・所属・出力順・通常候補の採番が不変 |
| 以前の matched 登録の localStorage 編集値があるが、今回は保留組 | 編集値で保留を解除せず、申請へ漏出させない |

既存の `ST-FR-009-01` は AZ 内「1 件」に前提を限定する。
`ST-FR-021-01` は従来の 5 カテゴリ同梱を維持し、review に孤立サミットと複数登録の保留単位を
混在させ、両者が出力されることと、保留した接続線が delete 側へ漏れないことを確認する。

## 8. 代替案と変更対象

### 8.1 比較した案

| 案 | 評価 |
|---|---|
| 全件要確認・組の申請を保留して続行 | メンテナ選択。判断材料を保持し、無関係な申請を進められる。保留組の表現が必要 |
| 1 件を自動選択して残りを削除候補にする | 登録標高・古さ・近さだけで存続の正当性は確定しないため不採用 |
| 確認用データを出して全体停止 | 一部の登録問題で全国の申請作業も止まるため不採用 |
| 既存 unmatched として扱う | 既知の AZ 帰属を失い、孤立件数ゲートにも混入するため不採用 |
| AZ 内だけ保留し、AZ 外削除候補は主ピーク座標を根拠に申請する | 削除候補の幾何判定は確定でき、自動申請を維持できる。一方、存続登録を担当者が確認する組の一部だけを先に削除申請へ出すことになるため、本案では組単位の確認を優先して採らない |
| `dominant_peak_code` に `review_group_id` を代入して削除申請する | サミットコード欄へ非コードを混在させるため採らない。組参照は専用属性で保持する |
| 複数登録の件数しきい値を新設する | 正常分布の実測がなく停止基準を根拠付きで設定できないため、現時点では採らない。大量発生時の残存リスクと実測後の再検討を §6 に記録する |

AZ 外削除候補も保留する範囲は、本案が「その組」を具体化した提案であり、メンテナの最終確認対象とする。
[ADR-SRS-043](../ADR-SRS-043-matched-peak-as-delete-reference.md) の自動削除申請を優先する判断に対し、
存続コードが未決着な場合だけ自動申請を保留する例外を設ける。これは地形判定ができないためではなく、
関連登録を一組として確認するための意図的な制限である。通常の matched 親の削除申請は維持する。
