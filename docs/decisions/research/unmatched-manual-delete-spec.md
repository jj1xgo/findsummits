## 1. 目的と範囲

[ADR-SRS-037](../ADR-SRS-037-unmatched-summit-needs-review.md) が定める
「担当者が地形変化を確認したうえで手動で削除申請に回す」を、作業用ビューアから行えるようにする。
担当者が指定した削除対象・根拠を申請書とエビデンスに一致して残し、エクスポート後の手書きだけに依存しない。
成果物は申請ドラフトであり、SOTA 登録の削除実行・公式提出は行わない。

対象はバッチ出力が次の全条件を満たす既存 summit Point に限る。

- `feature_type=summit`、`match_status=unmatched`、`category=review`
- `review_reason=unmatched`、`review_group_id` は空文字
- 当該入力に存在する、正式な既存 `summit_code` を持つ登録

[ADR-SRS-048](../ADR-SRS-048-multiple-summits-in-one-az.md) の複数登録ピーク・AZ 内登録・
主ピーク依存の AZ 外保留削除候補は対象外とし、組全体の保留と編集抑止を維持する。
通常候補を申請から外す機能、新規ピークの永続的な識別、廃止済み山の再提案抑止も今回の対象外。

2026-09-21、メンテナは「削除根拠が未記入なら警告し、出力を許す」方針を選択した。
その他は以下の提案であり、SRS への採用・コード実装は未承認。

## 2. 方式の比較

| 方式 | 評価 |
|---|---|
| 解析の match_status も delete に書き換える | 地形から検出した削除候補と担当者指定の削除を区別できなくなるため採らない |
| review のまま申請書にだけ削除行を追加する | ビューア・一覧・ZIP と申請書の分類が食い違い、消費側ごとに追加の判定が必要になるため採らない |
| 解析値を保持し、担当者判断から現在の category を更新する | 推奨。未編集のバッチ出力を維持し、現在の表示・編集状態を各出力が共通に参照する |

推奨案は [FR-019](../../20_SRS.md#fr-019-html-ビューア機能仕様) を担当者判断の管理主体とする。
バッチの入力データを保持したまま、操作または適格な保存値の復元から現在の状態を生成する。
各エクスポートはその同一時点の状態を読み、独自に category を導出しない。
これは [ADR-SRS-044](../ADR-SRS-044-category-property-summit-centric-5class.md) の
「category が共通の分類値」という方針を維持し、「バッチ算出後は不変」という範囲だけを拡張する提案である。

## 3. 判断とデータ契約

### 3.1 追加属性

中心 GeoJSON・ZIP 内 GeoJSON の全フィーチャに、次の2属性を追加する。
バッチ生成時は両方とも空文字。両サミット一覧 XLSX にも同名カラムを追加する。

| 属性 | 値・意味 |
|---|---|
| `review_decision` | 空文字（今回の手動削除指定なし）、`delete`（担当者が今回の申請に含めると指定） |
| `review_note` | 担当者が入力した削除根拠の本文。指定なしの成果物では空文字 |

`review_note` は生成済みの根拠テンプレート全体ではなく、担当者入力部分を独立して保持する。
これによりテンプレートの存在を「根拠記入済み」と誤判定せず、入力内容を表示・再編集・出力で共有できる。
`rationale` はこの入力を使う申請書用の生成値とし、二つを別々の編集欄で変更させない。

### 3.2 状態表

対象 summit Point の状態は次のとおり。元の `match_status`・`review_reason` は解析由来の情報として保持する。
`review_reason` が空でないことだけで、現在も申請保留中と判定してはならない。

| 属性 | 初期・取消後 | 担当者の削除指定中 |
|---|---|---|
| `category` | `review` | `delete` |
| `match_status` | `unmatched` | `unmatched` |
| `review_reason` | `unmatched` | `unmatched` |
| `review_group_id` | 空文字 | 空文字 |
| `review_decision` | 空文字 | `delete` |
| `review_note` | 空文字 | 担当者入力（空文字も許容） |
| `rationale` | 空文字 | §4 の専用フォーマット |

指定中も既存コード・名称・日本語名・座標・登録標高・登録 points・市区町村・地域名を変更しない。
ピーク・コル・ポリゴン・接続線は追加せず、主ピークコード・距離も付与しない。
この登録は主ピークに従属すると判定されたものではない。

元のバッチ出力はファイル・読み込み元データとも書き換えない。
`merged_summit.xlsx` は常に未編集の review / unmatched 行のまま残り、
申請内容反映版の `merged_summit_revised.xlsx` と ZIP の GeoJSON に担当者判断が反映される。

### 3.3 判定の順序と適格性

1. 当該バッチ入力から §1 の適格性を判定する。保存値の category / match_status で適格性を作らない。
2. 適格な対象の明示操作、または §5 の復元条件を満たした判断だけを適用する。
3. 判断から上表の現在状態と rationale を生成する。
4. ビューアと各エクスポートはこの状態を使用する。申請対象は従来どおり category で選ぶ。

通常の add / band_change / no_change / delete、複数登録の保留組、対象外フィーチャには
この判断を適用しない。古い保存値が存在しても、対象外登録の属性・category・根拠を上書きしない。
既存の [FR-009](../../20_SRS.md#fr-009-sotaリスト突合match_status-判定) 不備ゲートは変更しない。
担当者の判断はバッチへ逆流せず、unmatched 件数を減らしてゲートを迂回する用途にも使わない。

## 4. 操作と根拠文

### 4.1 ビューア操作

対象の popup またはサイドパネルに、現在状態に応じて次を提供する。配置・具体的な UI 部品は HLD で決める。

- 初期状態: 「削除申請に含める」操作。初期状態で自動選択しない。
- 指定中: 「担当者判断による削除申請」と表示し、削除根拠の入力欄と「要確認に戻す」操作を提供する。
  システムは地形変化を確認したと断定せず、未記入なら「根拠未記入」を併記する。
- 切替は当該登録だけに作用する。一括採用や複数登録の保留解除は追加しない。
- 指定中は削除カテゴリの表示対象、取消後は要確認カテゴリの表示対象になる。
  移動先カテゴリが非表示なら自動的に ON にして、選択中の登録が操作直後に見失われないようにする。
- コード・名称検索は同じ既存登録に到達する。手動指定だからといって主ピークやコルへの移動を表示しない。

通常の自動削除候補には従来の rationale 編集欄を維持する。
今回の手動指定対象では、その欄を `review_note` の入力欄に置き換え、生成 rationale は確認表示のみとする。
名称や登録値を変更する機能は加えない。

### 4.2 専用の根拠文

担当者指定中の summit Point の rationale は、通常の「主ピークに従属」という削除根拠を使わず、次で生成する。

```text
担当者判断による削除申請
対象：{summit_code}
確認内容：{review_note または「未記入（担当者補記）」}
```

前後の空白を除いた入力が空（空白・改行だけを含む場合も同じ）なら未記入とする。
判定・保存・出力には前後の空白を除いた本文を用い、内部の改行は保持する。
内容を推測して「噴火で消失」等の事実を自動記入しない。
通常の URL や参照資料名を根拠本文に記入できるが、資料の自動検証・取得は行わない。

申請書とエビデンス ZIP のエクスポート時、指定中かつ根拠未記入の件数・コード一覧を警告し、
出力を許す。該当登録を黙って除外せず、テンプレートの「未記入」を含めて申請書・GeoJSON に残す。
両出力で根拠本文と rationale は同じ現在状態に基づく。
根拠入力済みの明示判断をそのまま復元した場合に、毎回の個別承認操作を追加で要求することはない（同一解析内）。

## 5. 保存と再解析

### 5.1 同じ解析結果の再訪

既存の [FR-019](../../20_SRS.md#fr-019-html-ビューア機能仕様) の localStorage 編集内容を拡張し、
解析日時 `metadata.generated_at` と既存 SummitCode に対応付けて指定と根拠本文を保持する。
具体的なキー表現・JSON の配置は HLD の責務とする。

同じ解析結果の再訪では、現入力の適格性を再確認してから指定・根拠を復元する。
古い山岳名・通常 rationale の保存値だけでは手動削除を有効にしない。明示された `review_decision=delete` が必要。
複数登録の保留組へ変わっている等、適格性を満たさない対象には適用せず、未適用のコードを利用者に知らせる。
未知の判断値・不正な型のレコードは適用せず、その対象を知らせる。その他の適格な入力・判断は利用できる。

「要確認に戻す」は有効な指定を解除し、現在の出力を §3.2 の初期状態に戻す。
入力済み根拠は同じ解析の localStorage 内に下書きとして保持し、再指定時の入力欄に戻す。
取消中は下書きを申請・一覧・ZIP・公開データへ出力しない。
ブラウザ保存に失敗した場合は保存されていないことを表示する。メモリ上の現在状態からの出力は利用でき、
保存できたように表示しない。容量上限等の具体的な対処は既存規則どおり HLD に委ねる。

### 5.2 解析日時が変わった場合

既存の「前回の入力内容を引き継ぐか」という選択を維持する。
ただし今回追加する削除判断は、別の解析結果へ無条件に自動採用しない。

| 操作・条件 | 今回の状態 |
|---|---|
| 引き継がない | 判断なし。前回の保存内容は削除せず保持 |
| 引き継ぐ、同じコードが今回も適格 | 前回根拠を下書きに引き継ぎ、前回は削除指定だったことを表示。今回の category は review のままで、対象ごとに「削除申請に含める」を再操作すると採用 |
| 引き継ぐ、同じコードが対象外または存在しない | 削除判断・根拠を今回の登録に適用せず、未適用コードを表示。前回保存値は保持 |

根拠の下書きを引き継いだだけでは `review_decision`・成果物の `review_note`・rationale は空文字のままとする。
同じコードでも現役対象から消えた、正常 matched になった、複数登録の保留組になった、などを再判定する。
他のコードや近傍のピークへの自動付け替えはしない。
既存の山岳名・通常 rationale の引き継ぎ方針は維持し、複数登録の保留組の編集抑止を優先する。

この範囲は「同一解析の再訪復元、次解析への根拠下書き引き継ぎ」である。
次回以降の解析でも採否を自動適用する汎用的な永続判断ファイルや新規ピークの識別は別の仕様検討に残す。

## 6. 各成果物への反映

| 対象 | 手動削除指定中の扱い |
|---|---|
| バッチ GeoJSON / merged_summit.xlsx | review / unmatched の原本を維持。追加属性は空文字 |
| 申請書 XLSX | 削除1行。既存テンプレートの B は正式コード、C/D/E は自身の日本語名/名称/登録標高、F/G/H/J は空欄、I は専用 rationale。空の日本語名の従来許容も維持 |
| merged_summit_revised.xlsx | 既存 summit Point から1行。category=delete、match_status=unmatched、review_reason=unmatched、review_decision=delete、review_note=入力本文。重複する review 行は作らない |
| ZIP 内 GeoJSON | 当該 summit Point を delete.geojson のみに収める。review.geojson へ二重掲載しない。追加属性・解析由来の理由・専用 rationale を保持 |
| 公開用ビューア | 削除カテゴリに表示し、「担当者判断による削除申請」・根拠と元の unmatched 判定が分かる。操作・編集・localStorage は提供しない |

申請内容反映版の登録側各値（コード・名称・日本語名・municipality・region_name・sota_*）は自身の既存登録から取得する。
ピーク・コル・プロミネンス・points・stability・key_col_resolved・col_margin_px・analysis_count・expected_count・
area_complete・is_band_change_candidate・dominant_peak_code・dominant_peak_dist_m は空欄。
通常の自動削除行の主ピーク code / dist とは区別する。
`review_group_id` も空文字。rationale 列は従来どおり両一覧に設けず、追加する review_note 列で担当者入力を確認できる。
未指定・取消後は自身の review / unmatched 行だけを残し、追加属性は空文字とする。

両一覧の行構成・行数・既存行順は保ち、手動指定による複製や別位置への追加は行わない。
GeoJSON のカテゴリ分割は現在の category に従い、各ファイル内の元の相対順を維持する。
ZIP の5カテゴリ・空 FeatureCollection と metadata の出力規則を維持する。
同一バッチ入力と同一の確定した表示・編集状態からは同じ内容を生成する（既存の日時等の除外は維持）。

## 7. 受入例

以下は仕様採用後に [ST](../../70_ST.md) へ対応付ける期待結果であり、現在の実装で検証済みの結果ではない。

| 条件・操作 | 期待結果 |
|---|---|
| 孤立 unmatched を未操作 | review のまま、申請行なし。自動採用なし |
| 適格な1登録を指定、根拠入力 | category=delete / match_status=unmatched。申請削除1行・専用根拠。改訂一覧1行・delete.geojson のみ |
| 根拠未入力、または空白/改行のみで指定 | 未記入のコードと件数を警告し、申請・ZIP を出力。専用根拠に「未記入」、review_note は空文字 |
| 指定と根拠の編集後に出力 | 申請書 I と GeoJSON rationale が同一。改訂一覧/GeoJSON review_note は同じ入力本文 |
| 指定後に要確認へ戻す | category=review、現在の判断・本文・rationale は空。申請行なし、review.geojson のみ。下書きは保存し再指定時に復元 |
| 同じ解析を再訪 | 適格性を再確認し指定・根拠を復元。通常 rationale だけの旧保存値からは採用しない |
| 解析日時変更・引き継ぐ・同じ適格コード | 根拠下書きだけを復元し、再指定までは review・申請行なし |
| 解析日時変更・引き継がない | 今回は初期状態、前回保存値は残る |
| 引き継ぐがコード消失 / matched化 / 複数登録保留化 | 判断を適用せず未適用コードを表示。現在の登録値・保留組・通常カテゴリを上書きしない |
| 複数登録の AZ 内 / AZ 外保留に旧削除指定がある | UI に採用操作なし、古い値も適用せず、組全体 review のまま |
| 通常の自動削除・手動削除・未指定 review・保留組が混在 | 各申請行・一覧・ZIP が現在状態に一致。手動削除に主ピーク・距離・線を捏造せず、通常の自動削除の属性は維持 |
| 削除フィルター OFF で手動指定、要確認 OFF で取消 | 移動先フィルターが ON、対象登録と popup を追える。各コード・名称検索も同じ登録へ到達 |
| 生成した ZIP を公開用ビューアへ配置 | category=delete / match_status=unmatched の単独 Point を表示し、手動判断と根拠を確認可能。主ピーク欠如をエラー扱いせず編集機能なし |
| 同じ入力と同じ判断を異なる操作順で確定 | 行数・並び・分割・根拠が同じ。判断取消履歴や非出力の下書きが成果物へ漏れない |
| 不正な保存値、または保存失敗 | 不正レコードは適用せず通知。保存失敗は未保存と表示し、メモリ上の正しい状態からの出力は可能 |
| バッチの unmatched 件数超過・不完結・コル未確定 | 既存ゲートが停止。前回の手動判断でバッチ件数・不備を隠さない |

## 8. 採用時の文書反映先と残る範囲

- SRS の [FR-009](../../20_SRS.md#fr-009-sotaリスト突合match_status-判定): 追加属性のバッチ初期値、
  category の「バッチ算出」と「担当者反映後」の区別、review_reason の解析由来の意味を明記する。
  バッチ行集約と突合値域・不備ゲートは維持する。
- [FR-019](../../20_SRS.md#fr-019-html-ビューア機能仕様): 適格性、指定/取消、根拠入力、category 更新主体、
  保存/再解析引き継ぎ、警告を定義。review 編集禁止に孤立の明示操作による例外を設け、複数登録の禁止を維持。
- [FR-011](../../20_SRS.md#fr-011-申請書-xlsx-生成): 担当者指定の削除根拠の取得元を追加。
  全 delete が主ピークを持つ前提を撤回し、出力の category 選択と既存列を維持。
- [FR-012](../../20_SRS.md#fr-012-サミット一覧申請内容反映版生成): 入力は山岳名だけでなく担当者判断も参照。
  「delete→delete」の match_status 転記を原 Point の値の保持へ改訂し、手動削除行の空欄と追加カラムを定義。
  追加カラムはバッチ一覧にも揃え、レビュー本文を出せるよう概要の「座標・標高・突合結果のみ」も改訂。
- [FR-021](../../20_SRS.md#fr-021-申請エビデンス-zip-生成) と [FR-020](../../20_SRS.md#fr-020-公開用ビューア配信):
  手動削除 Point の分類・属性・表示、主ピーク/接続線が無い delete の扱いを追加する。
- 外部 I/F 詳細（§6）、ビューア入力（§7.2.2）、localStorage と表示・編集状態（§8）に判断/根拠と参照先を同期する。
  用語集・ST と [NFR-003](../../20_SRS.md#nfr-003-再現性決定論的出力) の前提も同期する。
- 新 ADR で決定・比較・制約を記録し、既存 ADR-SRS-037/044/045/048 に現行例外の追補を加える。
  [ADR-SRS-048](../ADR-SRS-048-multiple-summits-in-one-az.md) の複数登録保留自体を解除するものではない。

採否の汎用永続化・廃止済みの再提案抑止・通常候補の個別除外は別の仕様検討で扱う。
