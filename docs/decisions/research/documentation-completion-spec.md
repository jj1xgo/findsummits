## 1. 目的と現状

[UR-008](../../10_URD.md#ur-008) の「ドキュメントに従って環境構築から成果物生成まで実行できること」を、
SRS の検証可能な要件へ落とす。利用者は既存の想定利用者である解析・申請支援の担当者とし、
OS の一般操作を教える教材の新設や全 OS への対応は要求しない。

現行の [NFR-006](../../20_SRS.md#nfr-006-可搬性環境) は動作環境、
[NFR-007](../../20_SRS.md#nfr-007-ログ出力) はログを規定する。
いずれも実行の前提・支援であり、手順書の存在・対象範囲・完遂条件は規定していない。
一方、[ST の既存シナリオ](../../70_ST.md#st-ur-008-01-環境構築成果物生成の一気通貫) は
暗黙知なしでの完遂を要求しており、SRS 側の対応が欠けている。

本案はその欠落を埋める仕様案である。採用前のため SRS/ST 本体をまだ変更しない。
実際のコマンド・手順書の執筆と実地検証は設計・実装以降に行う。

## 2. 方式の比較

| 案 | 評価 |
|---|---|
| A: 専用 NFR を追加し、SRS と ST を対応付ける | 推奨。手順書による完遂を環境・ログとは別に検証できる。実際の手順は README とリンク先へ集約できる |
| B: OPS の成果物要件へ移し、RTM には前提の対応だと注記する | 手順の置き場は整理できるが、ST に既にある完遂要求の SRS 上の合格条件が残らない |
| C: 既存の環境 NFR に手順書の規定を追加する | 要件数は増えないが、環境で動作することと文書だけで操作できることを分けて追跡しにくい |

A を採り、SRS には必要な性質と合格条件を記す。OPS ステージではそれを満たす運用手順を整備する。
後工程の `80_OPS.md` が未作成でも、手順を実行する ST の時点では対象版に対応する利用者向け手順一式を揃える。
手順の所在を将来移す場合も README から辿れるようにし、未作成ファイルへのリンクで充足したことにしない。

## 3. 追加する要件案

### 3.1 要件の識別と文書の入口

`NFR-011: 手順文書による環境構築・成果物生成の完遂性` を追加する。
対応 UR は [UR-008](../../10_URD.md#ur-008) とする。番号は採用時に再確認する。

利用者が [README](../../../README.md) を入口として、対象版と対応する手順文書を辿り、
環境構築から申請用成果物の生成まで実行できること。手順の分冊と既存文書への参照は許すが、
非公開のエージェント設定・会話履歴・担当者の口頭補足・ソースコードの読解を操作手順の代わりに要求しない。
文書化された利用者入力（保存先、対象範囲、連絡先、候補の判断等）を行うことは手順の逸脱に含めない。

### 3.2 手順に含める範囲

| 段階 | 手順に必要な内容 |
|---|---|
| 環境構築 | 対象 OS・資源・ブラウザ条件への参照、依存導入、対象版の取得、ビルド、設定と作業ディレクトリの準備。ネットワークが必要な段階と権限の前提 |
| 入力準備 | 標高タイル、SOTA リスト、行政区域データ、申請テンプレート等、各処理に必要な入力の取得元・配置・前処理・確認方法。必須と任意を区別する |
| バッチ実行 | タイル取得、行政区域前処理、解析・広域解析、統合、突合、作業用ビューア生成の順序、各段の前提・入力・出力・完了の確認方法 |
| ブラウザ操作 | 作業用ビューアの開き方、確認・編集、申請書 XLSX と申請エビデンス ZIP の保存、除外判断 JSON の保存・読込。ネットワーク条件は現行 URD/SRS に従う |
| 成果物確認 | 出力先と成果物の用途、内容を確認する方法、警告・要確認・申請保留と生成失敗の区別。生成物が申請ドラフトであることと公式提出が手動であること |
| 異常時の対処 | 失敗段階と原因をログ等から確認する方法、入力・設定の是正、再実行の開始段階、再利用できる入力/キャッシュと再生成が必要な出力の区別 |

各段には操作と観測可能な完了条件を記載する。異常時は既存 FR が定める停止・継続・再試行の範囲で
対処手順を示し、処理途中の任意箇所からの再開や自動復旧を新設しない。
申請不備ゲートが成立しない入力を「成功させる」ための無条件な閾値変更・フラグ改変を手順にしない。
個別判断が必要な問題は、確認対象と判断後に再実行する範囲を示す。

### 3.3 クリーン環境と完遂条件

クリーン環境とは、[NFR-006](../../20_SRS.md#nfr-006-可搬性環境) と
[環境定義](../../01_environment.md) の OS・資源条件を満たし、一般的な OS 操作と
文書に記載する依存導入・データ取得に必要な権限・通信が使える環境で、
本ツール専用の依存環境・ビルド済みバイナリ・個別設定・参照データ・タイルキャッシュ・
中間/最終出力・ブラウザ保存状態を事前に用意していない状態とする。
対象版のソースと同版の手順文書から始め、これらを記載手順で準備する。
既存作業ディレクトリや実データを削除せず、別の作業領域・ブラウザプロファイル等で初期状態を隔離する。

完遂の合格条件は、記載手順とそのリンク先だけで必要な入力準備・処理・ブラウザ操作ができ、
次の成果物を当該実行で生成し、開いて SRS の各 I/F に適合する内容を確認できることとする。

- バッチ出力: 突合済み統合 GeoJSON、サミット一覧（突合後）XLSX、作業用 HTML ビューアとデータファイル。
- ブラウザ出力: 申請書 XLSX、申請エビデンス ZIP とその規定の全構成物、別ファイルの除外判断 JSON。
- 選択機能の出力: 標高地形図 PNG を生成する操作を実行し、その出力も確認する。

ZIP 内のサミット一覧（申請内容反映版）XLSX・5分類 GeoJSON 等の構成は
[SRS §6.2.8](../../20_SRS.md#628-申請エビデンス-zipパッケージング仕様) を正とし、独自に複製定義しない。
除外判断 JSON は ZIP に入れず、明示保存と読み戻しを確認する。
中間成果物は各段の完了と異常時の再実行を判断するために確認する。
ファイルの存在だけで合格にせず、過去の出力を当該実行の成果物として数えない。

公開用ビューアの配信手順・稼働確認は [FR-020](../../20_SRS.md#fr-020-公開用ビューア配信) の
検証で扱い、本要件の「成果物生成まで」の終点にはホスティングへの公開や公式申請の提出を含めない。
そのため生成完了を公開完了と報告しない。

[FR-009](../../20_SRS.md#fr-009-sotaリスト突合match_status-判定) の全国一括突合と不備ゲートを維持する。
正常系 E2E は必要な全国入力を記載手順で準備し、全国の必要範囲を解析する。小規模解析の成功や
事前生成済みの統合出力を渡すだけの確認を、クリーン環境からの完遂に代えない。
テストデータの対象版・取得日・識別情報、設定値、文書の版、実行環境、ログ、成果物の確認結果を記録する。
具体的なデータ版・コマンド・出力値は ST の実行手順で固定し、本要件で実装方式を先取りしない。

文書にない補足が必要なら手順書の不備として扱う。仕様上許容する警告・要確認が残ること自体は
生成失敗ではないが、停止条件を解除できないまま、または必要成果物が欠けたままなら完遂の合格にしない。
外部サービス停止等で実行できなかった場合は未完了と原因を記録し、文書不備・機能不備と区別する。

## 4. 受入確認

現行 ST の第1部「NFR 検証」に以下を追加し、第2部の既存 `ST-UR-008-01` を具体化する。
実行を共有してよいが、文書の存在確認だけで E2E 合格にはしない。

| 予定 ID | 観点・前提 | 手順 | 期待結果・合否判定 |
|---|---|---|---|
| `ST-NFR-011-01` | 対象版の README と参照先 | §3.2 の全段階と入口からの到達性を確認 | 必要な手順・前提・完了/異常判定が揃い、未作成文書や非公開情報への依存がない |
| `ST-NFR-011-02` | §3.3 のクリーン環境・全国入力を取得可能 | `ST-UR-008-01` と同じ実行で、入力準備から全成果物確認まで手順に従う | 暗黙の補足ゼロ、必要入力を手順で準備、全成果物を今回生成し内容確認。版・設定・ログ・警告等を記録 |
| `ST-NFR-011-03` | 手順で準備した正常入力を持つ隔離作業領域 | 単独起動するフェーズの必須中間入力を退避して不足させ、停止を確認後、文書に従い前段から再生成して再実行 | 原因と再実行位置を文書だけで特定でき、入力復元後に所定成果物を生成。不備ゲートを迂回せず、古い出力を成功の証拠にしない |
| `ST-NFR-011-04` | 仕様上許容する警告/要確認で続行するデータ、および不備ゲートで停止するデータ | それぞれのログと出力を文書の完了条件で判断 | 続行時のドラフトと停止時の調査用出力を区別でき、停止した実行を成果物生成の完遂と誤認しない |

`ST-UR-008-01` の前提は §3.3 のクリーン状態、手順は §3.2 の正常系全段階、
合否は §3.3 の成果物内容確認と文書外補足の有無に置き換える。
全国の検出網羅性や数値精度自体は既存の対応 UR/FR とその ST で検証し、本案では基準を変更しない。
異常系2件の具体的な入力は ST の実行時に対象 FR の既定条件を再現する形で固定する。

## 5. 採用時の反映先

| 文書 | 反映内容 |
|---|---|
| SRS §5・目次・§12 RTM | `NFR-011` の追加。既存環境/ログ NFR の対応は維持し、UR への直接の完遂要求と前提/支援の役割を説明 |
| ST 第1部・第2部・§5 | 上記4件、既存 UR シナリオの具体化、UR カバレッジ表への新 NFR/ケースの追跡 |
| SRS ステージの新 ADR | A 採用/B・C 不採用、ST 時点に必要な手順と後続 OPS 文書の責務を記録。採用・未実装として管理 |
| 本調査資料 | 採用日・正本への参照・レビュー結果を記録 |

URD の要求文は維持する。テスト方針書の ST 定義は環境構築から成果物生成までを既に含むため変更不要。
README や環境定義の操作手順の実装追従は HLD/LLD 確定後の作業とし、今回の記録を参照して管理する。
`80_OPS.md` の先行作成やプロトタイプコードの改修は含めない。

## 6. レビュー記録

仕様案の起草後、独立した Opus の読み取り専用レビューを実施する。
対象は UR/SRS/ST の整合、受入条件の判定可能性、後続設計への委任と作業範囲。
実地の全国解析・ブラウザ操作による完遂確認は未実施であり、文書レビューの合格とは区別する。
