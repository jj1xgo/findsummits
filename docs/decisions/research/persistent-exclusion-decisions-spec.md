## 1. 目的と範囲

担当者が add・delete・band_change の候補を申請から外し、次回以降も同じ対象・同じ条件なら
その判断を再利用できるようにする。除外した理由と解析結果をエビデンスに残す。
ブラウザデータ消去や別 PC への移行に備え、判断ファイルを保存・読み込みできる方式はメンテナ選択済み。
以下の具体的な状態・照合・出力契約は採用前の提案である。

[ADR-SRS-049](../ADR-SRS-049-unmatched-manual-delete.md) の担当者指定削除に続く、申請から外す方向の機能とする。
対象は申請ドラフトへの採否であり、SOTA 登録の更新、公式提出、解析対象からの除去はしない。
バッチのピーク検出・突合・件数・不備ゲートには判断を適用せず、元の GeoJSON/XLSX は保持する。
[ADR-SRS-048](../ADR-SRS-048-multiple-summits-in-one-az.md) の保留組を解除する機能は追加しない。

判断ファイルは担当者が明示的に保存・交換する。共同編集・複数ファイルの自動マージ・サーバ保存・
担当者アカウント・操作履歴の監査・座標変更後の自動追跡は対象外とする。

## 2. 方式の比較

| 案 | 評価 |
|---|---|
| localStorage のみ | 小さい変更だが別ブラウザへ持ち運べず、メンテナの要望を満たさない |
| 作業用ビューアで判断ファイルを入出力し、localStorage でも編集中の台帳を保持 | 推奨。既存のブラウザ内編集・エクスポートの責務を保ち、利用者がファイルを保管できる |
| バッチが永続判断ファイルを読み、候補そのものを消す | 解析結果と申請判断が混ざり、除外根拠の検証や不備の検出を難しくするため採らない |

申請分類は5カテゴリを維持し、除外を別の属性で明示する。除外後も元の提案種別を読み取れる。
category を review に移す案は、解析由来の要確認と担当者が決めた除外を混同する。
第6カテゴリを作る案は元のカテゴリを別途保持し、ZIP と公開用のファイル契約を変更する必要がある。

この提案は [ADR-SRS-044](../ADR-SRS-044-category-property-summit-centric-5class.md) の
「category だけで申請対象を選ぶ」契約を拡張する。category は提案されている申請アクション、
除外属性は今回それを出力するかの判断であり、ビューアが両方を確定した現在状態を各出力が読む。

## 3. 判断の対象と識別

### 3.1 対象単位

[FR-012](../../20_SRS.md#fr-012-サミット一覧申請内容反映版生成) の「1行=1サミット」を操作単位とする。
入力はバッチデータに [ADR-SRS-049](../ADR-SRS-049-unmatched-manual-delete.md) の有効な判断を反映した、
除外処理を適用する直前の状態（以下「候補状態」）。保存ファイルで候補状態を作らない。

| 候補 | 操作対象 | 台帳上の識別キー |
|---|---|---|
| add（new / dominant） | 行を生む peak Point | 新設種別 + peak_lat + peak_lon + アクション add |
| band_change | 行を生む matched peak Point | 既存種別 + 正式 SummitCode + アクション band_change |
| 通常 delete | 行を生む summit Point | 既存種別 + 正式 SummitCode + アクション delete |

- no_change・未選択/取消後の review・複数登録の保留組は操作対象外。旧判断から対象化しない。
- 担当者指定 delete も除外操作の対象外とし、申請から外す場合は既存の「要確認に戻す」を使う。
  自ら採用した削除を別の判断で除外する二重状態を作らず、通常 delete の除外記録も適用しない。
- peak/col/登録 Point を別々に操作して同じ行へ競合する判断を付けない。関連フィーチャへの反映は §4 に従う。
- 仮サミットコード・山岳名・配列番号・generated_at は永続識別キーにしない。
- 座標は中心データの WGS84 数値を使い、数値としての完全一致で照合する。丸め、距離許容、最寄りへの付け替えはしない。
  `35.0` と `35` のような数値表記差だけは区別しない。保存精度は元の数値を往復して保持できること。
- 同じキーが現行の複数候補を指す場合は一意に選ばず未適用とし、対象を通知する。

### 3.2 判断時の条件

キーが一致しても、次の判断時条件が全て一致するときだけ再利用する。
条件値は元のバッチデータから取る。
ファイル内の category や解析値を現行データへ上書きして一致させてはならない。

| アクション | 保存・比較する判断時条件 |
|---|---|
| add | match_status（new/dominant）、ピーク座標・標高・prominence・points、選ばれた主ピークがこのピークである通常 delete の正式コード集合 |
| band_change | match_status=matched、当該登録の座標・標高、対応ピーク座標・標高・prominence・points |
| 通常 delete | match_status=delete、当該登録の座標・標高、選ばれた親の識別子（matched は正式コード、dominant はピーク座標）・座標・標高・prominence |

値の集合は順序によらず比較する。数値と null を区別し、文字列・真偽値で代用しない。
名称、編集した rationale、generated_at、入力リストの基準日、ソフトウェア版の変更だけでは失効しない。
ただし従属 delete のコード集合が変われば、追加と削除の置換関係が変化したため親 add の除外も未適用にする。
基準日の変更だけの場合とは区別し、担当者が新しい関係を確認して再除外する。
ただし、上表の判断時条件が同じなら地形や運用状況も不変だと保証するものではなく、担当者は除外一覧を確認できる。

条件変化・アクション変化・対象外化・一意性喪失・対象不在は、今回の申請に判断を適用しない。
台帳レコードは保持し、未適用の識別子・理由を表示する。現行の候補がある場合は
現在の申請対象か要確認等の対象外かを併記する。申請対象なら「前回の除外は未適用。今回は申請対象」と明示する。
現在条件を確認して再度除外すると、そのキーの条件を更新する。
座標が変わった新設ピークは別キーとして新規に判断する。旧レコードは自動削除せず、担当者が不要なら削除する。

同じ条件で再び現れた対象には保持した判断を適用できる。解析範囲の縮小で一時的に不在となっても台帳から落とさない。

## 4. 状態と関連候補

### 4.1 現在状態の属性

全中心 GeoJSON フィーチャと両一覧 XLSX に次の属性/列を追加する。バッチ生成時は全件空文字。

| 属性 | 値と意味 |
|---|---|
| application_exclusion | 空文字: 今回の除外なし。manual: 有効な担当者の除外判断。parent_add: 親の追加候補が除外されているため従属する削除を保留 |
| exclusion_note | manual: 担当者の除外理由本文。parent_add: 下記固定文。空文字の状態では本文も空文字 |

category・match_status・review_reason・review_group_id・登録値・解析値・geometry は除外では変えない。
review_decision / review_note は担当者指定削除の属性として維持し、除外判断と意味を混ぜない。
通常 rationale や削除根拠へ除外理由を書き込まない。除外により登録が削除済み・承認済みとなったようには表示しない。

[FR-019](../../20_SRS.md#fr-019-html-ビューア機能仕様) が、候補状態へ適格な台帳を適用し、関連候補の扱いも含め
現在状態を生成する。申請書は category が add/delete/band_change で、かつ application_exclusion が空文字の行だけを出力する。
各出力や公開用ビューアは台帳を読み直したり、親子関係から除外を再計算したりしない。

### 4.2 追加と削除の関係

- 追加候補を manual 除外した場合、そのピークが選ばれた主ピークである通常 delete 行も申請から外す。
  追加しない新設ピークを前提とした削除だけを申請へ残さないためである。
- 子に有効な独自の manual 除外があれば manual を優先し、その理由を保持する。
  それ以外の子は parent_add とし、理由を「追加候補 {現在の親の仮コード} を除外したため削除申請を保留」とする。
- 親の除外を解除すると parent_add は消える。子自身の manual 判断は残る。
  parent_add を直接「申請へ戻す」操作は設けず、親の追加候補へ移動する手段を示す。
- 子の削除だけを除外しても親の追加を自動除外しない。存続予定の登録と追加候補が併存することを
  関係するコード付きで警告し、担当者が判断できるドラフトとして出力を許す。
- 親が matched の場合は既存登録が存続するため、親の band_change 除外によって子の delete を保留しない。
- 曖昧な保留組は最初から候補状態が review のため対象外。別親への再選択やゾーンの重なりによる連鎖は行わない。
- parent_add は現在状態から派生する表示・出力属性であり、永続台帳には保存しない。

### 4.3 関連フィーチャへの反映

[ADR-SRS-045](../ADR-SRS-045-summit-xlsx-row-aggregation-model.md) の行へ集約するフィーチャを単位に、
application_exclusion と exclusion_note を同じ値に揃える。

- add: peak・key_col・AZ・delete_zone・peak_col_link。
- band_change: 上記に加え、AZ 内 matched summit とその coord_diff。
- 通常 delete: 当該 summit とその coord_diff。
- 親子の申請行は別々の除外属性を持つ。子の coord_diff は子の値を持ち、親の値を無条件に継承しない。
- コルなし等、元々存在しないフィーチャを生成しない。no_change・review・担当者指定 delete の属性は空文字。

## 5. 保存と判断ファイル

### 5.1 台帳とブラウザ保存

台帳は manual の除外判断だけを持ち、適用中・未適用の両レコードを保持する。
各レコードは識別キー、判断時条件、理由本文、判断時の generated_at を持つ。最後の日時は出自情報であり照合条件ではない。
理由は前後の空白を除き内部改行を保持する。空白だけは未記入とし、除外自体は許す。

- 同じ世代への再訪: 台帳を localStorage から復元し、現行入力で適格性・条件を再検証する。
- 新しい世代: 既存の generated_at 変更時の引き継ぎ確認で、除外台帳も対象と明示する。
  「引き継ぐ」は台帳を今回へ複製し、一致する判断を個別再選択なしで適用する。適用・未適用件数を表示する。
  「引き継がない」は今回の空台帳から開始し、前世代の保存値は保持する。
- 対象不在や条件変化でも台帳から消さない。未適用一覧で識別子・理由・判断時条件を確認し、レコードを削除できる。
- 「除外を解除」は該当キーのレコードを台帳から削除して現在状態を再計算する。理由下書きは同一世代の
  ブラウザ編集状態にだけ残せるが、判断ファイル・エビデンスには入れない。再除外には明示操作が必要。
- 保存失敗は未保存と表示し、メモリ上の正しい台帳から判断ファイルや申請成果物をダウンロードできる。
  壊れた台帳キャッシュは採用せず、空台帳であることとファイルから復旧できることを示す。正常保存を偽装しない。

[ADR-SRS-049](../ADR-SRS-049-unmatched-manual-delete.md) の新世代への手動削除の継承は、引き続き根拠下書きだけである。
除外台帳の読み込みが review_decision=delete を復元したり、担当者指定削除を除外したりすることはない。
台帳は手動削除の採用履歴・通常名称・rationale の交換ファイルにはしない。

本案の除外は申請対象を減らす判断であり、削除申請を増やす担当者指定削除とは継承条件を分ける。
同じ対象・判断時条件の一致を必須とし、世代継承またはファイル置換への同意後に限って再適用する。
必要な申請まで省くリスクは残るため、適用・未適用の件数と一覧を示す。
ADR-SRS-049 の個別再採用は維持し、除外側の再適用を認める理由を新 ADR の比較検討にも記録する。

### 5.2 ファイルの入出力

作業用ビューアに「除外判断を保存」「除外判断を読み込む」を設ける。
保存は現在の台帳全体を JSON ファイルとしてダウンロードする。対象不在などの未適用レコードも含む。
ファイルを利用者が保管し、別 PC の作業用ビューアで選択して読み込む。
ブラウザが任意パスへ自動上書きすることや、バッチが `$DATA_DIR/ref/` から自動取得することは要求しない。

| 論理項目 | 契約 |
|---|---|
| schema_version | 1。互換性確認用。非対応版は拒否 |
| records | レコード配列。空配列は有効な空台帳 |
| 各レコードの対象 | §3 の種別・識別値・アクション。一意キー。仮コードをキーに含めない |
| 判断時条件 | §3.2 の値を欠落なく保持。該当しない親等は明示的な null |
| 理由本文 | 文字列。未記入は空文字 |
| 判断時の解析日時 | 元の metadata.generated_at の文字列。出自として保持 |

具体的な JSON のネスト・フィールド名・ファイル名・保存キーは HLD で規定する。
文字列は表示用データとして扱い、HTML やコードとして実行しない。資料名・URL を理由に書けるが自動取得しない。
数値は有限値、座標は WGS84 の値域、種別とアクションは §3 の組合せ、必要な文字列・null・配列の型を検証する。
不正 JSON・非対応版・必須項目欠落・型不正・同一キーの重複（内容が同一でも）はファイル全体を拒否する。
1キー1判断を契約とし、重複は生成元や手編集の異常として通知する。同一内容だけを黙って間引く処理は設けない。
検証失敗・読込失敗・取消では現在の台帳も表示も変更しない。構造が有効だが今回の対象がないレコードは有効な未適用記録とする。

読み込みは台帳全体の置換とし、自動マージや日時による勝者選択はしない。
変更・追加・削除される判断と、今回の適用・未適用件数をプレビューして、置換の確認後に一括反映する。
編集中の台帳がある場合は先にファイル保存できるようにする。通常の名称・rationale・手動削除判断は置換しない。
同じファイルの再読込は結果を増殖させない。古いファイルを読み込めば解除済み判断も復活しうるため、
置換の差分確認で分かるようにする。複数人の判断を統合する用途には拡張しない。

ブラウザ内保存とファイル書き出し済みを区別し、最後の読込/書き出し後に台帳を変えた場合は
「判断ファイルに未反映」と表示する。ダウンロード要求を出したことは実ディスクへの保存完了保証と扱わない。
申請 XLSX/エビデンス ZIP の出力やブラウザを閉じる操作を、判断ファイルの保存完了だけを理由に禁止しない。

## 6. 操作と成果物

### 6.1 作業用ビューア

- 対象の popup/パネルに「申請から除外」と任意の除外理由入力を設ける。
- manual は「申請から除外（担当者判断）」・理由・「除外を解除」、parent_add は関連追加候補と保留理由を表示する。
- 5カテゴリの色・分類は候補種別として維持し、除外対象を申請対象と誤認しない明瞭な表示を添える。
  除外を含む/含まない表示切替を追加する（初期は含む）。除外した直後も対象と popup を保持する。
  検索からの移動時はカテゴリと除外表示の必要なフィルターを ON にする。
- 台帳の適用中/未適用一覧、件数、未適用理由を確認できる。未適用記録を現行フィーチャとして地図へ作らない。
- 両申請出力ボタンで、除外件数（manual / parent_add を別集計）、未適用判断、理由未記入の manual の
  件数・識別子を知らせて出力を許す。新設候補は現在の仮コードと座標、未適用の新設記録は保存座標で示す。
- 未適用記録があるだけで現行候補を隠さない。関連する登録を誤って通常申請へ戻したように見せないため、
  今回は除外されていない旨を明示する。既存の不備・保留組・名称未入力等の警告は維持する。

### 6.2 各成果物

| 成果物 | 反映内容 |
|---|---|
| バッチ中心 GeoJSON / merged_summit.xlsx | 解析・突合結果のまま。新属性/列は全件空文字。台帳を消費しない |
| 申請書 XLSX | 候補の category が add/delete/band_change かつ application_exclusion が空文字の行のみ。除外行は出力せず、残る行の A〜J は従来どおり |
| merged_summit_revised.xlsx | 除外対象を含め全行を保持し、2新列に状態と理由を記録。行数・行位置・元の category と登録/解析属性は除外で変えない |
| ZIP 内5 GeoJSON | 既存の category で分割し、除外対象と関連フィーチャもそのファイルに保持。属性が除外を明示する。重複・消失・追加の架空フィーチャなし |
| 公開用ビューア | 除外の表示・理由・除外を含む表示切替・検索は作業用と同様。台帳の読込/保存・解除/編集・localStorage は提供しない |
| 除外判断 JSON | §5 の独立した保存ファイル。エビデンス ZIP へ自動同梱しない。過去の不在対象を公開データへ混ぜない |

除外理由未記入は exclusion_note を空文字とし、ビューアで「除外理由未記入」と表示する。
parent_add の固定文は §4.2 に従う。rationale / review_note は既存の申請根拠としてそのまま保持する。
公開エビデンスにも今回適用した除外理由が含まれることを、理由入力・出力時に利用者へ示す。

担当者指定削除の review_note 未記入警告は、既存どおり申請書と ZIP の両方で維持する。
新設ピークの名称未記入警告も申請書へ出力される行だけを数える。

同じバッチ入力・通常編集・手動削除判断・除外台帳から同じ現在状態と出力を得る。
JSON は対象種別→アクション→正式コード（文字列順）/座標（緯度→経度の数値昇順）の順で records を並べる。
生成時刻の追加で内容を変えず、同じ台帳なら同じ論理内容を保存する。XLSX/GeoJSON の既存の日時等の除外は維持する。
操作順でエビデンスの行・フィーチャを末尾へ付け替えず、申請書は基準行順から除外行だけを落とす。

## 7. 廃止済み登録の扱い

[入力 CSV の有効レコード規則](../../20_SRS.md#724-sota-サミットリスト-csv) は維持する。
廃止済みコードが存在するだけで、近くの新設候補を「既知の不採用」として自動除外しない。
現行の使用カラムからは廃止理由を判断できず、登録座標と今回のピーク座標が同じ対象を示すとも限らないためである。

担当者が再提案を望まない新設候補を一度除外すれば、同じ座標・判断時条件での次回提案は
台帳の継承または読込により申請から外れる。DEM 変更等で位置や判断時条件が変わったものは再確認する。
廃止済み登録の近傍照合・履歴表示・自動ルール生成は今回追加しない。
この方式は「一度判断した候補の再提案抑止」を解決し、未確認の廃止済みサミット全件を自動除外するものではない。

## 8. 受入例

以下は採用後に [ST](../../70_ST.md) へ反映する期待結果であり、実装検証済みの記録ではない。

| 条件・操作 | 期待結果 |
|---|---|
| add / 通常 delete / band_change を個別除外し解除 | 申請行だけが消え/戻り、エビデンスの行数・位置・分類・登録/解析値は不変。2新属性が一致 |
| 除外理由が空白だけ | manual 除外は有効、本文は空文字。両出力でコード/件数を警告して続行 |
| 親 dominant の追加を除外、子は未操作 | 親 manual・選択された親に従属する子だけ parent_add。別親・重なるゾーンの候補へ波及しない |
| 子 manual + 親 manual から親だけ解除 | 子の独自判断・理由は残り、他の parent_add 子だけ戻る |
| 子 delete だけを除外、親 add は残す | 対応コードを警告し、親の追加行を残して出力 |
| matched 親の band_change を除外 | 親の既存登録は残り、従属 delete は独立して申請対象のまま |
| 同一解析を再訪、または別 PC で同じ対象の判断ファイルを読む | 適格性を再検証して同じ除外と理由を復元。適用中・不在の台帳を往復保存 |
| 新世代へ継承/非継承 | 継承時は一致する判断を再選択なしで適用、非継承時は空台帳。前世代保存値は保持 |
| 仮コードが変更、ピーク座標と判断時条件は同じ | 除外を継承し、表示・parent_add 理由は今回のコードを使用 |
| 同じ仮コードが別座標へ割当、近傍へピークが移動 | 誤転用しない。旧記録は未適用として保持し、現行候補は除外されていないと通知 |
| 既存コード同一だがアクション・座標・標高・主ピーク等の条件が変化 | 除外を適用せず差異を通知。再除外時に今回条件へ更新 |
| 今回の対象が不在・廃止済み・no_change・保留組になった | 今回は未適用。元データや保留組を上書きせず、台帳は保持 |
| 担当者指定削除を申請から外す、または新世代へ移行 | 除外操作は提供せず「要確認に戻す」を使う。台帳は手動削除を復活・除外させず、新世代では個別再採用が必要 |
| 同じキーが現行の複数候補を指す | 全候補への自動適用も勝者選択もせず未適用通知 |
| 不正 JSON・非対応版・型不正・重複キーを読み込む、または読込取消 | 現在の台帳・表示・通常編集を一切変更しない |
| 有効な別台帳/空台帳を読み込む | 差分プレビューと確認後に置換。マージしない。再読込で増殖しない |
| ブラウザ保存失敗、ファイル書出後の編集 | 未保存/ファイル未反映を区別。メモリの有効状態からの出力は可能 |
| 公開用で除外対象を検索、フィルターを切り替える | 除外理由と元のカテゴリを閲覧できるが、判断操作や台帳使用はない |
| 除外理由を入力し、申請書または ZIP を出力する | 理由入力欄と両出力ボタンで、今回適用した理由が公開エビデンスに含まれることを告知 |
| 保存前に除外解除、または過去の対象が解析範囲外 | 解除した記録は JSON から消え、範囲外だけの記録は残る。理由下書きは成果物へ漏れない |
| 操作順・台帳レコード順を変えて同じ最終状態にする | 申請行順・エビデンス全体・JSON の論理内容が同じ |
| 旧保存値（除外属性/台帳なし）・判断ファイルなし | 既存仕様と同じ申請。勝手な除外なし |
| 廃止済みの山が new として検出される | 履歴だけでは除外せず、一度明示除外した後の一致候補は申請から外れる |
| 台帳に大量の除外があり、バッチの不備ゲート条件を満たす | バッチの出力・停止・ビューア生成スキップが台帳なしと同じ |
