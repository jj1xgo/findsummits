# ADR-URD-020: 要求から仕様・設計・プログラム・テストまでの整合を、宣言と lint と CI で保証する

| 項目 | 内容 |
|---|---|
| 状態 | 採用・実装済み |
| 決定日 | 2026-10-04 |

---

## Context

元の UR-009「仕様書・設計書の内容とプログラムの実装が整合していること」は、2026-05-24 にユーザー要件ではなく開発プロセスの品質目標と判断して URD から外した（[URD の注記](../10_URD.md#4-ユーザーニーズ)）。その後の規則は「設計確定後の実装・仕様変更では関連文書とコードを同期し、許容する乖離は ADR に記録する」の一文で、同期を求めるだけで更新漏れを見つける仕組みが無かった。追跡マトリクスは SRS §12 と ST §5 にあったが手で保守し、SRS では各 FR/NFR の「対応 UR」と §12 が同じ事実を二重に持っていた。push・PR で走る CI も無く、文書のリンク検査は `#` 以降のアンカーを見ていなかった。

## Decision

1. 目的を開発の規則として定める: 要求（URD）が仕様（SRS）・設計（HLD・LLD）に落とされ、仕様・設計とプログラム・テストが一致していること。どこかを変更して他の更新が漏れたら CI が止まること。意図して許すずれは ADR に記録されたものだけとすること。正本は[開発ガイド「6. 要求の追跡と整合」](../03_development.md#6-要求の追跡と整合)。
2. 対応関係の正は、下位が上位を指す宣言とする（書式は[文書管理ルール「追跡の宣言」](../CLAUDE.md#追跡の宣言)）。SRS の「対応 UR」、HLD の「対応 SRS」「担当コンポーネント」、LLD の「ID」「対応 HLD」「ファイル」、コードとテストのコードの `trace:` コメント。
3. 追跡マトリクスは読みやすさのために残し、`tools/lint_trace.py` が宣言から組み立て直して照合する。照合するのは今は SRS §12 と ST §5 で、HLD・LLD 末尾の表はそれぞれを作るときに検査に足す。
4. `tools/lint_trace.py` は T1（宣言の欠落・書式・欠番）、T2（参照先の実在）、T3（被覆）、T4（追跡マトリクス）、T5（コード・テストのコードとの双方向）を検査する。T3 と T5 は、下位の段がフェーズゲートを通った後に効かせる。
5. 欠番と構造上の例外は、根拠の ADR と一緒に `RETIRED_IDS`・`EXEMPTIONS` に書く。UR-009 の欠番の根拠は本 ADR とする。
6. push・PR で `make lint` と lint の検査のテストを走らせる CI を置く。製品のテストは、テストができた段で同じ CI に足す。
7. 機械で判定できないこと（文書の言い回しとコードの意図が合っているか）は、変更時のレビューで確かめる。

## Alternatives

- UR-009 を URD に戻す: 要求の一番上に置けるが、保証する手段は同じ lint・テスト・CI で、確定済みの URD・SRS の改訂だけが増える。却下。
- 各文書末尾の追跡マトリクスを正にする: 各節の宣言（SRS の「対応 UR」など）との二重管理が残る。却下。
- 機械で読める台帳（YAML など）を正にし、表を生成する: 正は 1 か所になるが、本文と離れた場所に対応を書くことになり、台帳の更新を忘れやすい。却下。
- コードに ID を書かず、LLD の表のファイル欄だけを正にする: 簡単だが、コードを読む人が仕様へ辿れない。却下。
- すべてを機械で止める（仕様から生成する、実行できる仕様にする）: 文書の書き方が大きく変わる。却下。

## Consequences

- 宣言・追跡マトリクス・リンクのアンカーの食い違いは、今後 `make lint` と CI で止まる。
- HLD の各節に宣言の 2 行が加わる。HLD 末尾の追跡マトリクスと [§2.2.4](../30_HLD.md#224-srs-の-frnfr-との対応) の置き換えは HLD の作業で行う。
- 開発用の道具（`tools/lint_trace.py` ほか）とそのテスト（`tests/tools/`）は、HLD [§2.6.4](../30_HLD.md#264-ディレクトリ構成) の構成どおり製品のコードと分けて置き、T5 の対象にしない（2026-10-04 に `scripts/`・`tests/scripts/` から移した）。
- LLD・UT・IT の検査とコードの照合は、文書とゲートの進みに合わせて効き始める。
- フェーズゲートの判定のたびに `CONFIRMED_STAGES` を書き換える作業が増える。

## 追記（2026-10-10）: HLD の末尾の表と 2.2.4 の扱い

Consequences の「HLD 末尾の追跡マトリクスと §2.2.4 の置き換え」は、2.2.4 を置き換えず、プログラムの割り当ての表として残して第 3 章の宣言と照合する形にした。HLD の末尾の表は [6. 要求追跡マトリクス](../30_HLD.md#6-要求追跡マトリクス) に置き、T4 で照合する（[ADR-HLD-005](ADR-HLD-005-hld-traceability-matrix-and-program-table.md)）。Decision 3 の「SRS §12」は、SRS の章の付け替えの後は [SRS §10](../20_SRS.md#10-要求追跡マトリクス) である。
