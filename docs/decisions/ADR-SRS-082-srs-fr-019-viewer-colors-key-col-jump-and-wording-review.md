# ADR-SRS-082: SRS の FR-019 の見直しで、マーカーとカテゴリの色、Keyコルへの移動の条件、編集欄の対象を書き分ける

| 項目 | 内容 |
|---|---|
| 状態 | 採用・実装済み |
| 決定日 | 2026-10-13 |

---

## Context

2026-10-13 に、改訂した多視点のレビュー（spec-panel）で、ソフトウェア要件仕様書（SRS）の §4.6（[FR-013](../20_SRS.md#fr-013-html-ビューア生成)）と §4.7 の [FR-019](../20_SRS.md#fr-019-html-ビューア機能仕様) を見直した（[#204](https://github.com/jj1xgo/findsummits/issues/204)）。照らした相手は §6〜8 の台帳と URD である。[FR-013](../20_SRS.md#fr-013-html-ビューア生成) に食い違いは無く、[FR-019](../20_SRS.md#fr-019-html-ビューア機能仕様) に次の食い違いが見つかった。

1. 「各マーカーの色は `points` に基づく標高バンド色」と「カテゴリは配色でも区別する」が並び、カテゴリの配色を何に付けるのかを書いていなかった。点の色がどちらで決まるのかが読み分けられない。概要設計書（HLD）は [DEC146](../30_HLD.md#4194-設計判断) で、カテゴリの色はフィルターの見出しにだけ使い、地図の上の点の色には使わないと解釈していた。
2. 既存 SOTA サミットの点は `points` を持たず、`sota_points` を持つ（[FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) の「Point: 既存 SOTA サミット」）。どちらも 150m 未満は null になる。マーカーの色を `points` だけで書いていた。
3. 「Keyコルへ移動」ボタンを `key_col_resolved=true` のときに出すとしていた。陸地最高峰・島嶼部最高峰は Key コルが海面で確定し（`key_col_resolved=true`）、コルの点を作らない（[FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) の「Point: コル」）ので、移り先の無いボタンが出る。同じ FR は、この場合の Keyコル標高を「海面（0m）」と表示すると定めている。
4. rationale の編集欄を「`category` ∈ {add, delete, band_change} の通常フィーチャ」に置くとしていた。これらのカテゴリにはコル・線・matched のサミットも含まれるが、rationale が申請書の列 I に転記されるのは、申請書の行のもとになる点（add と band_change のピーク、通常の削除のサミット。[FR-011](../20_SRS.md#fr-011-申請書-xlsx-生成)）だけである。申請から除外している間も、これらの点の編集はできる（[FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) の `rationale`）。HLD も [DEC134](../30_HLD.md#4194-設計判断) で、編集値を行を生む点にだけ当てている。
5. 出力の表が、申請書 XLSX と申請エビデンス ZIP を「各エクスポート」の 1 行にまとめていた。[§6.1](../20_SRS.md#61-外部if一覧) は、入出力の表のデータ名に外部 I/F 一覧の名前（「申請書 XLSX」「申請エビデンス ZIP（パッケージング仕様）」）を使うと定めている。
6. 不完全なゾーンがビューアに届かないことを、アクティベーションゾーン（AZ）についてだけ書いていた。2026-10-12 に delete判定ゾーンにも `area_complete` を足し、[FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) の不備ゲートが両方を検査する（[ADR-SRS-080](ADR-SRS-080-srs-section-4-5-second-review-read-errors-and-delete-zone-completeness.md)）。
7. HLD に委ねるパラメータを、地図のライブラリの設定の名前（`maxBounds`・`zoomSnap`）で書いていた。SRS には実装の手段の名前を書かない（`docs/CLAUDE.md`「SRS 機能要件（FR）記述規約」）。
8. 地理院基準点タイルの取得 URL を本文に書いていた。背景タイルの URL は SRS に書かず、出典の一覧（`ref/SOURCES.md`）に置いている。同じ URL は出典の一覧にもあり、本文はそこへリンクしている。

## Decision

1. マーカーの色は標高バンド色とし、カテゴリの配色はカテゴリの切り替えの表示に使い、マーカーの色には使わないと書く。どこにどう表示するかは HLD に残す。申請からの除外の項の「5カテゴリの分類と配色は維持し」も、マーカーの色と形を保つことが分かる字句にそろえる。
2. マーカーの色の参照先を、ピークと Keyコルは `points`、サミットは `sota_points` と書き分け、null のときの色は HLD に委ねる。
3. 「Keyコルへ移動」ボタンは、対応する Keyコルの点がある場合だけ出す（Key コルが海面で確定したピークには出さない）。
4. rationale の編集欄は、申請書の行のもとになる点（add と band_change のピーク、通常の削除のサミット。申請から除外している間も含む）に置く。担当者指定削除は、これまでどおり専用の入力欄を使う。
5. 出力の表を「申請書 XLSX」と「申請エビデンス ZIP（パッケージング仕様）」の 2 行に分ける（名前は [§6.1](../20_SRS.md#61-外部if一覧) の台帳と同じ）。
6. ビューアに届かないことを、AZ と delete判定ゾーンの両方について書く。
7. HLD に委ねるパラメータを、手段の名前を使わずに書く。
8. 基準点タイルの URL を本文から消し、出典の一覧へのリンクに任せる。

1・3・4 のほかは、要求の中身と範囲を変えない。1 と 4 は HLD が決めていた扱いを SRS に書いたもので、3 は移り先の無いボタンを出さないようにしたものである。

## Alternatives

- **(a) 1 を SRS に書かず、HLD の [DEC146](../30_HLD.md#4194-設計判断) で SRS の字句を狭めたと示すだけにする**: SRS を直す箇所は減るが、SRS の字句の読み分けの曖昧さが残る。カテゴリの配色をマーカーに付けるかどうかは利用者に見える振る舞いなので、SRS に置く。
- **(b) 3 で、海面で確定したピークにもボタンを出し、押すと「海面（0m）」と知らせる**: 移る先が無い操作を置くことになり、同じ popup の「海面（0m）」の表示と重なる。

## Consequences

- SRS の [FR-019](../20_SRS.md#fr-019-html-ビューア機能仕様) を直した。HLD がすでに決めていた振る舞い（1・4）のほかは、3 で移り先の無いボタンを出さなくなる。
- HLD の [DEC146](../30_HLD.md#4194-設計判断) は、1 で SRS の字句を変えるもとになったので、HLD の重要の基準（[ADR-HLD-006](ADR-HLD-006-hld-decision-selection-criteria-and-open-item-cleanup.md)）の「上位文書」に当たるようになる。4 のもとになった [DEC134](../30_HLD.md#4194-設計判断) と、1 で直した除外中の字句のもとになった [DEC144](../30_HLD.md#4194-設計判断) も、同じ基準で印を見直す。[HLD 4.19.2](../30_HLD.md#4192-処理の流れ) の popup のピークの行（`key_col_resolved=true` なら「Keyコルへ移動」）は 3 に合わせる。HLD 4.19.2 が SRS の字句を逐語で引く 2 か所（「要確認の見え方」の「カテゴリは配色でも区別する」と、「除外中の見え方」の「5カテゴリの分類と配色は維持し、除外中であることを明瞭に添える」）は、1 で直した字句に合わせる。印を付けることと字句をそろえることは、HLD の追従の見直しで扱う。
- システムテスト仕様書（ST）に、Key コルが海面で確定したピークの popup のケースを足すか、ST の見直しで扱う。
