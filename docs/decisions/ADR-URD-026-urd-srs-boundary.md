# ADR-URD-026: URD には要求と制約を書き、方式は SRS 以下に委ねる

| 項目 | 内容 |
|---|---|
| 状態 | 採用・実装済み |
| 決定日 | 2026-10-11 |

---

## Context

文書の書き分けの規約は、SRS と HLD の間（[文書管理ルール](../CLAUDE.md)「SRS 機能要件（FR）記述規約」の「実装方式はHLDへ」）、HLD と LLD の間（[「HLD と LLD の書き分け」](../CLAUDE.md#hld-と-lld-の書き分け)）、用語集と SOURCES の間にはあった。URD と SRS の間には無かった。

[ADR-OPS-002](ADR-OPS-002-reference-standards-and-intended-deviations.md) は、URD を利害関係者要求仕様（StRS）として扱うとした。規格の本文は持っていないので、StRS に何を書くかを ISO/IEC/IEEE 29148:2018 の本文では確かめていない。

規約が無いので、多視点のレビュー（spec-panel）は、URD に方式が書かれていても、置き場が別の文書だと示せなかった。URD を下の Decision で 1 件ずつ当てると、SRS の決定を写した記述は次の 4 件だった。

1. [§5](../10_URD.md#5-前提制約) の DEM5a / DEM5b / DEM5c / DEM10b の優先順（[ADR-SRS-002](ADR-SRS-002-dem-hierarchy-fallback.md)）
2. 同じ行の、HTML ビューアの等高線に DEM1a も使うこと（[ADR-SRS-067](ADR-SRS-067-contour-uses-dem1a-at-high-zoom.md)）
3. [§6](../10_URD.md#6-スコープ外対象外) の、解析に DEM1a を使わない理由（ADR-SRS-002）
4. §6 の「サーバー側リアルタイム処理」の、どの成果物をバッチで作り、どれをビューアの操作で作るかという処理の分け方と場所の説明

どれも SRS の [3.5](../20_SRS.md#35-制約前提条件) と [3.6](../20_SRS.md#36-スコープ外) に同じ記述がある。方式に触れているが残した記述と、残した理由（下の Decision の項）は次のとおり。

- 入力元（Decision 3）: [§1](../10_URD.md#1-目的背景) の「標高タイル（DEM5/DEM10b）を使って」、§5 の「解析の標高データは国土地理院タイルのみ使用」、§6 の「既存サミットの山岳名JP は SOTA 山名 GeoJSON から自動取得する」
- 利用者に見える使い方（Decision 3）: [§3.3](../10_URD.md#33-運用の流れ) の 3 の「バッチで実行する」、§5 のインターネット接続の行の「バッチ処理による解析・成果物生成はオフラインで可」
- 外部が定めたもの（Decision 2）: 申請書テンプレート、[UR-001](../10_URD.md#ur-001) の 1 次メッシュ（第 1 次地域区画）、国土地理院コンテンツ利用規約
- URD の ADR に記録した持ち主の決定（Decision 2）: 北方領土と竹島の除外、[UR-013](../10_URD.md#ur-013) の中間成果物（[ADR-URD-016](ADR-URD-016-observability-intermediate-visualization-ur.md)）
- 範囲の決定: §6 の除外判断の項目（何をしないかで、方式の採否ではない）
- 要求が必要な理由の説明（Decision 4）: [UR-007](../10_URD.md#ur-007) の「特別な解析を要する」、§5 のインターネット接続の行の「背景地図タイル・ライブラリ（CDN）を実行時取得するため」
- 将来の要望（Decision 4）: [§7](../10_URD.md#7-将来スコープv20候補)

## Decision

1. URD は利用者の要求と制約を書き、それを実現する方式は SRS 以下に委ねる。規約は[文書管理ルール「URD と SRS の書き分け」](../CLAUDE.md#urd-と-srs-の書き分け)に置く。
2. URD に書いてよい制約は、外部が定めたもの（SOTA 日本支部、国土地理院、データの提供元など）と、持ち主が利用者として決めたもの（URD の ADR に記録）に限る。
3. 入力元（データの提供元と種類）と、利用者に見える使い方（解析をバッチで実行するなど）は、利用者の要求として URD に書いてよい。入力元の中のどのデータをどの順で使うか、どの成果物をどこで作るかは方式とする。
4. 要求が必要な理由の説明で、方式の選択や採否を定めないものは、方式に触れていても URD に書いてよい。将来の要望も同じ。
5. 範囲外とすることのうち、方式の採否に当たるもの（使わないデータ、処理の場所など）は、URD には項目名だけを置き、理由と範囲は SRS を指す。
6. URD の記述が、SRS 以下で決めた方式や方式の採否の理由を写していたら、URD からは消して、SRS への参照を残す。要求・制約・範囲は、SRS に同じ記述があることだけを理由に消さない。Context の 4 件をこの形に直す。確定済みの URD の補足として、URD に注記を置く。

## Alternatives

- **(B) URD に方式を一切書かない**: 1 次メッシュ、独立峰の「特別な解析」なども SRS へ移すことになり、確定した UR を作り直す。外部が定めた定義や、要求の理由の説明まで消すと、URD が利用者の言葉で読めなくなる。採らないことは持ち主の判断（2026-10-11）。
- **(C) 利用者が関心を持つことなら書いてよい**: 今の URD はほぼ残るが、レビューで「置き場が別の文書」と示せる場面がほとんど無くなる。採らないことは持ち主の判断（2026-10-11）。
- **方式の記述を消すだけで、SRS への参照を残さない**: URD は短くなるが、URD から行き先をたどれなくなる。採らないことは持ち主の判断（2026-10-11）。
- **規約を URD の冒頭に置く**: 書き分けの規約は、ほかの層の分も文書管理ルールに置いている。URD だけを URD に置くと、規約の置き場が分かれる（計画者の判断。持ち主が設計を承認）。

## Consequences

- [文書管理ルール](../CLAUDE.md#urd-と-srs-の書き分け)に「URD と SRS の書き分け」の節を足した。
- URD の [§5](../10_URD.md#5-前提制約) と [§6](../10_URD.md#6-スコープ外対象外) の 4 件を、SRS への参照に改めた。ツールの振る舞いと SRS は変わらない。
- 多視点のレビュー（spec-panel、`.agents/skills/spec-panel/SKILL.md`）の層の適合チェックに、URD の例を戻し、この規約を根拠に挙げた。
- ISO/IEC/IEEE 29148:2018 の本文で確かめていない点（StRS に書く項目の範囲）は、[ADR-OPS-002](ADR-OPS-002-reference-standards-and-intended-deviations.md) の Decision 4 に従い保留する。
