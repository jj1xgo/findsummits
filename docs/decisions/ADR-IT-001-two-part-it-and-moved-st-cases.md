# ADR-IT-001: IT の仕様書を内部結合と外部結合の 2 部にし、ST から移すケースを振り分ける

| 項目 | 内容 |
|---|---|
| 状態 | 採用・実装済み |
| 決定日 | 2026-10-14 |

---

## Context

結合テスト（IT）の仕様書 `60_IT.md` を、概要設計書（HLD）の第 3 章の結合のつなぎ目（`CMP<N>-INT<n>`・`CMP<N>-EXT<n>`）から作る（[ADR-HLD-001](ADR-HLD-001-program-structure-chapter-and-two-tier-it.md)）。作るにあたり、次の 3 つが決まっていなかった。

- ケースの並べ方。[テスト方針書 §2](../02_test_policy.md#2-テストレベル定義と役割分担) は IT を内部結合と外部結合の 2 段で行い、内部結合を先に確かめるとし、[§5.6](../02_test_policy.md#56-開始基準) はシステムテスト（ST）の開始基準を内部結合と外部結合のそれぞれで数える。
- ST が「UT/IT で実施する」とした 47 件（ID の後の括弧に印のある 21 件と、[FR-002](../20_SRS.md#fr-002-dem-階層フォールバック)・[FR-003](../20_SRS.md#fr-003-標高デコードnodata-処理)・[FR-005](../20_SRS.md#fr-005-ピーク候補検出)・[FR-006](../20_SRS.md#fr-006-コル検出プロミネンス計算) の全 26 件）の扱い。[`70_ST.md`](../70_ST.md) の §2 は、これらを `50_UT.md`・`60_IT.md` の作成時に移すとしていた。
- ケースの粒度。[テスト方針書 §5.2](../02_test_policy.md#52-カバレッジ粒度の正本) の規則は FR/NFR 向けで、IT の決めごとが無かった。

## Decision

1. `60_IT.md` は、第 1 部に内部結合、第 2 部に外部結合を置く。それぞれの中は CMP1〜CMP8 の順に、つなぎ目ごとに小見出しを立てて並べる。
2. ST から移すケースは、次の規則で単体テスト（UT）と IT に振り分ける。前提か確かめることが、別のプログラムか別の起動が書いたものに依るケースは IT。1 本のプログラムの 1 回の起動の中で完結するケースは UT。
3. 移した先は `60_IT.md` の §5 の対応表に、ST のケース 1 件につき 1 行で書く。ST の行は、ID の直後の全角の括弧の中に、「。」で区切った項目の 1 つとして「UT/IT で実施」の印を持つ（`（境界値。UT/IT で実施）`）。対応表の 1 列目はコード表記の ST のケース ID 1 つ、2 列目はコード表記の UT・IT のケース ID を「・」で並べたもの。UT 行きは ``UT（`50_UT.md` で作る）`` と書き、`50_UT.md` を作るときに UT のケース ID に置き換える。`tools/lint_trace.py` が、印と対応表が 1 対 1 であること、書いた ID が実在することを照合する。
4. IT のケースの粒度は、テスト方針書 §5.2 の IT の段落に置く（HLD のつなぎ目の表の「確かめること」に書かれた挙動 1 つにつき 1 件以上）。
5. システムの外の相手は次のとおり扱う。国土地理院のタイルサーバーは、実サーバーから少数のタイルを取って確かめ、異常系は模擬サーバーで起こす（テスト方針書 §3.2）。CDN と背景タイルの提供元も、実サービスからの取得はブラウザで手動で確かめ、応答ごとの扱いは応答を差し替えた試験で確かめる（HLD の 3.7.5）。地図を動かすなどの対話操作を伴うケースは手動とする（テスト方針書 §3.1）。静的ホスティングの組み立て（Workers Builds）は、実際の push で起きた組み立てと配信を観察して手動で記録し、IT のために push はしない。

## Alternatives

- CMP ごとに 1 節を立て、その中を内部結合と外部結合に分ける: HLD と並べて読みやすいが、正式な実行の単位（内部結合と外部結合のそれぞれ）が 8 節に散る。却下。
- つなぎ目のケースだけを先に作り、ST からの移し替えを `50_UT.md` の回に回す: 範囲は小さいが、ST の「作成時に移す」と食い違ったまま残る。却下。
- ST の 47 件をすべて IT に移す: 関数の中の挙動が IT に入り、テスト方針書 §2 の分担（関数の中は UT、プログラムの境界をまたぐ受け渡しは IT）と食い違う。却下。
- つなぎ目 1 つにつき代表ケースを 1 件にする: 件数は少ないが、「確かめること」に書いた異常のときの挙動（止まる、警告して続ける）が、どのレベルでも確かめられなくなる。却下。

## Consequences

- `50_UT.md` を作るとき、対応表の UT 行きの行を UT のケース ID に置き換える。
- HLD のつなぎ目を変えるときは、IT のケースも同じ変更で直す（`tools/lint_trace.py` の T2 が止める）。
- ST に「UT/IT で実施」のケースを足すときは、対応表の行も同じ変更で足す（`tools/lint_trace.py` の T4 が止める）。

## 追記（2026-10-17）: 自動と手動の分け方

Decision 5 の「実サービスからの取得はブラウザで手動で確かめ」と「地図を動かすなどの対話操作を伴うケースは手動とする」は、[ADR-OPS-007](ADR-OPS-007-automated-or-manual-by-who-judges.md) で改めた。自動と手動は、テスト方針書 3.1 の分け方（合否をテストのコードが判定するなら自動、人の知覚や読解そのもので決まるなら手動。手順の一部を人が行うことは手動の理由にしない）で決める。IT のケースの印は [#300](https://github.com/jj1xgo/findsummits/issues/300)「IT の手動のケースを、自動と手動の新しい分け方で判定し直す」で判定し直す。静的ホスティングの組み立てを「観察して手動で記録し」とする扱いも、同じ Issue でこの分け方に照らす。
