# ADR-OPS-001: バージョン採番規則・タグ運用・1.0 到達条件

| 項目 | 内容 |
|---|---|
| 状態 | 採用・未実装 |
| 決定日 | 2026-09-19 |

## Context

findsummits には現時点でタグが 0 本、`release/*` ブランチも存在しない。`docs/00_GLOSSARY.md`「バージョン呼称」
には v1.0 / v2.0 の呼称があるが、採番規則・タグを打つ時点・1.0.0 の到達条件・互換性保証の対象範囲は
文書化されていない。

本体 `AGENTS.md`「リリース」節が定める `devel → release/* → main` の経路が既に存在し、いずれ最初のマージが
発生する。マージ時にどう版を決めるかを先に定めないと、成果物（申請書 XLSX・GeoJSON・HTML ビューア）に
どの解析条件で生成されたかを示す版識別が埋め込まれず、持ち主が生成物同士を区別できない。

## Decision

1. **v0.x.y の更新基準**: 正式リリース前は `v0.x.y` で採番する。x を上げるのは、
   [SRS §6 外部インターフェース仕様](../20_SRS.md#6-外部インターフェース仕様)（申請書 XLSX・CSV 列・
   GeoJSON プロパティ・ビューア）、[SRS §2.2.1 設定可能項目](../20_SRS.md#221-設定可能項目）、CLI 引数の
   いずれかを非追加的に変える場合、または新しい FR を実装する場合。y はそれ以外（修正・表示調整・内部
   アルゴリズム変更）。
2. **採番の時点**: `release/*` → main のマージ時に、main のマージコミットへ annotated tag `vX.Y.Z` を打つ。
   devel から生成した成果物は `git describe --tags` の出力（例 `v0.2.0-5-gabc1234`）で自然に区別されるため、
   `-dev` 表示の別規則は設けない。
3. **成果物への版識別の埋め込み**: 解析結果とビューアーは同一番号を使う（同一パイプラインが両方を生成する
   ため独立採番は二重管理になる）。metadata に `software_version` を 1 キー追加し、
   [FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) が付与、
   [FR-019](../20_SRS.md#fr-019-html-ビューア機能仕様) / [FR-020](../20_SRS.md#fr-020-公開用ビューア配信)
   が既存の基準日と並べて表示する。値は `git describe --tags --dirty` 相当（例 `v0.2.0`、
   `v0.2.0-5-gabc1234`）。タグが無い場合はコミットハッシュのみ（`--always` 相当、例 `8428ea0`）とする
   （現状タグ 0 本のため直ちに該当する）。正本は git のタグのみとし、手書きの `VERSION` ファイルは作らない。
4. **1.0.0 の到達条件と互換性保証対象**: 条件は「確定 SRS の FR/NFR を実装し、
   [`docs/70_ST.md`](../70_ST.md) を合格」。互換性保証の対象は
   [SRS §6 外部インターフェース仕様](../20_SRS.md#6-外部インターフェース仕様)・
   [SRS §2.2.1 設定可能項目](../20_SRS.md#221-設定可能項目)・CLI 引数。内部アルゴリズムと per-mesh
   中間物は対象外（[NFR-003 再現性](../20_SRS.md#nfr-003-再現性決定論的出力)は別途保証）。
   [URD §7 将来スコープ（v2.0 候補）](../10_URD.md#7-将来スコープv20-候補)はスコープ名であり、SemVer 上は
   1.x になりうる。
5. **URD/SRS の表記**: 現行維持。[SRS §1](../20_SRS.md#1-目的範囲)の「対象バージョン」は
   「対象システムバージョン」に改める（直前行「対象システム: findsummits」と対応させる）。
6. **記録先**: 本 ADR に決定を記録し、
   [本体 `AGENTS.md`「リリース」節](../../AGENTS.md#リリース)にタグを打つ 1 行、詳細は
   [開発ガイド](../03_development.md)、[用語集「バージョン呼称」](../00_GLOSSARY.md#バージョン呼称)に
   呼称の意味と本 ADR への参照、SRS（[FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) /
   [FR-019](../20_SRS.md#fr-019-html-ビューア機能仕様) /
   [FR-020](../20_SRS.md#fr-020-公開用ビューア配信) /
   [FR-021](../20_SRS.md#fr-021-申請エビデンス-zip-生成) / §1 / §5
   [NFR-003](../20_SRS.md#nfr-003-再現性決定論的出力) / §6.2.4 / §6.2.7）に版識別の付与・表示を反映する。

## Alternatives

- **(a) 0.x で y のみ上げ x は固定**: 採番が最も単純だが、破壊的変更（外部 I/F・設定項目・CLI 引数の変更）が
  番号に現れず、利用者が互換性の変化に気づけないため不採用。
- **(b) devel から生成した成果物に `-dev` 表示の別規則を設ける**: `git describe --tags` の出力
  （`vX.Y.Z-N-g<hash>`）で devel 由来の生成物は自然に区別できるため、追加の表示規則は不要。GitHub Pages
  で devel を常時公開する場合の表示は別途の要件変更（ビューアーの利用手順・Pages 運用の相談）で扱う。
- **(c) ビューアーを製品と独立に採番する**: ビューアーのテンプレートはソースに同梱され同じパイプラインが
  生成するため、独立採番は二重管理になるだけで区別の利益が無く不採用。
- **(d) 手書き `VERSION` ファイルを正本にする**: git の無いビルド環境でも版を取得できる利点があるが、
  現行運用は git チェックアウトを前提としており、タグとの二重管理が発生するため不採用。
- **(e) URD/SRS の「v1.0 / v2.0」を「初回リリース／将来スコープ」に言い換える**: 用語集の定義を書き換える
  コストが、現行表記のまま呼称に条件を追記するより大きく、現行表記で整合が取れているため不採用。
- **(f) SRS §1 を「対象製品バージョン」に改称する**: findsummits は SOTA 申請支援ツールであり製品ではない。
  「製品」の語は文書中のどこにも定義がなく新規に持ち込むことになるため却下し、直前行「対象システム」と
  対応する「対象システムバージョン」を採用した。

## Consequences

- [SRS](../20_SRS.md) の [FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) に
  `software_version` の付与、[FR-019](../20_SRS.md#fr-019-html-ビューア機能仕様) /
  [FR-020](../20_SRS.md#fr-020-公開用ビューア配信) /
  [FR-021](../20_SRS.md#fr-021-申請エビデンス-zip-生成) / §6.2.4 / §6.2.7 に同キーの表示・列挙、§1 の
  1 語修正、[NFR-003](../20_SRS.md#nfr-003-再現性決定論的出力) の除外対象への追加を行う
  （本体 commit で実施）。
- [用語集「バージョン呼称」](../00_GLOSSARY.md#バージョン呼称)に `v0.x.y` の行を追加し、既存の `v1.0` /
  `v2.0` 行に本 ADR への参照を追記する（本体 commit で実施）。
- 本体 `AGENTS.md`「リリース」節に、タグを打つ手順を 1 行追記する（本体 commit で実施）。
- [開発ガイド](../03_development.md)に採番規則の要約と本 ADR への参照を持つ新設節を追加する（本体 commit
  で実施）。
- `software_version` の取得・埋め込み機構（Makefile が `-D` で渡す、Python が `git describe` を呼ぶ等の
  実装詳細）は HLD の項目とし、実装は HLD/LLD 確定後の実装追従として `todo.md` で扱う。
- 初回の `release/*` → main マージでは devel の全履歴が main に入る。履歴書き換えはせず許容する。
- GitHub Pages の運用（本番と開発版の分け方、Actions による自動生成の要否）は本 ADR の対象外とし、別途
  ビューアーの利用手順の相談で扱う。
- URD の変更は無い。版識別は開発プロセス上の関心であり、利用者要件の追加ではないため、
  [URD §12 要求追跡マトリクス](../20_SRS.md#12-要求追跡マトリクス)の
  [FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) 対応は既存のまま変わらない。
