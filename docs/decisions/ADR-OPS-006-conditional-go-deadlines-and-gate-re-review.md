# ADR-OPS-006: 条件付きGo の条件に次のステージの作業の節目の期限と追う課題を求め、判定の後に規則や前提が変わったら再審査する

| 項目 | 内容 |
|---|---|
| 状態 | 採用・実装済み |
| 決定日 | 2026-10-15 |

---

## Context

[開発ガイド §4](../03_development.md#4-フェーズゲート) は、条件付きGo を「着手可能。明記した条件を次ゲートまでに消化する」と定めていた。期限の既定が取りうる最も遅い時点（次のゲート）で、条件を消化したかを確かめる時点が、条件を付けない Go と同じだった。条件ごとの期限・No-Go にしない理由・消化の追い方を記録に書く決まりも、審査資料や審査のレビューで「条件の期限は十分に早いか」を問う決まりも無かった。

ゲート 3（概要設計（HLD）→ 詳細設計（LLD）、2026-10-14）の判定は条件付きGo で、条件は (a) システムテスト仕様書（`docs/70_ST.md`）の残りのケースを足すこと、(b) テスト文書のステータスを分ける計画を立てることだった。どちらも期限は「次のゲート（LLD の段の終わり）まで」で、LLD の段の全体に当たった。審査資料・計画のレビュー・公開の前のレビューは、期限を既決のこととして受け取り、問い直さなかった。(b) は 2026-10-15 に [ADR-OPS-005](ADR-OPS-005-test-document-status-and-t5-timing.md) で済んだ。

ゲート 2（ソフトウェア要件仕様書（SRS）→ HLD、2026-07-12）の条件付きGo は、条件を「HLD の最初の 1 単位が確定した時点で早期チェックポイントを行う」とし、消化を追う Issue を立て、HLD の最初の単位の後に確かめた（2026-09-28 に消化）。この形は §4 の定義に書かれていなかった。

判定の後に規則や判定の前提が変わったときに、審査をやり直す手順も無かった。ADR-OPS-005 の Consequences は、`CONFIRMED_STAGES` から段を外す場面を想定しないとしていた。

持ち主が 2026-10-15 に次のとおり決めた。

## Decision

1. **条件の期限**: 条件付きGo の条件には、条件ごとに期限を決める。期限は次のステージの作業の節目とし、節目は「次のステージのどの作業の単位にも入る前」か「指定した単位が確定するまで」のどちらかにする（「最初の単位」とすると、どの単位から書き始めるかで期限に掛からなくなり、最初に書く単位が先に決まらないこともあるため）。日付は節目に加えて目安として書いてよいが、日付だけを期限にしない（日付だけでは、その日付が十分に早いかを確かめられず、過ぎたときに止める作業も決まらないため）。「次のゲートまで」は期限にしない。（2026-10-19 に [ADR-OPS-009](ADR-OPS-009-gate-condition-deadline-before-named-units.md) で、節目に「指定した単位に入る前」を足した。）
2. **記録に書くこと**: 条件ごとに、期限、No-Go にしない理由（条件が残ったまま次のステージに着手してよい理由と、期限の根拠）、消化を追う課題を記録に書く。期限の根拠には、その条件が要る作業と時点（どの作業の入力や前提になるか）と、選んだ期限の節目でその作業に間に合い、手戻りを防げる理由を書く。指定した単位の確定を節目にする形は、最後に書く単位を指定すれば「次のゲートまで」に近づくので、早さを後から確かめ直せる材料を記録に残す。課題を Issue に置くときは `type:進捗` にし、開発ガイド §7.1 の `type:進捗` の説明にゲートの記録と条件の追跡を足す。
3. **早さの審査**: 承認者（メンテナ）は条件ごとに、記録に書いた要る作業と時点に照らして、期限がその条件の要る時点より遅くないか、No-Go にしない理由が成り立つかを確かめる。持ち越しの中に条件にすべきものが無いかも確かめる。
4. **観点 2 の形**: 未解決課題の処置を「条件」と「持ち越し」に分け、別の表に書く。条件は、条件付きGo の条件の期限（Decision 1）までに消化を確かめるもので、観点 6 の条件と同じものを指す。期限の言い方は Decision 1 の箇所だけに書き、観点 2 と判定の表はそれを指す。持ち越しは後の段で扱うもので、扱う段と持ち越す理由を書く。当該ステージに帰属する課題（当該ステージの成果物の欠けや、それへの追従）を次のステージの途中で済ませるものは、持ち越しにせず条件にする。持ち越しの扱う段は、その課題が作業の範囲に入る段にする。振り分けの基準が無いと、当該ステージの課題を、扱う段に次のステージを書いた持ち越しとして送り、期限も追う課題も無いまま次のゲートまで残せるため（2026-10-14 のゲート 3 の記録では、帰属ステージが HLD の ST の改訂を持ち越しとし、次のゲートまでに終えるとしていた）。
5. **消化の確かめと期限の延長**: 消化したら、追う課題に何をどの版で済ませたかを書く。承認者が成果物を確かめて追う課題を閉じ、ゲートの記録にそのことを追記したときを、条件の消化とする。この追記はゲートの記録の補足に当たり、公開の前のレビューを通す。期限の節目の作業（単位に入る、単位を確定する）は、条件を消化してから行う。期限の節目までに消化できていなければ、その節目の作業を行わずに再審査する。期限の節目を替えるときも再審査による。期限を延ばす（節目を後ろの作業に替える）のは条件ごとに 1 回だけとし（再審査で引き継いだ条件の期限を元の節目より後ろに置くときも延長に数える）、延ばした期限も節目の形にし、延ばす理由と、延ばした節目で間に合う根拠を記録に書く。もう一度延ばす必要があるときは、延ばさずに No-Go（当該ステージへの差し戻し）として再審査する。
6. **再審査**: 次のときは、同じ 6 観点で審査をやり直す。(i) 判定の後、次のゲートの判定より前に、審査の規則や判定の前提が変わり、それがその判定の結論や条件に影響するとき。影響するかは承認者が判断し、影響しないと判断したときも、その旨と理由をゲートの記録に追記する（作業者の判断だけで再審査を省けないようにし、省いた判断を後から確かめられるようにするため）。(ii) 条件を期限の節目までに消化できていないとき、期限の節目を替えるとき（Decision 5）。(iii) No-Go の後に、差し戻した理由を解消したとき。発動の条件は §4 の再審査の段落の 1 か所にまとめる。再審査の記録は元の記録とは別に保存して互いに参照できるようにし、元の記録は書き換えない。元の記録に条件があれば、再審査の記録に、条件ごとに引き継ぐ（再審査の記録の条件にし、追う課題もそちらに付け替える）か、閉じるか（理由を書く）を書く。再審査は、フェーズゲートの審査として §4 の区分「境界」の扱い（計画のレビューと公開の前のレビュー）を受ける。
7. **No-Go の再審査と `CONFIRMED_STAGES`**: 再審査の判定が No-Go なら、その段と、その段を上位に持つ段（下位へたどった先まで。テスト文書の段を含む。たとえば HLD を外すなら LLD・UT・IT も）を `CONFIRMED_STAGES` から外し（`IMPLEMENTED_STAGES` にあれば、そこからも外す）、外した段の文書のヘッダーのステータスを「ドラフト」に戻す。No-Go は当該ステージへの差し戻しなので、確定のヘッダーを残さない。下位の段も外すのは、`tools/lint_trace.py` の T1 が上位の段を末端までたどり、上位の段の欠けと `IMPLEMENTED_STAGES` の段の欠けで止めるため。T1 は、段を外さないことやヘッダーを戻さないことでは止まらないので、No-Go の反映そのものは承認者が確かめる。
8. **道具に依る手順は個人の補足に置く**: 追う課題を Issue のどこに置くか（ゲートの記録の Issue の子にする、着手を止めたい Issue に依存を付ける）、マイルストーンの扱い、審査資料とレビューの依頼文に入れる観点は、メンテナ個人の補足資料に書く（[ADR-OPS-004](ADR-OPS-004-scope-of-public-defect-and-review-rules.md) の線引き）。

## Alternatives

- **期限は「次のゲートまで」のまま、追う Issue だけ足す**: 条件の一覧は追えるようになるが、消化を確かめる時点が次のゲートのままで、条件を付けない Go と差が出ない。ゲート 3 の条件の緩さが残る。不採用。
- **条件を禁じ、残る課題があれば No-Go にする**: 条件の中身が次のステージの入力でないとき（ゲート 3 の ST の残り）も、次のステージの全体を止める。次のステージに着手してよい理由がある課題は、期限の早い条件か、持ち越しで扱える。不採用。
- **期限を一律に「次のステージの最初の単位の確定まで」にする**: 条件によって要る早さが違う（次の作業に入る前に要るもの、ある単位の確定までに要るもの）。一律にすると、より早く要る条件の期限まで遅くなる。期限の取りうる形の 1 つとして書き、条件ごとに決める。不採用。
- **日付だけの期限を認める**: 次のゲートの日付は決まっていないので、日付が十分に早いかを確かめられない。次のゲートの直前の日付を書けば「次のゲートまで」と同じになり、過ぎたときに止める作業も決まらない。日付は節目に添える目安にとどめる。不採用。
- **期限の延長の回数を限らない**: 延長のたびに再審査を通せば、延長ごとの理由は確かめられる。しかし延長を重ねると、節目の形のまま次のステージの最後の単位まで延ばせ、「次のゲートまで」と同じ遅さに戻る。延長は 1 回にし、それでも足りないときは No-Go として差し戻す。不採用。
- **規則が変わった後も元の判定を保ち、変わった点だけを元の記録に追記する**: 6 観点を新しい規則で見直さないので、新しい規則で判定し直したことにならない。確定した記録を書き換えない決まり（§4）にも合わせ、新しい記録で再審査する。不採用。

## Consequences

- 開発ガイド §4 の観点 2・観点 6、判定の表の条件付きGo の行、記録の項目、区分の段落を改め、条件付きGo の条件の段落と再審査の段落を足し、`CONFIRMED_STAGES` の段落に No-Go の再審査の文を足し、§7.1 の `type:進捗` の説明を広げ、`status:` の説明を文書の執筆を追う Issue に限った（2026-10-15）。
- ゲート 3（2026-10-14）の記録は条件の期限が「次のゲートまで」なので、本 ADR の規則で再審査する。ゲート 2（2026-07-12）は、条件を 2026-09-28 に消化し、次のゲート（ゲート 3）の判定も済んでいるので、再審査の対象にしない。
- ADR-OPS-005 の Consequences の「`CONFIRMED_STAGES`・`IMPLEMENTED_STAGES` から段を外す場面を想定しない」のうち、ゲートの判定で `CONFIRMED_STAGES` に足す段が再審査で No-Go になったときは、その段と、それを上位に持つ段（下位へたどった先まで。テスト文書の段を含む。たとえば HLD を外すなら LLD・UT・IT も）を外す。ADR-OPS-005 に追記した。テスト文書自身の再評価による取り消しは本 ADR では決めないが、上位の段の取り消しに伴う連鎖は対象になる。
- 条件の期限が次のステージの作業の節目に掛かるので、条件を消化するまで、期限の節目の作業（単位に入る、単位を確定する）を行えない。条件が多いと次のステージの進みが遅れる。条件を付けるかは、No-Go にしない理由と期限を書けるかで決まる。
