# ADR-HLD-004: HLD の 2.6〜2.8 を 1 節にまとめ、FR 固有の中身を第 4 章に置き、手順と未決事項の項目を番号と題で指す

| 項目 | 内容 |
|---|---|
| 状態 | 採用・未実装 |
| 決定日 | 2026-10-09 |

---

## Context

[HLD](../30_HLD.md) の第 3 章（プログラム構造）が全コンポーネントでそろった時点（2026-10-09）で、HLD の構造に次の 3 つの問題が残っていた。

- 第 2 章の 2.6 技術スタック・2.7 外部依存ライブラリ・2.8 モジュール/ディレクトリ構成・ビルド構成は、中身は要るが、読み手（LLD・環境定義・Makefile の作者）が同じで、3 つの独立した節にするほどの量が無かった。2.7 の中身は C4 の依存だけだった。第 3〜5 章からのリンクは、2.6 が 2 回、2.7 が 7 回、2.8 が 9 回だった（2026-10-09 時点）。
- 横断の規約の節に、個別の FR の中身が混ざっていた。2.5.3 利用者向けのメッセージの表（約 50 行）の 40 行あまりは個別の FR の場面で、2.5.4 タイル取得の再試行は C2 だけの規則、2.4.4 フェーズ指定には C3 の起動前提条件の検査の手順が入っていた。第 4 章や LLD の作者は、1 つの FR の異常系を読むのに 2 か所を見に行く必要があった。
- 「処理の流れ」の手順と「未決事項と後続」の項目を、`[4.8.2](../30_HLD.md#482-処理の流れ) の 6` のように位置の番号だけで指していた（範囲を含めて 555 か所。2026-10-09 時点）。番号だけでは何を指すか分からず、手順を足して番号がずれても気づく手段が無かった。設計判断（D）には題を添えて lint で照合する規則が既にある（[文書管理ルール](../CLAUDE.md)「HLD の記号の書き方」）。

## Decision

1. 2.6・2.7・2.8 を [2.6 技術基盤](../30_HLD.md#26-技術基盤) にまとめ、2.7 と 2.8 は欠番にする。2.9〜2.11 の番号は変えない。小節は 2.6.1 目的と範囲、2.6.2 コンポーネント別の言語と処理系（旧 2.6.2）、2.6.3 ライブラリと使う範囲（旧 2.7.2）、2.6.4 ディレクトリ構成（旧 2.8.2）、2.6.5 ビルド構成（旧 2.8.3）、2.6.6 設計判断（旧 2.6.3・2.7.3・2.8.4。D9〜D26）、2.6.7 未決事項と後続とする。2.6.7 の項目は、まとめるときに 1 回だけ番号を振り直す（下の表）。統合で意味を失う項目（旧 2.6.4 の 1・2、旧 2.7.4 の 6。どれも「2.7（2.8）で決めた」という項目）は落とす。
2. 第 2 章には全体に共通する決まりだけを置き、FR に固有の中身は第 4 章のその FR の節に置く。
   - 2.5.3 の表は、全体に共通する場面（設定・引数の誤り、起動前提条件の不足、同時起動、ログの出力先を用意できない、不備ゲート）だけにする。FR に固有の場面の行は、その FR の節の「異常系」に、同じ 3 列（場面・終了コード・必ず含める内容）の表で置く。
   - 2.5.4 タイル取得の再試行は [4.1.3](../30_HLD.md#413-異常系) へ移し、2.5.4 は欠番にする。2.5 の題は「エラー処理・終了コード」にし、[NFR-004](../20_SRS.md#nfr-004-アクセスマナー) の追跡の宣言は 4.1 に置く。
   - 2.4.4 は `--phase` の値・動作・引数の組み合わせだけにし、フェーズごとの起動前提条件とその検査は [4.23.2](../30_HLD.md#4232-処理の流れ) に置く。
3. 「処理の流れ」と「未決事項と後続」の番号付きの項目は、節へのリンクに番号と項目の題を添えて指す（`の 4「代表行を選ぶ」`）。いくつかを並べるときは各番号に題を添え、続いた範囲（`の 1〜5`）は題を添えない。小節の 2 つ目からの箇条は、そのすぐ前の `**名前**` で始まる段落の名前で指す（`の「名前」の 3「題」`）。指される項目は頭に 30 字以内の題を置き（`4. **代表行を選ぶ**。本文`）、指されない項目には題を置かなくてよい。字下げした下位の項目は、親の項目に題を添えて指し（`の 4「題」の 2`）、下位の番号は照合しない。未決事項の項目は、解決しても消さず、番号を振り直さない（Decision 1 の統合のときだけは振り直す）。番号と題は `make lint`（`tools/lint_docs.py` の検査G）が照合する。
4. 決める前に始めた記録（レビューの周回の記録、Issue のコメント、調査資料の本文）は、番号を直さない（[ADR-HLD-002](ADR-HLD-002-hld-chapter-order-program-structure-first.md) の Decision 4 と同じ）。`docs/` の文書と ADR の本文のリンクは、新しい節へ直す。決める前に書いた記録と照らすときは、次の表で引く。

## Alternatives

- 2.6〜2.8 をまとめて、2.9〜2.11 の番号を詰める: 番号は連続するが、2.7・2.8 が別の中身の番号として使い直され、決める前の記録の「2.8」がディレクトリ構成かフェーズ分割かを日付で見分ける必要が出る。却下（持ち主の判断、2026-10-09）。
- 2.6〜2.8 をまとめない: 費用は最小だが、独立した 3 節が過剰という問題が残る。却下（同上）。
- 2.5.3 の表を残し、FR ごとの小見出しで分けるだけにする、または各 FR の節から 2.5.3 の行を指すリンクだけを足す: 1 つの FR の異常系を 2 か所見に行く状態が残る。却下（同上）。
- 移す 2.5.3 の行を、移す先の「異常系」の既存の表に列として足す: 表は 1 つになるが、行ごとに既存の行と合わせる作業が要り、写し間違いが起きやすい。却下（計画者の判断、2026-10-09）。
- 手順と未決事項の項目に、D のような通し番号の ID（未決事項に U、手順に S など）を振る: 節を移しても ID は変わらないが、覚える記号が増え、手順にまで ID を振るのは過剰。却下（持ち主の判断、2026-10-09）。
- 各項目を小見出しにし、アンカーで指す: 約 370 の見出しで目次と文書の形が崩れる。却下（同上）。
- すべての項目に題を置く: 書き方はそろうが、題を書く量が倍になり、指されない項目の題は誰も照合しない。却下（同上）。
- 決めるだけにし、書き換えは後で行う: 計画は小さくなるが、書き換えが済むまで lint を警告の扱いにする必要があり、古い参照が残る期間ができる。却下（同上）。

## Consequences

- [HLD](../30_HLD.md) の 2.4.4・2.5・2.6〜2.8・第 4 章の前書き・各節の「異常系」・4.23.2 を書き換え、2.6〜2.8 と 2.5.4 と 2.4.4 を指すリンクを新しい節へ直した。ほかの文書（テスト方針書、開発ガイド、ADR-URD-020、ADR-HLD-001、ADR-SRS-010・058・059・060・069）の、無くなる節を指すリンクも直した。当時の反映先として 2.5.3 を挙げた ADR のリンクは、2.5.3 が残るので直していない。
- HLD の指される項目に題を置き、項目を指す参照に題を添えた。4.13.2 の「開き方による切り替え」と 4.19.2 の「除外判断を読み込む」は、2 つ目からの箇条の形（`**名前**` の段落と字下げしない箇条）にした。
- [文書管理ルール](../CLAUDE.md)の「HLD と LLD の書き分け」に Decision 2 を、「HLD の記号の書き方」に Decision 3 の規則を足した。`tools/lint_docs.py` に検査G を足した。
- HLD の外の文書（ADR、調査資料、テスト方針書）から項目を `の N` で指しているものと、字下げした下位の項目の番号は、検査G の対象外である。
