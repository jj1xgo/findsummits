# ADR-OPS-003: リスク台帳を GitHub Issues の `risk` ラベルで置き、フェーズゲートごとに見直す

| 項目 | 内容 |
|---|---|
| 状態 | 採用・実装済み |
| 決定日 | 2026-10-08 |

---

## Context

[開発ガイド §4](../03_development.md#4-フェーズゲート) のフェーズゲートは、観点 5「リスク管理」で、リスク台帳とコンティンジェンシープランの整備状況を記録するとしていた。しかし、リスク台帳そのものは定義していなかった。ISO/IEC/IEEE 12207:2026 はリスク管理をプロセスの 1 つに置いている（[ADR-OPS-002](ADR-OPS-002-reference-standards-and-intended-deviations.md) の参照の範囲。公開の目次による。規格の本文では確かめていない）。

SRS → HLD のゲート（2026-07-12）では、専用の台帳を個人開発の規模には過剰として見送り、代わりの仕組み（Issue の優先度のラベル、ADR の Consequences、HLD の進捗表の備考、観点 4 の体制の評価）で扱うとした。その後、HLD の進捗表は GitHub Issues に移って無くなった。まだ起きていないリスク（標高タイルの取得の一部の失敗、外部データの仕様の変更、参照規格の本文を確かめていないことなど）は、作業ごとの引き継ぎの記録にだけ書かれ、引き継ぎを書き直すたびに落ちやすくなっていた。

## Decision

1. リスク台帳を、GitHub Issues に `risk` ラベルを付けた Issue の集まりとして置く。1 リスク 1 Issue とする。新しい文書やツールは作らない。
2. 本文には、リスク（何が起きると、何に響くか）、起きやすさ（高・中・低）、影響（高・中・低）、対策（いましていること）、起きたときの対応（コンティンジェンシープラン）の 5 つを書く。担当の欄は置かない（メンテナが 1 人で、いつも同じ人になるため）。
3. ラベルは `risk` と、起きやすさと影響のうち高い方に合わせた優先度のラベルを付ける。種別のラベル（`type:` で始まるもの）は付けない。リスクは、決めるべき論点でも起きた欠陥でもないためである。対策が別の Issue になっているときも `risk` の Issue は立て、対策の欄からその Issue を指す。
4. open は監視中を表す。リスクが消えたとき、または起きて欠陥や論点の Issue に移ったときに閉じ、閉じる理由をコメントに書く（移したときは移行先の Issue を添える）。
5. フェーズゲートのたびに open の `risk` の Issue をすべて見直し、観点 5 に一覧と見直しの結果を書く。見直しの中で見つけた新しいリスクは Issue を立てる。前提が変わったと気づいたときは、その場で見直し、必要なら本文と優先度のラベルを更新し、変更の理由をコメントに残す。
6. 置き方の正本は [開発ガイド §4.1](../03_development.md#41-リスク台帳) とする。

## Alternatives

- **(a) 台帳を置かず、見送りを正式にする**: 2026-07-12 の判断を続ける形で費用は無い。しかし、代わりの仕組みの 1 つが既に無くなっており、まだ起きていないリスクを持つ場所が引き継ぎの記録だけになる。不採用（持ち主の判断、2026-10-08）。
- **(b) 文書（`docs/` の中の表）で台帳を持つ**: 一覧は 1 か所で見やすい。しかし、項目を足すたびに文書の commit とレビューが要り、Issue と同じ優先度の並びに乗らない。不採用。
- **(c) 担当・期日・スコアなどの項目を足す**: 個人開発では担当が常に同じで、スコアは実データが無く根拠の無い数字になる。不採用。

## Consequences

- [開発ガイド](../03_development.md) の観点 5 を、§4.1 の台帳を見直した結果を書く形に改め、§4.1 を足した。
- `risk` のラベルは、本 ADR を取り込んだ版を公開した後に作る。最初の `risk` の Issue は、引き継ぎの記録の未解決事項からメンテナが選んで立てる。
- 12207 の本文で確かめていない点（リスク管理のプロセスが求める活動と記録の範囲）は、[ADR-OPS-002](ADR-OPS-002-reference-standards-and-intended-deviations.md) の Decision 4 に従い保留する。
