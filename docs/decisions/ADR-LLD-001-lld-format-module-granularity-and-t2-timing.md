# ADR-LLD-001: LLD の書式とモジュールの粒度を決め、「ファイル」のパスの実在の検査を COD の段から効かせる

| 項目 | 内容 |
|---|---|
| 状態 | 採用・未実装 |
| 決定日 | 2026-10-14 |

---

## Context

詳細設計書（LLD、`docs/40_LLD.md`）は、概要設計書（HLD）の確定とフェーズゲート 3（HLD → LLD）の後に書き始める。書き始める前に、次の 5 つが決まっていなかった。

- LLD の章立てと、モジュールの節の中の書き方。[文書管理ルール「HLD と LLD の書き分け」](../CLAUDE.md#hld-と-lld-の書き分け)は、LLD に「関数ごとの細部（型、内部のデータの持ち方、メッセージの文面、ファイルへの割り付け）」を書くとするが、節の並びは決めていない。
- モジュールの粒度。[ADR-HLD-001](ADR-HLD-001-program-structure-chapter-and-two-tier-it.md) は、プログラムと関数の名前と一覧を [HLD 第 3 章](../30_HLD.md#3-プログラム構造)で決め、LLD のモジュールの粒度は「LLD の書式を決めるときに決める」とした。[追跡の宣言](../CLAUDE.md#追跡の宣言)の検査（`tools/lint_trace.py` の T3）は、LLD の確定後、HLD の第 3 章〜第 5 章のどの節にも、それを「対応 HLD」に持つモジュールを求める。第 5 章（NFR 設計）の 11 節は特定のプログラムに還元しにくい。
- HLD が LLD に送った項目の受け皿。HLD の各節の「目的と範囲」の `- 対象外:` の行のうち「LLD」を含む行が 27 行あり、ログの文面、一時ファイルの名前、書きかけのファイルを残さない書き方のように、いくつもの節で同じ種類の項目が繰り返し出る。[ADR-HLD-008](ADR-HLD-008-remove-hld-open-items-subsections.md) の[付録 B](ADR-HLD-008-remove-hld-open-items-subsections.md#付録-b-旧番号の対応表) は、旧「未決事項と後続」の項目のうち送り先が LLD のものを、この「対象外」の行へ移した。HLD を書く段で挙がった単体テスト（UT）の候補は [#202](https://github.com/jj1xgo/findsummits/issues/202)「LLD と IT を書くときに、UT と IT の候補を割り当てる」に集めてある。結合テスト仕様書（`60_IT.md`）の §5 の対応表は、システムテスト（ST）から移した 45 件を「UT（`50_UT.md` で作る）」としている。
- LLD 末尾の追跡の表の要否。[開発ガイド 6.1](../03_development.md#61-宣言と追跡マトリクス) は「LLD 末尾の表は LLD を作るときに検査に足す」と、表を置く前提で書いていた。
- LLD の「ファイル」の宣言の検査の時期。`tools/lint_trace.py` の T2 は、「ファイル」に書いたパスが git に無ければ、LLD の文書があるだけで止める。今のコードはプロトタイプで、ファイルの名前は HLD の名前（[HLD 2.6.4](../30_HLD.md#264-ディレクトリ構成) と第 3 章）にそろっていない。HLD の名前どおりのパスを書くと、コードの段（COD）でコードを書き直すまで T2 が止め続ける。

持ち主が 2026-10-14 に次のとおり決めた。

## Decision

1. **章立て**: LLD は、§1 に用語と規約、§2 に共通部品と横断、§3 以降に CMP1〜CMP8 の順でコンポーネントごとの章（§3 が CMP1、…、§10 が CMP8）を置き、各章の下にモジュールの節を置く。
   - §1 は、[文書管理ルール「ドキュメントフォーマット標準」](../CLAUDE.md#ドキュメントフォーマット標準)の番号付きの「用語定義」の節を兼ね、用語の定義の後に、LLD の中だけの規約（宣言の書き方、横断の節の指し方など）を置く。
   - §2 は、[HLD 3.9](../30_HLD.md#39-共通部品) の共通部品のモジュールと、HLD の「対象外」の行で繰り返し出る項目を受ける横断の節を持つ。横断の節は、ログとメッセージの文面の決まり、ファイルの名前と書き方（一時ファイル・ロックファイル・取得完了の記録の名前と、書きかけのファイルを残さない書き方）、言語ごとに別に実装する式のテストベクトル（HLD の DEC6 の決まりで C++・Python・JavaScript の結果をそろえるもの）の 3 つから始める。
   - 横断の節はファイルに割り付ける単位ではないので、追跡の宣言（`ID`・`対応 HLD`・`ファイル`）を持たない。各モジュールの節は、横断の節の決まりに従うところを、その節へのリンクで指し、写さない。
2. **モジュールの節の書き方**: 各モジュールの節は、見出しの直下に追跡の宣言（`- **ID**: LLD-<モジュール名>`・`- **対応 HLD**:`・`- **ファイル**:`。書式は[文書管理ルール「追跡の宣言」](../CLAUDE.md#追跡の宣言)のまま）を置き、小節を「ファイル割付」「型とデータ」「関数の細部」「メッセージ文面」「UT 候補」の 5 つで、この順に固定する。
   - 書くことが無い小節も見出しを残し、「なし」と理由を書く。
   - パスの一覧は「ファイル」の宣言が正で、「ファイル割付」の小節は関数をそのパスに割り付けるだけにし、宣言に無いパスを足さない。
   - 関数が多いモジュール（`index_calc` など）は、「関数の細部」と「UT 候補」の中を、HLD 第 3 章の関数の表の群（表の分かれ目）ごとの見出しで分ける。
   - UT のケース ID は `UT-<モジュール名>-NN` とし、LLD の ID とそろえる。2 つ以上のモジュールの関数のつながりを確かめる UT は、呼び出しを取りまとめる関数のモジュール（CMP4 なら `run_normal_mode`・`run_wide_mode` のある `analyze_terrain_stage`、`index.html` なら起動の関数のあるモジュール）の「UT 候補」に置き、呼ばれる側のモジュールからはそのケースを指す。
3. **モジュールの粒度**: プログラム（HLD 第 3 章の各節の「プログラム」の表の 1 行）を 1 モジュールとすることを既定にする。例外は次の 2 つ。
   - CMP4 の `analyze_terrain` は、[HLD 3.4.3](../30_HLD.md#343-関数) の表の「群」を 1 モジュールとする（12 モジュール）。
   - CMP7 と CMP8 が共有する `index.html` は、[HLD 3.7.3](../30_HLD.md#373-関数)・[3.8.3](../30_HLD.md#383-関数) の「置き場」の「計算」（DOM に触れず Node.js で UT を行う script 要素。関数 50）と「画面」（DOM・地図・localStorage に触れ、手動で確かめる script 要素。関数 28）の 2 モジュールに分け、どちらも「対応 HLD」に HLD の 3.7 と 3.8 を並べる。

   2 つ以上のプログラムが使う部品は、プログラムに属さないので別のモジュールにする。HLD 3.9 の共通部品は §2 の 1 モジュール、CMP5 の[コンポーネント内の共通部品](../30_HLD.md#354-コンポーネント内の共通部品)は §7 の 1 モジュールとする。
4. **モジュール名**: HLD のプログラム名をそのまま使う。CMP4 の群は `analyze_terrain_` の後に群の英語の短い名前を付ける。`index.html` は拡張子を除いた `index` の後に `_calc`（計算）・`_screen`（画面）を付ける。HLD 3.9 の共通部品は `common`、CMP5 のコンポーネント内の共通部品は `cmp5_common` とする。名前は ID の書式（英数字と `_`）に従う。HLD でプログラム名や群を変えたときは、LLD のモジュール名を同じ変更で直す（[文書管理ルール「HLD と LLD の書き分け」](../CLAUDE.md#hld-と-lld-の書き分け)の名前の決まり）。

7. **送った項目の受け皿**: HLD の「対象外」の行で送り先が LLD の項目（[付録 B](ADR-HLD-008-remove-hld-open-items-subsections.md#付録-b-旧番号の対応表) の送り先が LLD の行は、HLD のこの行に移っている。今の文面は HLD を正とする）は、次のとおり置く。
   - 1 つのプログラムだけにかかるものは、そのモジュールの節の該当の小節に置く。
   - 2 つ以上の節で同じ種類のものは、§2 の横断の節に置く。
   - どのプログラムにも属さない項目（Makefile のターゲット名・テスト用の実行ファイルの名前など。[HLD 2.6.1](../30_HLD.md#261-目的と範囲) の「対象外」の行）は、§2 の横断の節に置く（1 つの節にしか出なくても同じ）。

   UT の候補は、該当するモジュールの節の「UT 候補」の小節に割り当てる。入力は 2 つある。[#202](https://github.com/jj1xgo/findsummits/issues/202) の UT の候補と、`60_IT.md` の §5 の対応表で「UT（`50_UT.md` で作る）」とした 45 行（ST のケースごとに、確かめる関数を受け持つモジュールを選ぶ）。#202 の IT の候補は、`60_IT.md` を書くときに割り当てた（#202 のコメント）。
8. **UT の仕様書**: 単体テスト仕様書（`docs/50_UT.md`）は LLD の段で作る（[テスト方針書 §2](../02_test_policy.md#2-テストレベル定義と役割分担)）。章立ては LLD の §2 以降のモジュールの並びにそろえ、各モジュールの「UT 候補」の小節からケースを起こす。[ADR-IT-001](ADR-IT-001-two-part-it-and-moved-st-cases.md) の Decision 3 が `60_IT.md` の §5 の対応表に「UT（`50_UT.md` で作る）」と書いた行は、`50_UT.md` を作るときに UT のケース ID に置き換える。
9. **LLD 末尾の追跡の表**: LLD は末尾に追跡の表を置かない。モジュールと HLD の節の対応は各モジュールの宣言が正で、被覆は T3 が宣言から検査する。表は 26 モジュールの宣言から機械で組み立てられる写しになるので、照合の検査（T4）も足さない。
10. **「ファイル」のパスの実在の検査の時期**: `tools/lint_trace.py` の T2 のうち、LLD の「ファイル」に書いたパスが git にあるかの検査は、LLD がフェーズゲートを通った後（ゲート 4〈LLD → COD〉で LLD を `CONFIRMED_STAGES` に入れた後。COD の段に入った後）だけ効かせる。段の判定は、ほかの段で効く検査（T3・T5、[ADR-HLD-001](ADR-HLD-001-program-structure-chapter-and-two-tier-it.md) の Decision 5 の LLD の T3、IT の確定後の T3）と同じく `CONFIRMED_STAGES` で行う。それまでも、「ファイル」の宣言が無い・コード表記のパスが無いことは T1 が止める。

## Alternatives

- 関数を 1 モジュールとする: HLD 第 3 章の関数の数だけ節ができ（`index.html` だけで 70 を超える）、型やデータの持ち方のように関数にまたがる細部の置き場が無い。却下。
- ファイルを 1 モジュールとする: ファイルの名前は LLD で決めるもので、書き始めに単位が決まらない。`public/index.html` は 1 ファイルなので、性質の違う計算と画面が 1 節にまとまる。却下。
- CMP4 もプログラム単位（1 モジュール）にする: HLD 3.4.3 が関数を処理の段（対象、窓、タイルとグリッド、走査、書き出しなど）に沿った群に既に分けていて、群をそのままモジュールにすれば、UT のケース ID の対象も段ごとに分かれる。1 モジュールにすると、関数が 40 を超える 1 節に、段の違う細部が混ざる。`index_calc`（関数 50）も関数は多いが、HLD 3.7.3 の分かれ目は UT の手段（自動か手動か）で、それに合わせて 2 つにし、中を群の見出しで分ける（Decision 2）。却下。
- `index.html` を 1 モジュールにする: 計算は Node.js で自動の UT を行い、画面は手動で確かめる（HLD 3.7.3）。UT の書き方が違うものが 1 節にまとまる。却下。
- LLD の章を FR/NFR の順にする: プログラムの中の関数が複数の章に散り、「ファイル」の割り付けと UT の単位がずれる。HLD は処理の正本を第 4 章・第 5 章に置き、第 3 章でプログラムに割り付けたので、LLD はプログラムの側から書く。却下。
- 第 5 章の受け手を §2 の横断の節にし、横断の節にも追跡の宣言を置く: 横断の節はファイルに割り付ける単位ではなく、「ファイル」に何を書くかが決まらない（すべてのファイルを並べることになる）。却下。
- LLD 末尾にモジュールと HLD の節の表を置き、T4 で宣言と照合する（HLD §6 と同じ形）: 宣言から組み立てられる写しを手で保つことになり、直すたびに 2 か所を直す。被覆は T3 で足りる。却下。
- 「ファイル」のパスの実在の検査を `EXEMPTIONS` で外す: `EXEMPTIONS` は構造上の例外を指摘の 1 件ごとに外すもので、モジュールが増えるたびに項目を足し、COD の段で 1 件ずつ消すことになる。外す理由は個々の指摘ではなく段にあるので、段で効かせる。却下。
- 「ファイル」に今のプロトタイプのパスを書き、COD の段で HLD の名前に書き換える: LLD の確定の後に宣言を書き換えることになり、HLD の名前と LLD の宣言がそろわない期間ができる。却下。
- 段の判定に `COD` を `CONFIRMED_STAGES` に足す: `CONFIRMED_STAGES` はフェーズゲートを通った文書の段で、COD には対応する文書が無い（`STAGE_DOCS` に無い段は T1 が止める）。ゲート 4 で LLD を入れることが COD の段に入ることに当たるので、LLD で判定する。却下。

## Consequences

- `docs/40_LLD.md` は、ゲート 3 の判定の後に、本 ADR の章立てと書き始めのモジュールの一覧で書き始める。本 ADR の状態は、LLD の全モジュールの節がそろったときに「採用・実装済み」にする。
- [文書管理ルール「HLD と LLD の書き分け」](../CLAUDE.md#hld-と-lld-の書き分け)に、LLD の章立てとモジュールの節の小節の短い段落を足し、本 ADR を指す。[追跡の宣言](../CLAUDE.md#追跡の宣言)の LLD の書式は変えない。
- [開発ガイド 6.1](../03_development.md#61-宣言と追跡マトリクス) の LLD 末尾の表の文を、表を置かず宣言から T3 で検査する形に直した（Decision 9）。
- `tools/lint_trace.py` は、LLD の「ファイル」のパスの実在の検査を `'LLD' in confirmed` のときだけ行うように改めた（2026-10-14。[開発ガイド 6.2](../03_development.md#62-検査) の T2 の行）。ゲート 4 で LLD を `CONFIRMED_STAGES` に入れると、この検査と T3・T5 が一緒に効き始め、コードを HLD の名前にそろえる前なら CI が止まる。その段取り（`CONFIRMED_STAGES` に入れる時機と、コードをそろえる作業の順）は、ゲート 4 の前に決める（Issue を立てる）。
- `tools/lint_trace.py` の T5 の対象には、HLD 2.6.4 で製品とテストに区分したもののうち、次が入っていない: 製品の `public/index.html`、そのテストの `tests/public/`、拡張子の `.js`・`.html`（`CODE_SUFFIXES` に無い）、HTML の script 要素の中の `trace:` のコメントの読み方。このままだと、LLD の確定後に `LLD-index_calc`・`LLD-index_screen` の「ファイル」で T5 が止まり、UT の確定後に `index_calc` の UT のケースが実装されていないとされる。[開発ガイド 6.2](../03_development.md#62-検査) の「製品のコード」も、HLD 2.6.4 の「製品」区分のうち `src/`・`scripts/` だけを指していて、2.6.4 の表と範囲が違う。上の段取りの Issue で、対象を足すか、本 ADR に扱いを追記するかを決める。
- UT のケース ID の連番は 2 桁（[テスト方針書 §6](../02_test_policy.md#6-テストケースid命名の大枠)）で、1 モジュール 99 件までである。`50_UT.md` を書く中で 99 件を超える見込みのモジュールが出たら、連番の桁を改めるか、そのモジュールを HLD の群で分けるかを決め、本 ADR に追記する。
- 横断の節は「対象外」の行で繰り返し出る種類の数だけ増やしてよい。増やすときは本 ADR に追記しない（受け手の表を変えるときだけ追記する）。
