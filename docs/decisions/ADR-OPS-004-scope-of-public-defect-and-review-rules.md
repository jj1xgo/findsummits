# ADR-OPS-004: 欠陥管理・課題のラベル・レビューの原則を公開の開発ガイドに置き、道具に依る手順と個人の運用は個人の補足に残す

| 項目 | 内容 |
|---|---|
| 状態 | 採用・実装済み |
| 決定日 | 2026-10-08 |

---

## Context

欠陥を見つけたときの流れ、課題のラベルの意味、レビューの手順は、メンテナ個人の運用の補足にだけ書かれていた。一方で、公開の文書はラベルの名前を定義なしで使っていた（[開発ガイド §4.1](../03_development.md#41-リスク台帳) の `bug`・`type:`・優先度のラベル、[テスト方針書 5.3](../02_test_policy.md#53-既知欠陥の許容基準) の `priority:低`）。[AGENTS.md「個人運用の補足」](../../AGENTS.md#個人運用の補足)は、補足が無くても公開の文書だけで共通開発規則が成り立つとしている。

[ADR-OPS-002](ADR-OPS-002-reference-standards-and-intended-deviations.md) は、ISO/IEC/IEEE 12207:2026 を参照し、手順の一部を個人の補足に置く形を Decision 3 の表の 5 行目に「未確認」として保留し、どこまで公開するかを決めていなかった。12207 は問題解決（欠陥管理）とレビューをプロセスとして置いている（公開の目次による。規格の本文では確かめていない）。

## Decision

1. 道具に依らない骨格を、[開発ガイド §7](../03_development.md#7-課題とレビュー) に置く。課題のラベルの意味（§7.1）、欠陥の扱い（§7.2）、レビューの原則（§7.3。作成に関わらないレビュアー、作業の区分とレビューの段階、指摘の深刻度とその扱い、仕様文書の多視点のレビュー）である。
2. 次は公開の文書に置かず、メンテナ個人の運用の補足に置く。
   - 使う道具の名前とその起動のしかた（仕様文書の多視点のレビューの具体的な手順を含む）
   - レビュアーとモデルの割り当て
   - レビューの記録の置き場と形式
   - どの課題を Issue にし、どれを別の作業リストで扱うかの振り分けと、公開しないリポジトリへの起票先の振り分け
   - 課題の対応の流れ（対応方針と対応完了のコメント、閉じる者）
3. 公開の文書と個人の補足が食い違うときは、公開の文書に従う（[AGENTS.md「個人運用の補足」](../../AGENTS.md#個人運用の補足)）。このため §7 は、2 に挙げた個人の運用を禁じる書き方をしない（§7.1 はラベルの意味だけを定め、何を Issue にするかとどこに起票するかを定めない）。個人の補足は、§7 と重なる部分を §7 への参照にする。
4. ADR-OPS-002 の Decision 3 の表の 5 行目を、2 に挙げたものを個人の補足に置く形に狭め、本 ADR を指す。確認の程度は「未確認」のまま残す（12207 が公開の範囲について何を求めるかは、引き続き確かめていない）。

## Alternatives

- **(a) 欠陥の扱いとラベルだけを公開し、レビューの手順はすべて個人の補足に残す**: 変更は小さい。しかし、外から貢献する人には、どのレビューを経れば取り込まれるのかが分からない。不採用（持ち主の判断、2026-10-08）。
- **(b) 何も公開せず、ADR-OPS-002 の 5 行目の理由を書き足して確定する**: 費用は無い。しかし、公開の文書がラベルの名前を定義なしで使う状態が残る。不採用（持ち主の判断、2026-10-08）。
- **(c) 道具の名前と起動のしかたまで公開する**: 道具とモデルは個人の運用で変わりやすく、変わるたびに公開の規則の改訂とレビューが要る。不採用。

## Consequences

- [開発ガイド](../03_development.md) に §7「課題とレビュー」を足し、[AGENTS.md「作業時の必須事項」](../../AGENTS.md#作業時の必須事項)と[文書管理ルール](../CLAUDE.md)の常駐ドキュメントの説明から指した。
- ADR-OPS-002 の Decision 3 の表の 5 行目を狭め、本 ADR を指した。
- 12207 の本文で確かめていない点（問題解決とレビューのプロセスが求める活動と記録の範囲）は、ADR-OPS-002 の Decision 4 に従い保留する。
