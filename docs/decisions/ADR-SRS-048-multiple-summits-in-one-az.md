# ADR-SRS-048: 同一 AZ 内の複数登録を組単位で要確認・申請保留にする

| 状態 | 採用・未実装 |
| 決定日 | 2026-09-21 |

## 2026-09-21 担当者指定削除の追補

本 ADR の保留組（AZ 内・AZ 外とも）への編集・採用禁止は維持する。[ADR-SRS-049](ADR-SRS-049-unmatched-manual-delete.md) の担当者指定削除は review_group_id が空の孤立 unmatched だけを対象とし、保存済み判断でも保留組を解除しない。

以下は当初の決定記録（既存追補を除く）。

## Context

AZ が互いに素であることは、1 登録座標が属する AZ が高々1個であることを示す。
1 AZ 内に異なるコードの既存登録が複数存在しないことは導けない。
従来の [FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) はこの2つを混同し、
既存コード1個をピークに付与する GeoJSON・一覧・申請を前提としていた。
登録標高・登録日だけでは残すべき登録を確定できず、恣意的な選択や登録の取り落としを防ぐ必要がある。

## Decision

同一 AZ 内に異なる SummitCode の現役登録が2件以上ある場合、ピークと AZ 内登録全件を
`match_status=ambiguous`、`category=review` とし、その組の申請を保留して通常処理を続行する。
入力は SummitCode が一意の CSV を前提とする。同座標でも異なるコードは別件とし、廃止済みは数えない。
同一コードの重複行の採用規則は本決定の対象外。

- 主ピーク特定は ambiguous を含む従来の候補集合・プロミネンスと座標の選択規則を維持する。
  選ばれた親が ambiguous の場合だけ、その AZ 外削除候補も同じ組の review とする。
  `summit.match_status=delete` は保持し、別親への付け替えや重なるゾーンによる保留の連鎖は行わない。
- ピークに代表既存コードや仮コードを付与しない。地形・全登録・接続線を保持し、全て review にする。
  `review_reason` と成果物内の結合用 `review_group_id` を全 GeoJSON フィーチャ・両一覧 XLSX に追加する。
  組 ID は AZ 内コード集合から決定論的に生成し、入力変更後の判断を引き継ぐ永続キーにはしない。
- 両一覧は1行=1既存登録。AZ 内行にピーク・コル・解析値を反復し、AZ 外保留行は解析値を空欄とする。
  AZ 外保留行の主ピークコードは空文字、距離は保持し、組 ID 経由で AZ 内行の主ピーク情報を参照できる。
- 作業用・公開用ビューアは要確認フィルターで組全体を表示し、登録ごとの検索と組内移動を提供する。
  保留組への編集・採用操作は設けず、過去の編集値による review 情報の上書きや申請への漏出を防ぐ。
  申請書は通常の add / delete / band_change のみ出力し、保留組数・登録件数を警告する。
  ZIP は保留組全体を review.geojson に格納する。カテゴリは5種を維持する。
- 複数登録の件数自体では停止せず、孤立 unmatched のしきい値には加算しない。
  AZ / delete 判定ゾーン不完結・コル未確定等の既存ゲートは review ピークも検査する。
  不備時は全件評価後に GeoJSON/XLSX を出力して停止し、ビューア生成をスキップする。
- 組数・AZ 内件数・AZ 外保留件数、組の座標・コード一覧を記録する。ログ・一覧・GeoJSON の保留組を
  入力順に依存しない順序に固定する。

値域・空値・行の取得元・親参照・並びの正本は [FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定)。
表示・申請・一覧・ZIP の消費契約は [FR-019](../20_SRS.md#fr-019-html-ビューア機能仕様)・
[FR-011](../20_SRS.md#fr-011-申請書-xlsx-生成)・[FR-012](../20_SRS.md#fr-012-サミット一覧申請内容反映版生成)・
[FR-021](../20_SRS.md#fr-021-申請エビデンス-zip-生成) とし、検証条件は [ST](../70_ST.md) に記録する。
検討と Opus レビューの経緯は [採用時仕様案](research/multiple-summits-in-one-az-spec.md) に残す。

## Alternatives

| 案 | 採らない理由 |
|---|---|
| 登録標高・登録日・コード順で1件を残す | 正しい存続登録の根拠にならず、登録誤りを固定する可能性がある |
| 複数登録を検出したら全処理を停止する | 登録上の未決着だけで無関係な申請候補まで確認できなくなる |
| AZ 内登録だけを保留し AZ 外削除は自動申請する | 地形上の従属判定は可能でも、その主ピークの存続コードが未決着。関連登録を一組として担当者に確認してもらうため AZ 外も保留する |
| ambiguous 親を除外し別の主ピークを選ぶ | 従来の地形上の主ピーク選択を変更し、未決着の関係を隠す |
| 件数による新しい停止ゲートを追加する | 正常時の分布を未実測であり、妥当なしきい値の根拠がない。まず警告・保留・実測を採る |

## Consequences

[ADR-SRS-037](ADR-SRS-037-unmatched-summit-needs-review.md) の孤立要確認とは区別し、
[ADR-SRS-043](ADR-SRS-043-matched-peak-as-delete-reference.md) の自動削除申請に存続コード未決着時の例外を設ける。
通常 matched 親の削除申請は維持する。
[ADR-SRS-044](ADR-SRS-044-category-property-summit-centric-5class.md) の導出・
[ADR-SRS-045](ADR-SRS-045-summit-xlsx-row-aggregation-model.md) の行集約を上記範囲で拡張する。

過大な AZ 等の解析不備が複数登録として大量発生する可能性があり、既存ゲートが全て検出する保証はない。
当面は件数の警告と申請除外を行い、それだけでは異常終了しない制約を受け入れる。
初回全国解析で入力リスト基準日・ソフトウェア版・解析範囲・組数と内訳・原因を記録し、
その分布と原因の確認を件数ゲート再検討のトリガーとする。未実測の件数を根拠にしない。

現段階の申請は保留組を除いたドラフト。担当者判断後の保留解除・採否の永続化は別の仕様検討とする。
HLD で内部構造・UI 配置等を具体化する。今回の文書改訂ではプロトタイプコード・モックアップを変更せず、
実装と初回全国解析の実測は設計確定後に行う。この実測を仕様決定の完了条件とはしない。
