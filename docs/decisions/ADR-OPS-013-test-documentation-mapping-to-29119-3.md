# ADR-OPS-013: テスト文書と 29119-3:2021 の項目の対応を置き、UT のカバレッジ項目の表を試す

| 項目 | 内容 |
|---|---|
| 状態 | 採用・実装済み |
| 決定日 | 2026-11-26 |

---

## Context

テスト文書の 3 本（[単体テスト仕様書](../50_UT.md) 833 件、[結合テスト仕様書](../60_IT.md) 197 件、[システムテスト仕様書](../70_ST.md) 399 件。2026-11-26 に数えた）は、[ADR-OPS-002](ADR-OPS-002-reference-standards-and-intended-deviations.md) の Decision 2 の表の ISO/IEC/IEEE 29119-3:2021 を参照するが、規格のどの項目がどこにあり、どれを外しているかを示す対応表が無かった。詳細設計書には IEEE 1016-2009 のビューポイントとの対応表がある（[ADR-LLD-001](ADR-LLD-001-lld-format-module-granularity-and-t2-timing.md)）。

jj1xgo は 2026-11-26 に、目的は成果物の品質の向上だと述べ、あわせて次の考えを述べた。「グローバルスタンダードに沿っていれば品質確認もやりやすい。独自方式では他の人の視線に触れても理解されず欠陥の温床になり得る」。

同じ日の片づけで、詳細設計書が列挙している引数の形（位置引数、`--help`、`--` だけ、空の引数など）を、単体テスト仕様書の `UT-check_cols-002` と `UT-generate_viewer-002` の入力が受けていない抜けが 2 件見つかった（直しは `3b60dc0`）。ケースの選び方は各モジュールの節の前置きに文で書いていて、詳細設計書の列挙とケースの入力を突き合わせる仕組みが無かった。29119-3:2021 は、テストケースの前にカバレッジ項目（覆う対象）を ID 付きで挙げる形を持つ。

規格の本文は買わない（ISO と IEC の販売ページで CHF 227、日本規格協会で 45,400 円。2026-11-26 に確かめた。jj1xgo が買わないと決めた）。項目の見出しの名前は、公開の目次で確かめた（[SOURCES「開発プロセスの参照規格」](../../ref/SOURCES.md#開発プロセスの参照規格)の二次資料）。

## Decision

進め方（各文書に対応表と英語名の併記を置く、単体テストに追跡とカバレッジ項目を足す、優先度などは理由を書いて外す、レビューの視点を ISO/IEC 25010:2023 の品質特性で組む）と、規格の本文を買わないことは、jj1xgo が 2026-11-26 に会話で決めた。視点の過不足を確かめた後に、受け渡しの両側の照合と、動かして保守する人のシナリオを足すことも、同じ日に jj1xgo が決めた。ほかの中身は設計者（Fable 5.2）が決め、jj1xgo が設計と計画を承認した。

1. **29119-3:2021 の項目との対応**: この節の末尾の「29119-3:2021 の項目との対応」の表を、テスト文書と 29119-3:2021 の項目の対応の正本にする。
2. **読み方**: 各テスト文書の 1 章に、末尾の表の全部の行を、その文書での置き場で引ける小節を置く。小節の表の列は、項目（英語名と条番号）、本書での置き場、外す場合はその理由の 3 つ。理由の文の正本は本 ADR で、小節には要約とリンクを書く。列の名前と規格の英語名の対応を、各文書の記述規約に書く。テストケースの表のヘッダーの文字列は変えない。
3. **カバレッジ項目の表（試行）**: 単体テスト仕様書の 7.4 と 8.1 のモジュールの節の前置きに、ID・LLD の関数・覆う対象・技法・ケースの 5 列の表を置く。書式と粒度の決まりはテスト方針書 5.2 と単体テスト仕様書の 1.2 に置く。技法の呼び名は ISTQB の CTFL シラバス v4.0.1 の 4 章の名前に合わせる。`make lint` の検査（開発ガイド 6.2）が保証するのは、表と詳細設計書の関数の見出し・メッセージの表の記号、表とテストケースと入力の目印の間の参照の整合までで、「覆う対象」の文と入力の中身が合っているかは、表を書くときの照合と多視点のレビューが見る。表を必ず置くモジュールは `tools/lint_trace.py` の `UT_COVERAGE_TRIAL`（今は 7.4 と 8.1）で、その節に正しい表がちょうど 1 つ無ければ `make lint` が止まる。入力の目印は、テストケースの「前提条件」か「手順」の列にあるものを照らす（範囲の書き方の端は数えない）。目印の文字列がその列のどこかにあれば通すので、別の入力を指す文（「(c) に加えて」など）に目印が残るケースでは、その入力の記述を消しても止まらない。試行の結果を見て、書式を確定するか、残りのモジュールにどう入れるかを決め、そのときに本 ADR に追記する。
4. **レビュー**: 多視点のレビュー（本体 `.agents/skills/spec-panel/SKILL.md`）に、対応表との照合、品質特性の逆引き、受け渡しの両側の照合、動かして保守する人のシナリオを足す。根拠は CTFL シラバス v4.0.1 の 3.1.3（レビューで見つけやすい欠陥の種類。インターフェース仕様の誤り、セキュリティの脆弱性、テストの網羅の抜けなど）、3.1.2（幅広い利害関係者をレビューに入れる）、3.2.2（シナリオによるレビュー）。視点の数は変えない。

### 29119-3:2021 の項目との対応

確認の程度: 見出しの名前で確かめた（2026-11-26。AS/NZS ISO/IEC/IEEE 29119.3:2022 の販売ページの目次は 8.3.3.8 まで、VDE Verlag のプレビューと DIN の目次は 8.3.3 まで）。規格の本文では確かめていない。規格は 4.1.3 に Tailored conformance の節を持つが、外すときに何を書くかの本文は読んでいない。「保留」は ADR-OPS-002 の Decision 4 の保留で、残りのモジュールへのカバレッジ項目の表の入れ方を決めるときに承認者に聞く。

| 29119-3:2021 の項目 | 扱い | 置き場・理由 |
|---|---|---|
| 5.2 Common information elements のうち Unique identifier・Status・Introduction・Scope | 持つ | 各文書のヘッダーと 1 章 |
| 5.2 のうち Issuing organization・Approval authority・Change history・References・Glossary | 外す | 発行と承認はフェーズゲートとテスト文書の確定の記録（[開発ガイド 4](../03_development.md#4-フェーズゲート)）、履歴は git、出典は SOURCES、用語は用語集にある（References と Change history は ADR-OPS-002 の Decision 3 の 1・2 行目と同じ型） |
| 8.2 Test model specification | 外す | テストモデルを別の文書にしない。ケースの選び方はモジュールの節の前置きと[テスト方針書 5.2](../02_test_policy.md#52-カバレッジ粒度の正本) に置く |
| 8.3.2 Test coverage items（Unique identifier・Description・Traceability） | 単体テストは試行中（7.4・8.1 の 2 節）、結合テストとシステムテストは保留 | 単体テストはモジュールの節の「カバレッジ項目」の表（Decision 3）。結合テストとシステムテストは表を持たない |
| 8.3.2.4・8.3.3.4 Priority | 外す | 正式な実行では対象範囲の全ケースを判定の対象にし、優先度で取捨をしない（実行しなかったケースは未実施として記録する）。持たせても全部が同じ値になる（要求に優先度を持たせない ADR-OPS-002 の Decision 3 の 6 行目と同じ理由） |
| 8.3.3.2 Unique identifier | 持つ | ID の列（[テスト方針書 6](../02_test_policy.md#6-テストケースid命名の大枠)） |
| 8.3.3.3 Objective | 単体テストは持つ、結合テストとシステムテストは保留 | 単体テストは「確かめること」の列。結合テストとシステムテストの表にはこの列が無い |
| 8.3.3.5 Traceability | 持つ（形が違う） | 単体テストは節の番号が詳細設計書のモジュールの節と同じこと（全節）と、「カバレッジ項目」の表の「LLD の関数」の列（試行中の 7.4・8.1）。結合テストは ID に入った概要設計書 3 章のつなぎ目の記号、システムテストは ID に入った FR・NFR・UR の番号（[開発ガイド 6.2](../03_development.md#62-検査) の検査が照らす） |
| 8.3.3.6 Preconditions | 持つ | 「前提条件」の列 |
| 8.3.3.7 Inputs | 持つ（置き場が違う） | 「手順」の列に対象の呼び方と渡すものを、「前提条件」の列に置く入力（ファイルと中身）を書く |
| 8.3.3.8 Expected results | 持つ | 「期待結果」の列 |
| （項目に無い） | 足している | 「合否判定基準」の列（期待結果のうち何をどう照合するか） |
| 8.4 Test procedure specification | 外す | 手順を別の文書にしない。ケースの中の操作は 1 ケース 1 行の「手順」の列が兼ねる。ケースの間の実行の順は決めず（各ケースは前提条件を自分で整える）、実行の開始と終了は正式な実行の記録に書く |
| 8.9 Actual results and test result | 持つ | 正式な実行の記録（[テスト方針書 5.5](../02_test_policy.md#55-テスト結果の記録)） |

## Alternatives

- **テスト文書の 3 本を規格の項目の形に組み替える**: 優先度・追跡・入力の列を足し、1,429 件を書き直す。いちばん規格に近いが、本文を持たないまま見出しだけで組み替えるので、寄せ方を誤る危険がある。不採用。
- **違いを ADR-OPS-002 の Decision 3 に記録するだけにする**: 軽いが、外の人が規格の知識で読める形にならず、目的に合わない。不採用。
- **レビューの規格（ISO/IEC 20246）を参照する規格に足す**: シラバスが名前を挙げているが、中身を読めていない。今は足さない。

## Consequences

- ADR-OPS-002 の Decision 2 の表にテスト技法の行（ISO/IEC/IEEE 29119-4:2021）を、Decision 3 の表に本 ADR を指す 1 行を足した。SOURCES に 29119-4:2021 の目録と、29119-3:2021 の見出しを確かめた二次資料 3 つを足した。
- 単体テスト仕様書・結合テスト仕様書・システムテスト仕様書の 1 章に対応の小節を置き、記述規約に英語名を併記した。
- テスト方針書 5.2 と単体テスト仕様書の 1.2 にカバレッジ項目の表の決まりを、開発ガイド 6.2 に検査を書いた。`tools/lint_trace.py` に表の検査を足した。
- 多視点のレビューの正本に、Decision 4 のチェックを足した。
