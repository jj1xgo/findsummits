# ADR-SRS-086: 山岳データ登録変更リストを突合の必須の入力にし、申請済みの候補の状態と「申請に戻す」判断の持ち方を SRS で定める

| 項目 | 内容 |
|---|---|
| 状態 | 採用・未実装 |
| 決定日 | 2026-10-19 |

---

## Context

[ADR-URD-029](ADR-URD-029-pending-applications-in-matching.md) は、SOTA 日本支部に申請済みで現行 SOTA リストに未反映の申請（山岳データ登録変更リスト）を、突合の入力にすると決めた（[UR-003](../10_URD.md#ur-003)）。入力の形、未反映の見分け方、変更の当て方、山岳 ID の表記、状態の持ち方、申請に戻す判断の扱いなど、ソフトウェア要件仕様書（SRS）で決めることは、同 ADR の Decision 5 に挙げ、そこでは決めていない。この ADR はそれを決める。

2026-10-19 に、登録変更リストの実物（<https://little-ctc.com/wp_html/sota_updatelist_2026.xhtml>。入手の入口は <https://little-ctc.com/sota_hp/>）を確かめた。

- ページは LibreOffice が書き出した XHTML で、表が 1 つある。2026・2025・2024 年の表が、新しい年から順に続く。各年の表の頭に「YYYY年 山岳データ登録変更リスト」の行と「YYYY-MM-DD Update」の行、2 行の見出し（結合したセルを含む）がある。
- 表の中は申請日の古い順に並ぶ。年の表と申請日は一致しない（再申請、年をまたぐ申請、同じ申請が 2 つの年の表に載る例がある）。2025 年の表の途中に「ここまでは2025年7月1日版に反映済」の行が 1 行だけある。状態の列は無い。
- アクションの欄が「追加」「変更」「削除」の行は 291 行（176・113・2）あった。照合に使う欄（アクション、山岳 ID、変更後の標高、追加の位置）は、すべて読めた。表記の揺れは、標高の末尾の `m`、座標の区切り、全角の空白、山岳 ID のアソシエーションの部分（`JA/KC-027` と書いた行が、SOTA サミットリストでは `JA5/KC-027`）だった。
- SOTA サミットリスト（2026-10-18）の JA 系の地域コードは、どれも 1 つのアソシエーションにだけ属する。変更・削除の行の山岳 ID は、そのままで一致するものが 112、廃止済みの登録に一致するものが 2（削除の 2 行）、アソシエーションの部分だけ違うものが 1 あった。

持ち主が 2026-10-19 に、次を決めた。

1. 入力は、利用者が保存した登録変更リストのページ（XHTML）を、そのまま読む。CSV に整える手順は設けない。
2. 置いていないときは、SOTA サミットリスト CSV と同じ必須の入力として止める。古さでは止めず、表の「Update」の日付を示して利用者が確かめる。
3. 「申請に戻す」の判断は、次の解析に引き継ぐ。
4. 公開用ビューアには、申請済みの候補を、申請済みと分かる印を付けて残す。出す申請の情報は、申請日と出典まで（申請者は作業用ビューアにだけ出す）。
5. SOTA サミットリストに無い山岳 ID の行は、利用者に知らせる。
6. 申請エビデンス ZIP の GeoJSON では、`pending_applications` の申請者（コールサイン）を空文字にする（第 1 周の spec-panel で、公開用データとして置かれるファイルに申請者が残る件を持ち主に回して決めた）。

## Decision

1. **入力**: 利用者が保存した登録変更リストのページを `$DATA_DIR/ref/` 直下に置き、そのまま読む。ファイル名の全体が `sota_updatelist_(\d{4})\.xhtml` に合うもので、複数あれば年が最大のものを採る（N03 行政区域 ZIP の [7.2.3](../20_SRS.md#723-n03-行政区域-zip) と同じ考え方。各年のページは前の 2 年分の表も含む）。ツールは取得しない。無ければ止まる（起動前提条件にも入れる）。設定のキーは足さない（置き場を SRS で固定した入力は設定で渡さない）。ファイルの中の外部参照（画像・スタイル・スクリプト）は読み込まず、実行しない。
2. **読み方**: ファイルの中の年の表をすべて読む。行の分け方と判定の順は次のとおり。
   - アクションの欄が空の行（年の題、Update、反映済みの目印など）と見出しの行は読み飛ばす。アクションの欄が「追加」「変更」「削除」の行を申請の行とする。それ以外の語がアクションの欄にある行は「読めない行」とする。
   - 列は見出しの文字で特定する。見出しが見つからない（書式が変わった）とき、ファイルが XHTML として読めないときは、突合の前に止まる。
   - 表記の揺れ（全角・半角、前後の空白、標高の末尾の `m`、座標の区切りの `,`・`，`・`、`・空白）は、読むときに揃える。
   - 申請の行のうち、追加で位置の座標が読めない行、変更・削除で山岳 ID が読めない行、変更で変更後の標高の欄に値があるのに数として読めない行、申請日の欄が空か日付として読めない行は「読めない行」とする（申請日は並びと判断時条件の鍵になるため。申請者の欄の空欄は許し、空文字として扱い、空の申請者どうしは同じ申請者として重複の判定と判断時条件に使う）。変更で変更後の標高の欄が空の行（名称・座標だけの変更）は、読めない行にせず、取り込まない行とする。
   - 同じ申請（アクション、山岳 ID か追加の座標、変更後の標高、申請者・申請日が同じ）が複数の年の表にあれば 1 つに数え、載っている年をすべて残す。
   - 年の表ごとの Update の日付を読む。読めない年の表は、日付を空にし、知らせる行に足して続ける。
3. **取り込む申請**: 追加（位置の座標がある行）、削除（山岳 ID がある行）、変更のうち次をすべて満たす行。変更後の標高があり、それを `floor` してから [FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) の `points` と同じ表でバンドにした値が null でなく、SOTA サミットリストの今の `AltM` のバンドとも null でなく違う。名称・座標だけの変更、バンドの変わらない変更、バンドが null になる変更は取り込まない（[URD §6](../10_URD.md#6-スコープ外対象外) のスコープ外。[FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) が null のときに変更の候補にしないのと同じ）。判定の順は、アクション、山岳 ID の照合（Decision 4）、バンドの比較。
4. **山岳 ID**: SOTA サミットリストの SummitCode とそのまま照合し、無ければ地域コードと番号（`/` の後ろ）で照合する（JA 系のアソシエーションで地域コードが重ならないため。重なる地域コードがあれば、その行は知らせる行にする）。どちらでも見つからない ID の行は、「SOTA サミットリストに無い ID」として利用者に示す。廃止済み（基準日で有効でない）の登録に当たる ID は、反映済みとみなし、示さない。
5. **照合**: 未反映かどうかは別に判定しない。反映済みの申請は、次の理由で通常は何にも当たらない（例外は Consequences の既知の限界）。追加は、既存サミットの AZ に入る。削除は、廃止済みの ID になる。変更は、今の標高とバンドが同じになる。
   - 追加の申請: 位置の座標を [FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) のピークと同じく Z15 の画素の中心に寄せ（AZ の境界の上の点をあいまいにしないため。点の内外の判定も同じ規則）、`category=add` のピーク（`match_status` が `new`・`dominant`）の AZ ポリゴンに入れば、そのピークに「同じ内容」で当てる。どの追加の候補にも入らず、既存サミット（`matched`・`ambiguous` のピーク）の AZ にも入らない追加の申請は、「当たらなかった追加の申請」として利用者に示す。
   - 削除の申請: その山岳 ID のサミットに当てる。サミットが削除の候補なら「同じ内容」。その ID に対応するピークが変更の候補なら、そのピークに「違う内容」で当てる。
   - 変更の申請: その山岳 ID のサミットに当てる。対応するピークが変更の候補で、申請の変更後のバンドがピークの `points` と同じなら「同じ内容」、違えば「違う内容」。サミットが削除の候補なら「違う内容」。
   - 候補でないもの（`no_change`、`review`）に当たった申請は、候補の判定を付けない。ただし、担当者指定削除で後から削除の候補になるサミットのために、`unmatched` のサミットへの削除・変更の申請は、サミットの Point に保持し（`pending_match` は空文字）、[FR-019](../20_SRS.md#fr-019-html-ビューア機能仕様) がその時点で判定する。
   - 1 つの候補に複数の申請が当たれば、「同じ内容」が 1 つでもあれば「同じ内容」、無ければ「違う内容」とする。
   - 既存サミットの近く（AZ の中など）にある追加の申請、管理者が座標を直して反映した追加の申請は、特別に扱わない。上の AZ による照合で、既存サミットの AZ に入れば何にも当たらず、追加の候補の AZ に入ればその候補に当たる。
6. **状態の持ち方**: 除外（[UR-015](../10_URD.md#ur-015)、`application_exclusion`）とは別の属性にする。
   - バッチが書く属性は 3 つ。`pending_applications` は、当たった申請と保持した申請の一覧で、正本とする。論理項目は、アクション、山岳 ID（SOTA サミットリストの表記に揃えたもの）か追加の座標（揃えた値）、変更後の標高とそのバンド、申請者、申請日、載っている年の表の一覧、その候補への当たり方（同じ内容・違う内容・保持）。並びは、申請日の昇順、アクション、山岳 ID か座標、申請者の順。項目名と入れ子は HLD に委ねる。`pending_match` は `""`・`same`・`different` のどれか。`pending_note` は `pending_applications` から作る表示用の文で、各申請を「{アクション} {申請日}（{年}年の表）」で書き（複数の年の表に載る申請は、年を新しい順に「・」でつないで「（2026・2025年の表）」とする）、`／` でつなぐ。並びは `pending_applications` と同じで、無ければ空文字とする。
   - ブラウザが持つ属性は `pending_return`（真偽値。バッチは全件 `false`）。同じ行に集まるフィーチャは、どれも同じ値にそろえる（除外の属性と同じ規則）。
   - 申請書から外す条件は、「`application_exclusion` が空でない、または `pending_match=same` かつ `pending_return=false`」とする。category・match_status・件数・不備ゲートは変えず、一覧・5 つの GeoJSON・ZIP・公開用ビューアには残す。
   - [FR-012](../20_SRS.md#fr-012-サミット一覧申請内容反映版生成) の一覧には、`pending_match`・`pending_note`・`pending_return` の列を足し、`pending_applications` は列にしない。一覧は人が読むもので、申請の中身は `pending_note` で足りるため。
   - 登録変更リスト由来の文字列（申請者、県名、山岳 ID など）は、どのビューアでも文字として表示し、HTML やコードとして実行しない（除外の理由と同じ扱い）。
7. **申請に戻す**: 作業用ビューアで `pending_match=same` の候補に、「申請に戻す」と「申請済みに戻す」を置く。
   - 判断は「申請に戻した記録」として、除外の台帳とは別に持つ。除外判断 JSON の別の配列で保存・読込し、新しい世代へ引き継ぐ。保存・復元の規則は、除外の台帳と同じにする。同じ世代に戻ったときの復元、「引き継がない」なら空、記録を持たない古い保存値は空、ブラウザに保存した記録が壊れていて読めないときはその記録を採用せず空として扱い、その旨と判断ファイルを読み込めば戻せることを示す、ブラウザの保存の失敗は未保存と示してメモリから JSON を書き出せる、未適用の記録を一覧から消せる、の各規則である。
   - 記録のキーは、除外の台帳と同じ（追加は座標、変更・削除は正式コードとアクション）。判断時条件は、その候補の `pending_applications` のうち「同じ内容」の申請の集合（Decision 6 の論理項目のうち、アクション、山岳 ID か座標、変更後のバンド、申請者、申請日）と、候補の出どころ（通常の候補か、担当者指定削除か）とする。集合は順序を問わない。集合か出どころが変われば、記録は未適用として残し、利用者に示す。
   - 担当者指定削除の候補: 担当者が削除申請に含めると、保持していた申請を申請ごとに評価し直し、当たり方を「同じ内容」「違う内容」にして、`pending_match` と判断時条件をその結果から作る。同じ内容の削除の申請があれば、申請済みとして外れ、その旨を示す。「要確認に戻す」では当たり方を「保持」に戻し、`pending_match` を空文字、`pending_return` を false に戻す（記録は残す）。「申請に戻す」は置き、記録の出どころを担当者指定削除にする。次の世代で同じコードが通常の削除の候補になっても、その記録は効かない。担当者指定削除そのものは毎回選び直すので、記録は、担当者指定削除を選び直したときにだけ効く。
   - 引き継ぐ理由: 申請を増やす判断だが、バッチが付けた既定（外部の申請に基づく）を担当者が覆すもので、却下された申請のように、解析をやり直しても変わらない判断である。判断時条件が同じ申請の集合を求めるので、別の申請や、内容の変わった申請には効かない。[§8.2.2](../20_SRS.md#822-localstorage-編集内容詳細仕様) の「申請を増やす判断は毎回選び直す」の原則の例外として書く。
8. **親子**: 申請済みで外れた追加の候補に従属する削除の候補は、保留にしない（除外の `parent_add` と違う）。申請書には残し、作業用ビューアで「親の追加は申請済み（{申請日}）。この削除の根拠の文は申請書に無い追加を指す」と示し、エクスポートの警告で件数を知らせる。根拠の文の書き換えは担当者に任せる。根拠の文は担当者が直せる項目で、自動で書き換えると担当者の編集とぶつかるためである。申請の取りこぼしの方が重いので（[ADR-URD-029](ADR-URD-029-pending-applications-in-matching.md) の Consequences）、保留にしない。
9. **示し方**: 作業用ビューアに「登録変更リスト」の欄を置き、採ったファイル名、年の表ごとの Update の日付、知らせる行（読めない行、SOTA サミットリストに無い ID の行、当たらなかった追加の申請、Update の日付が読めない年の表）を一覧で示す。知らせる行の論理項目は、種類、理由、年の表、その表の中の申請の行の通し番号（見出しの後の 1 から）、アクションの欄の値、山岳 ID か県名、申請者、申請日、問題の値。並びはファイルの中の順とする。バッチのログにも件数と行を警告で出す。どれも止めない（不備ゲートに足さない。不備の種類は、持ち主の確認の後にだけ足す規則のため）。
   - 作業用ビューアは、申請済みと内容の違う申請の候補に、`pending_note` と、`pending_applications` の申請者を示す。内容の違う申請だけがある候補（`pending_match=different`）には、申請済みの印とは別の印「申請あり（内容が違う）」を、作業用でも公開用でも付ける（2026-10-19 に持ち主が決めた。申請書から外れていないことが分かる見た目にする）。
   - 公開用ビューアは、申請済みの候補に、印と `pending_note`（申請者を含まない）と出典を示し、メタデータ表示に登録変更リストの年の表ごとの Update の日付を示し（2026-10-19 に持ち主が決めた。申請済みの印の鮮度を閲覧者が確かめられるようにするため）、申請者は示さない（持ち主の判断 4）。申請エビデンス ZIP の GeoJSON では、`pending_applications` の申請者を空文字にする（持ち主の判断 6、2026-10-19。ZIP の GeoJSON は利用者が公開用データとして置くので、公開用ビューアに出さないと決めたものを、公開用データになるファイルにも残さない。申請者は元のページで公開済みなので、必要なら元のページで確かめられる）。作業用ビューアのブラウザの状態と、申請に戻した記録の判断時条件には、申請者を使い続ける（ZIP は読み戻さない）。公開用ビューアの「全データ」でも、`pending_applications` の申請者は示さない。公開用ビューアには、「申請済みを含む」の表示の切り替え（初期は ON）を置く。申請に戻した候補は、申請済みの印を付けず、申請に戻したことを示す。知らせる行は、担当者の作業の材料なので、公開用ビューアには出さない。
10. **記録と出典**: `metadata` に `updatelist_file`（採ったファイル名）、`updatelist_updates`（年の表ごとの年と Update の日付）、`updatelist_notices`（知らせる行）を残す。公開用のデータ（申請エビデンスの GeoJSON）に複製する `metadata` には、`updatelist_file` と `updatelist_updates` だけを入れ（公開用ビューアが Update の日付を画面に示すため、また公開用データだけで、どの登録変更リストに基づく申請済みかを後から確かめられるようにするため）、`updatelist_notices` は入れない。[NFR-003](../20_SRS.md#nfr-003-再現性決定論的出力) の入力条件に、登録変更リストのファイルを足す。作業用ビューアの「登録変更リスト」の欄と、公開用ビューアの申請済みの表示に、出典（「山岳データ登録変更リスト（ジオサミットでひとこえ）」と入手の入口の URL）を示す。[UR-011](../10_URD.md#ur-011) は国土地理院の出典の要求なので、これは [UR-011](../10_URD.md#ur-011) の追従ではなく、申請済みの根拠を見る人が確かめられるようにするためである。
11. **整数の設定値の上限**: SRS 2.2.1 の許容範囲に上限を書いていない整数の項目は、18 桁までとする。LLD 2.1.2 の実装（19 桁以上を拒む）の上限に合わせる。運用で意味のある値は、どれも遥かに小さい。この ADR の主題とは別の決定だが、同じ SRS の改訂で入れるので、ここに記録する（ゲート 3 の条件の消化）。
12. **追従のずれ**: HLD・IT・ST・LLD が追従するまでのずれを、意図して許す。ST の UR カバレッジ表は、[UR-003](../10_URD.md#ur-003) の行の FR の一覧だけを直し、ケースは ST の追従で足す。

## Alternatives

- **(A) 申請者が整えた CSV を入力にする**: 持ち主が 2026-10-19 に、ページをそのまま読むと決めたので採らない。
- **(B) 申請に戻す判断を毎回選び直す**: 持ち主が 2026-10-19 に、引き継ぐと決めたので採らない。
- **(C) `application_exclusion` に新しい値（`pending`）を足す**: 除外の理由・台帳と混ざる。[ADR-URD-029](ADR-URD-029-pending-applications-in-matching.md) の Decision 5 の最後の論点にある、除外と混ぜない方針に反する。
- **(D) バッチが申請済みの候補を出力から外す**: [ADR-SRS-050](ADR-SRS-050-persistent-exclusion-decisions.md) が「バッチが判断ファイルを読み候補を消す」案を却下したのと同じく、エビデンスと不備の検出から対象を隠す。この ADR では、バッチは候補を消さず、外すのは申請書だけとする。
- **(E) 反映済みの目印の行で、反映済みを判定する**: 目印は 1 行だけで、2026 年の表に無い。版の区切りの日付をツールに持たせると、次の版で直す必要が出る。
- **(F) 当たらない行を不備ゲートに足す**: 1 行の誤記で全体が止まる。
- **(G) 申請の情報を表示用の文だけで持つ**: 申請に戻した記録の判断時条件と、担当者指定削除の判定し直しに要る項目が無くなる。

## Consequences

- SRS の改めた節は、[2.2.1](../20_SRS.md#221-設定可能項目)、[3.1](../20_SRS.md#31-システムコンテキスト)、[3.2](../20_SRS.md#32-主要コンポーネント構成)、[3.4](../20_SRS.md#34-外部システム依存関係環境)、[3.5](../20_SRS.md#35-制約前提条件)、[FR-023](../20_SRS.md#fr-023-解析パイプライン制御) の入力の表、[FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定)、[FR-011](../20_SRS.md#fr-011-申請書-xlsx-生成)・[FR-012](../20_SRS.md#fr-012-サミット一覧申請内容反映版生成)・[FR-019](../20_SRS.md#fr-019-html-ビューア機能仕様)・[FR-020](../20_SRS.md#fr-020-公開用ビューア配信)・[FR-021](../20_SRS.md#fr-021-申請エビデンス-zip-生成)、[NFR-003](../20_SRS.md#nfr-003-再現性決定論的出力)、[§6.2](../20_SRS.md#62-外部if詳細仕様) の外部 I/F の定義、[§7.1](../20_SRS.md#71-ユーザー入力一覧) と新しい 7.2.9、[§8.1](../20_SRS.md#81-内部データ一覧)・8.2.2・新しい 8.2.4、[§10](../20_SRS.md#10-要求追跡マトリクス)、用語集、[SOURCES](../../ref/SOURCES.md#山岳データ登録変更リスト)である。SOURCES の節は、入力のファイルの節（summitslist.csv などと同じ並び）へ移した。
- HLD（統合・突合 CMP5 の入力とデータフロー、2.3.1 の置き場を固定した入力の列挙、4.23.2 の起動前提条件、CMP7・CMP8）、IT、ST、LLD（5.1・5.2・6.12、CMP5・CMP7・CMP8 の章）の追従が残る。設定のキーは増えない（HLD 2.3.1 の「SRS §2.2.1 の 10 件」は変わらない）。HLD 2.3.3 に整数の上限の文を足すことは、HLD の字句の直しで行う。
- 既知の限界: 却下された申請と、管理者が標高を直して反映した変更の申請（例: 申請はバンド X、登録はバンド Y で、解析がバンド X への変更の候補を出す）は、表に状態の列が無いので、「申請済み」に見え続ける。担当者が申請に戻し、その記録が引き継がれることで扱う。
- 反映された追加の登録が後に廃止され、古い追加の行が入力ページに残り、同じ場所が再び追加の候補になると、完了した申請が再申請を既定で外す。廃止履歴による自動判定は行わず（[7.2.4](../20_SRS.md#724-sota-サミットリスト-csv) が廃止履歴だけで自動除外しない方針）、担当者が申請に戻す。
- 座標の精度が低い追加の申請が、AZ の少し外に落ちると、当たらず、二重申請の候補が黙って残る。当たらなかった追加の申請を、利用者に一覧で示すことで扱う。
