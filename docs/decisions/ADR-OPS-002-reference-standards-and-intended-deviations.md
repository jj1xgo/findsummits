# ADR-OPS-002: 開発文書とプロセスが参照する国際規格と、意図して外す点

| 項目 | 内容 |
|---|---|
| 状態 | 採用・実装済み |
| 決定日 | 2026-10-07 |

## Context

開発文書（[URD](../10_URD.md)・[SRS](../20_SRS.md)・[HLD](../30_HLD.md)・[テスト方針書](../02_test_policy.md)・[ST](../70_ST.md)・[開発ガイド](../03_development.md)・[文書管理ルール](../CLAUDE.md)）は、開発プロセスや文書の構成の国際規格を、どれも名指ししていない。名指ししている規格は、日付の ISO 8601、GeoJSON の RFC 7946、座標系の EPSG、通信の RFC 7231 のような、データ形式・座標系・通信・数値表現の規格だけである。

持ち主は 2026-10-07 に、開発とドキュメントを国際標準に沿わせる方針を示した。あわせて、規格の本文は購入せず、「参照」として進めると決めた。

参照する規格と版を先に決めないと、文書を直すたびに別の規格や別の版を拠り所にしてしまう。また、今の文書とプロセスには、規模に合わせて規格の構成と違う形にしている点がある。理由が記録に無いと、後で規格と照らしたときに欠落と取り違える。

## Decision

1. **規格に対して「参照」と書き、「準拠」と書かない**: 本プロジェクトは規格の本文を持たない。公開の目録、規格の範囲（Scope）の記述、無料で読める資料で分かる範囲で、文書の構成と用語を規格に合わせる。これを「参照」と呼ぶ。規格の要求をすべて満たすと主張する「準拠（conformance）」は、開発プロセスと文書の構成のどの規格にも宣言しない。本 ADR の対象は開発プロセスと文書の構成の規格で、データ形式・座標系・通信・数値表現の規格（ISO 8601、RFC 7946、EPSG など）と、規格以外の文書や規則に従う意味の「準拠」（[FR-011](../20_SRS.md#fr-011-申請書-xlsx-生成) 準拠など）は対象外とする。
2. **参照する規格と版**: 次の表の版を参照する。目録の URL と確認日は [SOURCES「開発プロセスの参照規格」](../../ref/SOURCES.md#開発プロセスの参照規格)に置く。

   | 対象 | 規格 | 版 |
   |---|---|---|
   | プロセス全体 | ISO/IEC/IEEE 12207 | 2026 |
   | 要求（URD を利害関係者要求仕様（StRS: Stakeholder Requirements Specification）、SRS をソフトウェア要求仕様として扱う） | ISO/IEC/IEEE 29148 | 2018 |
   | 設計（HLD） | ISO/IEC/IEEE 42010 | 2022 |
   | テスト | ISO/IEC/IEEE 29119-1・29119-2・29119-3 | 29119-1 は 2022、29119-2 と 29119-3 は 2021 |
   | 非機能要求の分類 | ISO/IEC 25010 | 2023 |
   | 用語（補助） | ISO/IEC/IEEE 24765 とそのオンライン版の SEVOCAB | 24765 は 2017。SEVOCAB は版を固定しない |
   | テスト（補助） | ISTQB（International Software Testing Qualifications Board）の CTFL（Certified Tester Foundation Level）シラバスと ISTQB 用語集 | シラバスは v4.0.1。用語集は版を固定しない |

3. **意図して保つ形（規格と違いうる点）**: 次の 9 点は、今の形を意図して保つ。ISO の規格の本文を持たないので、ISO の規格と本当に違うかは確かめきれていない（CTFL シラバスは原文を読める）。「照らした資料」に何と照らしたかを、「確認の程度」にどこまで確かめたかを書く。「確認の程度」が「未確認」で始まる行（5〜9 行目）は、規格と違うと決めたものではなく、Decision 4 の保留にあたる。

   | 今の形 | 照らした資料 | 確認の程度 | 理由 |
   |---|---|---|---|
   | 文書ごとの「参照資料」の節を作らない（[文書管理ルール「ドキュメントフォーマット標準」](../CLAUDE.md#ドキュメントフォーマット標準)） | 29148:2018 に基づくとする公開の SRS の雛形（[SOURCES「開発プロセスの参照規格」](../../ref/SOURCES.md#開発プロセスの参照規格)の二次資料）の、序論の References の節 | 二次資料の要約（2026-10-07、Web 検索の結果）。規格の本文では未確認 | 出典は [SOURCES](../../ref/SOURCES.md) に 1 か所でまとめ、本文はインラインの注記で指す。文書ごとに一覧を持つと、同じ出典の書き方が文書の間で食い違う |
   | ヘッダーに版数を持たない（同じ節） | 同じ雛形の、版を含む文書の識別（Document Identification） | 同上 | 版と変更の履歴は git が持つ |
   | 受け入れテストを独立のテストレベルにせず、ST の第 2 部（URD の妥当性確認）で行う（[ADR-ST-001](ADR-ST-001-two-part-st-no-separate-at-family.md)） | CTFL シラバス v4.0.1 の 2.2.1（Test Levels）。受け入れテスト（acceptance testing）をシステムテストと別のテストレベルにする | シラバスの原文で確認（2026-10-08。2.2.1 は 5 つのテストレベルを挙げ、受け入れテストを別のレベルにしている）。それまでは istqb.org に限定した Web 検索の要約（2026-10-07）だった | 個人開発の規模では、ST と似たシナリオを別に保つ手間が見合わない（ADR-ST-001 の理由） |
   | IT の外部結合に、コンポーネントどうしのつなぎ目と、システムの外とのつなぎ目の両方を入れる（[ADR-HLD-001](ADR-HLD-001-program-structure-chapter-and-two-tier-it.md)） | 同じ 2.2.1。component integration testing と system integration testing を別のテストレベルにする | シラバスの原文で確認（2026-10-08。2.2.1 は 2 つを別のテストレベルとして挙げている） | 外部結合のつなぎ目は、システムの外とのものも含めて、[HLD 第 3 章](../30_HLD.md#3-プログラム構造)の各コンポーネントの節の同じ表で管理する。システムの外とのつなぎ目だけを別のテストレベルにする利点が無い |
   | 欠陥管理とレビューの手順のうち、道具に依る手順と個人の運用（[ADR-OPS-004](ADR-OPS-004-scope-of-public-defect-and-review-rules.md) の Decision 2 に挙げたもの）を、公開の文書でなく、メンテナ個人の運用の補足に置く（[`AGENTS.md`「個人運用の補足」](../../AGENTS.md#個人運用の補足)） | 12207 のプロセスの記述 | 未確認（12207 が公開の範囲について何を求めるかを確かめていない） | 個人の運用で変わりやすい手順を、公開の規則と分けている。道具に依らない骨格は [開発ガイド §7](../03_development.md#7-課題とレビュー) に置いた |

4. **規格との違いを見つけたとき**: 根拠の資料と適用の範囲を確かめ、次のどれかに決める。直す。意図して外すなら、上の表に行を足す。根拠を確かめられないなら、確かめられないことを記録して保留する。確かめていない違いを欠陥と決めつけない。
5. **版を改めるとき**: 発行元（ISO・ISTQB）の目録で新しい版を確かめたら、採るかを決める。採るなら、上の表の各行への影響を確かめてから、版の表と SOURCES を改め、改めた日と中身を Consequences の末尾に 1 行で追記する。

## Alternatives

- **(a) 規格の本文を購入して「準拠」を宣言する**: 準拠を確かめる手間と費用が個人開発の規模に見合わず、持ち主が 2026-10-07 に不採用とした。
- **(b) 規格を名指しせず、一般的な慣行に合わせるとだけ書く**: 拠り所が文書ごとにぶれる。規格と照らして欠落を見つける手がかりにもならないため不採用。
- **(c) 版を書かず、規格の番号だけにする**: 12207 は 2026 年に改訂され、29148 と 24765 も改訂が進んでいる。版が無いと、どの版の構成に合わせたのかを後から追えないため不採用。
- **(d) 外す点を各文書の中に注記する**: 外す点が文書にまたがり、一覧で見られない。新しく外す点を足す場所も決まらないため不採用。

## Consequences

- [SOURCES「開発プロセスの参照規格」](../../ref/SOURCES.md#開発プロセスの参照規格)に、各規格の題・目録の URL・確認日を置く。
- [用語集「参照規格」](../00_GLOSSARY.md#参照規格)に「参照」と「準拠」の意味を置き、本 ADR を指す。
- [文書管理ルール「参照する規格」](../CLAUDE.md#参照する規格)に、文書の構成と用語を本 ADR の規格に合わせることと、規格との違いの扱いを置く。
- 規格と照らして見つかった欠落は、本 ADR の決定に従って個別に扱う。本 ADR の時点では、既存の要求・設計・テスト仕様の内容は変えていない。
- 2026-10-08: Decision 3 の表の 5 行目を、道具に依る手順と個人の運用だけを個人の補足に置く形に狭めた（[ADR-OPS-004](ADR-OPS-004-scope-of-public-defect-and-review-rules.md)）。
- 2026-10-08: Decision 3 の表に、要求に優先度と根拠の属性を持たせない 2 行（6・7 行目）を足した（[ADR-SRS-070](ADR-SRS-070-requirement-verification-section.md)）。
- 2026-10-08: Decision 3 の表に、テスト計画と報告を別の文書にしない 1 行（8 行目）を足した（[テスト方針書 1](../02_test_policy.md#1-目的位置づけ)・[5.5](../02_test_policy.md#55-テスト結果の記録)）。
- 2026-10-08: Decision 3 の表の 8 行目の確認の程度を、テスト方針書 1 の対応表を CTFL シラバス v4.0.1 の 5.1.1 の原文と照らした結果に改めた。29119-3 の文書の構成は未確認のまま。
- 2026-10-08: Decision 3 の表の 3・4 行目の確認の程度を、CTFL シラバス v4.0.1 の 2.2.1 の原文と照らした結果に改めた。規格がどうしているかの記載は原文どおりで、今の形を保つ判断は変えていない。
- 2026-10-09: Decision 3 の表に、テストレベルを略語 UT・IT・ST で呼ぶ 1 行（9 行目）を足し、書き出しの点の数と保留にあたる行の範囲を改めた（[文書管理ルール「ドキュメントフォーマット標準」](../CLAUDE.md#ドキュメントフォーマット標準)）。
