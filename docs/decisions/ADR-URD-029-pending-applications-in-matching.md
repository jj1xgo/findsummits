# ADR-URD-029: SOTA 日本支部に申請済みで未反映の申請を突合の入力にし、重なる候補を申請済みとして扱う

| 項目 | 内容 |
|---|---|
| 状態 | 採用・未実装 |
| 決定日 | 2026-10-19 |

---

## Context

2026-10-09 に、SOTA 日本支部に申請済みで承認待ちの申請を突合で考慮するかを検討し、仕様は変えず、担当者が除外判断（[UR-015](../10_URD.md#ur-015)）で手で外すと決めた。理由は、山岳データ登録変更リスト（[SOURCES](../../ref/SOURCES.md#山岳データ登録変更リスト)）の書式が揃っていないこと、入力に使ってよいか確かめていないこと、実害が年に数件の追加に収まることだった。見直す条件は、座標変更の扱い（[ADR-URD-025](ADR-URD-025-coordinate-change-stays-out-of-scope.md)）を決めること、入力に使ってよいかと入手の経路を確かめること、確かめた結果で入手の手順などを決めて ADR にすることだった。

2026-10-19 に確かめると、前提が崩れていた（[調査資料](research/pending-applications-in-update-list-2026-10.md)）。

- 登録変更リストの 2026 年の表（2026-10-14 更新）に、追加が 162 件ある（158 件が 2026-09 の申請）。2026-10-18 の SOTA サミットリストと座標を突き合わせると、対応する登録を見つけられなかったので、未反映と推定する。159 件は、1 km 以内に現役の JA のサミットが無い。残る 3 件は既存のサミットの近く（166〜656 m）にあり、別の山か同じ山の座標違いかを確かめていない（確認保留）。標高の変更も、6 件のうち 5 件は、SOTA サミットリストの標高が変更前のままだった。
- 過去の反映は、2025-07-01 と 2026-07-01 の版にまとまって入っていた（ほかの日付の版もあった）。次の 7 月 1 日の版（2027-07-01）まで入らない見込みで、ほかの日付の版でそれより前に入る可能性は否定できない。それまでの解析では、申請済みのサミットが新規の候補（`new`）として出て、二重に申請される。
- 持ち主が 2026-10-19 に、登録変更リストは公開のページなので入力に使ってよく、ジオサミットでひとこえの SOTA のページから必ずリンクされるので安定して入手できる、と確かめた。座標変更の扱いは ADR-URD-025 で決着している。

## Decision

1. 山岳データ登録変更リストを、突合の入力にする。利用者が入手して配置する参照データとし、ツールは自動取得しない。入手の入口は、ジオサミットでひとこえの SOTA のページ（<https://little-ctc.com/sota_hp/>）とする。年ごとのページの URL は変わりうるが、このページからリンクされる。
2. [UR-003](../10_URD.md#ur-003) を広げる。申請済みで現行 SOTA リストに未反映の申請のうち、候補と同じ対象で同じ内容のもの（追加は同じ山頂、削除は同じサミット、変更は同じ変更後のバンド）がある候補は、申請済みとして識別し、既定で申請から外し、作業用ビューアで区別して示し、担当者が申請に戻せる。同じ対象で内容の違う申請（例: 申請はバンド 3 から 5、解析は 3 から 4）がある候補は、申請から外さず、作業用ビューアでその申請があることを示す（持ち主の判断、2026-10-19。正しい変更を出す機会を逃さないため）。
3. 取り込む申請は、追加・削除と、[UR-003](../10_URD.md#ur-003) のバンドをまたぐ標高変更とする（持ち主の判断、2026-10-19。削除も、未反映のままだと二重に申請しうる。2024〜2026 年の 3 年分で削除の行は 15 行ある）。名称・座標・同じバンドの中の標高の変更は、[URD §6](../10_URD.md#6-スコープ外対象外) のスコープ外のままとする。
4. 新しい UR を足さず、[UR-003](../10_URD.md#ur-003) に入れる（計画者の判断）。突合の相手を広げて候補の識別を変えるもので、[UR-003](../10_URD.md#ur-003) と同じ関心事だからである。[ADR-URD-022](ADR-URD-022-split-ur-006-into-geojson-and-two-viewers.md) の Decision 1 の分割の基準（成果物が異なる複数の要求を含み、実現する FR/NFR の集合が違うときに分割する。1 つの成果物に条件が付くだけなら分割しない）に当てると、候補の識別という同じ成果物に条件が付いたものなので、分割しない。あわせて、要求の決定を先に記録し、SRS 以下の追従を、この ADR に記録したずれとして段階的に進められる。
5. SRS 以下で決めることを、次のとおり挙げる（ここでは決めない）。
   - 入力の形（申請者が表から整えた CSV か、ページを直接読むか）と、読めない行の扱い
   - どの年の表を入力にするか（年をまたいで未反映のまま残る申請がある）
   - 表に状態の列が無い中で、未反映をどう見分けるか。未反映かどうかを別に判定する仕組みは設けず、候補との照合の条件で見分ける（反映済みの追加は既存サミットとして突合されるので、追加の候補と重ならない。反映済みの削除は廃止済みの登録になり、突合から外れる。反映済みの変更でも、標高のバンドが違えば変更の候補になりうる）。照合の条件は、アクションごとに SRS で決める（追加は AZ に申請の座標が入るかで当てる案）
   - 変更をどう当てるか（山岳 ID と変更後のバンドで当てる案）
   - 山岳 ID の表記の違い（`JA8/IS-024` など）と、現行 SOTA リストに無い ID の行の扱い（読めても当たらない行は、黙って二重申請につながるので、利用者に示すか）。SOTA サミットリストに無い ID（表記の違い・誤記）と、廃止済みの ID（反映済みの削除とみなせる。SOTA サミットリストは廃止済みの登録も含む）は分けて扱う
   - 却下された申請や、座標を直して反映された申請の扱い
   - 同じ対象に複数の申請がある場合
   - 申請の追加が、既存サミットの近く（アクティベーションゾーンの中など）にある場合（2026 年の表に 3 件ある）
   - 申請に戻す判断を判断ファイルに残すか
   - 入力の版と出典の記録（[NFR-003](../20_SRS.md#nfr-003-再現性決定論的出力)。[UR-011](../10_URD.md#ur-011) は国土地理院の出典の要求で、登録変更リストの出典を成果物に示すかは別に決める）と、入力の更新日（表の Update の日付）を利用者に示すか（利用者が入力を更新していないと、この機能が黙って効かなくなる）
   - 公開用ビューア（[UR-018](../10_URD.md#ur-018)）で、申請済みとして申請から外した候補をどう示すか（公開用ビューアは申請エビデンスの GeoJSON を表示し、除外の状態と理由も示す）
   - [UR-015](../10_URD.md#ur-015) の除外判断との関係（申請済みで外すのは、担当者の除外判断とは別の既定で、除外の理由や台帳と混ぜない）。[ADR-SRS-050](ADR-SRS-050-persistent-exclusion-decisions.md) は「バッチが判断ファイルを読み、候補を消す」案を、解析結果と申請判断の混同として却下した。申請から外した候補を、エビデンスと不備の検出に残すか（解析結果と申請判断を混ぜないか）を決める
6. URD が SRS より先に進む期間のずれを、意図して許す。SRS・HLD・ST が追従するまで、SRS の [FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) などは登録変更リストを読まない。

## Alternatives

- **(A) 仕様を変えず、除外判断で手で外す**: 2026-10-09 の判断。追加が 160 件を超える規模では、手間が大きく、外し忘れも出る。
- **(B) ビューアに重ねて表示するだけにする**: 申請書から外れないので、二重申請を防げない。
- **(C) ツールが出した申請を判断ファイルに残し、次回から抑止する**: 他の申請者の申請を覆えない。今回の分はほとんどが他の申請者による。
- **(D) 新しい UR を足す**: 突合の相手を広げる変更で、[UR-003](../10_URD.md#ur-003) と同じ関心事のため、Decision 4 のとおり採らない。
- **(E) 同じ対象への申請があれば、内容が違っても外す**: 内容が違う場合に、正しい変更を出す機会を逃す。持ち主が 2026-10-19 に採らないと判断した。

## Consequences

- URD の [UR-003](../10_URD.md#ur-003)、[§3.1](../10_URD.md#31-ステークホルダー)、[§3.3](../10_URD.md#33-運用の流れ)、[§5](../10_URD.md#5-前提制約)、用語集、[SOURCES](../../ref/SOURCES.md#山岳データ登録変更リスト) を改めた。
- 追従する文書は次のとおり。
  - SRS: [2.2.1](../20_SRS.md#221-設定可能項目)（入力のファイルを指定するなら）、[3.5](../20_SRS.md#35-制約前提条件)、[7.1](../20_SRS.md#71-ユーザー入力一覧)、7.2 の入力の定義、[FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定)、[FR-011](../20_SRS.md#fr-011-申請書-xlsx-生成)・[FR-012](../20_SRS.md#fr-012-サミット一覧申請内容反映版生成)・[FR-019](../20_SRS.md#fr-019-html-ビューア機能仕様)・[FR-020](../20_SRS.md#fr-020-公開用ビューア配信)・[FR-021](../20_SRS.md#fr-021-申請エビデンス-zip-生成)、[§6](../20_SRS.md#6-外部インターフェース仕様) の外部 I/F の定義（突合済み GeoJSON・サミット一覧 XLSX・申請書 XLSX など。判断ファイルに保存するなら 6.2.10 も）、§8・§9・§10。上の各 FR の「対応 UR」の宣言に [UR-003](../10_URD.md#ur-003) を足す
  - HLD: 統合・突合（CMP5）の入力とデータフロー、申請書生成 UI（CMP7、HLD 3.7）の表示と申請に戻す操作、公開用ビューア（CMP8、HLD 3.8）の表示、関係する処理方式の節
  - LLD: CMP5 の突合のモジュールと、CMP7・CMP8 の関係するモジュール。書き始める前に、SRS・HLD の追従を終える
  - ST: 申請済みの判定（追加・削除・変更、同じ内容と違う内容、同じ対象に複数の申請がある場合）と、申請に戻すケース
  - SOURCES: SRS で入力の形を決めたときに、[山岳データ登録変更リスト](../../ref/SOURCES.md#山岳データ登録変更リスト)の節を入力のファイルの節（summitslist.csv などと同じ並び）へ移し、配置場所を書く
- 誤って申請から外す害（申請の取りこぼし）は、抑止し損ねる害（二重申請を管理者の側で弾く）より重い。そのため、申請済みの候補を黙って消さず、区別して示し、担当者が申請に戻せるようにする。
- ゲート 3（HLD から LLD へ）の判定の前提が変わる。承認者が、判定の結論や条件に影響するかを判断し、その旨と理由を、ゲートの記録に追記する。承認者は 2026-10-19 に、判定の結論や条件に影響すると判断した（[#311](https://github.com/jj1xgo/findsummits/issues/311)「ゲート 3 の判定への影響の判断: 未反映の申請を突合に取り込む要求の変更（#310）」）。[開発ガイド §4](../03_development.md#4-フェーズゲート) の再審査を行う。
