# ADR-SRS-068: 追加根拠（※2）に Key コルの位置を入れる

| 状態 | 採用・未実装 |
| 決定日 | 2026-10-07 |

## Context

[FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) の ※2 追加根拠フォーマットは、ピークの座標・所在地・コル標高・プロミネンスの 4 つを書き、Key コルの位置を含まなかった。コルの位置は `merged_summit.xlsx` の `col_lat`/`col_lon` と、中心データの `key_col` の点にはあるが、申請書の列 I（[FR-011](../20_SRS.md#fr-011-申請書-xlsx-生成)）だけを読む人には伝わらない。載せる意図はあったが、仕様に入っていなかった。

SOTA 日本支部の山岳データ登録変更リスト（管理者が受け付けた申請の一覧）は、新規追加の詳細に「位置・所在地・コル位置・比較SOTA-ID・コル標高・プロミネンス」の列を持つ。2026-10-07 に確認した 2026 年版の一覧では、「追加」の 18 行（同じ申請の重複を含む）はどれもコル位置の欄を記入しており、17 行は `緯度,経度` の形、1 行（東京都の申請）は「周囲は海（0m)」と書いている。

## Decision

1. ※2 の所在地の行とコル標高の行の間に、`コル位置：{col_lat},{col_lon}` の行を足す。見出しと並びは登録変更リストの列に、値の形はピークの座標の行に合わせる。
2. Key コルが海面で確定したピーク（`key_col_resolved=true` で `col_lat`/`col_lon` が 0.0）は `コル位置：海面` とする。0.0 は未確定のピークも持つ印なので、海面か未確定かは `key_col_resolved` で見分ける。
3. `key_col_resolved=false` のピークは、コル標高・プロミネンスと同じく `コル位置：未確定` とする。
4. ※5 変更根拠フォーマットには足さない。
5. 値の書き方（桁）は [HLD 4.9.2](../30_HLD.md#492-処理の流れ) で定める。

## Alternatives

**(A) 海面で確定したコルを `コル位置：周囲は海` と書く**

却下。登録変更リストの書き方には近いが、標高はすぐ下のコル標高の行にあり、この行は場所の種類だけで足りる。「海面」はビューアの「海面（0m）」とも言葉がそろう（持ち主の判断、2026-10-07）。

**(B) ※5 にもコル位置を入れる**

却下。※5 は標高を測り直してバンドが変わることを示す根拠で、コル標高もプロミネンスも持たない。コル位置だけを足すと釣り合わない。登録変更リストで変更の行にコル位置があるのは位置を変えた例で、既存サミットの位置の変更をどう扱うかは別の論点として検討する（持ち主の判断、2026-10-07）。

**(C) 「比較SOTA-ID」も入れる**

却下。同じ一覧には比較先が申請した山より低い例がある（櫛形山の位置の変更で比較先が丸山、など）。定義（親ピークか、Key コルを挟んだ隣のサミットか）が定まっていない。扱うなら管理者に用途を確かめてから別に決める。

## Consequences

- 反映先: [FR-009](../20_SRS.md#fr-009-sotaリスト突合match_status-判定) の ※2、[HLD 4.9.2](../30_HLD.md#492-処理の流れ) の「出力の組み立て」の 2、[ST](../70_ST.md) の `ST-FR-009-25`、HTML ビューアのモックアップの rationale の例と初期値。
- [FR-011](../20_SRS.md#fr-011-申請書-xlsx-生成) は rationale を列 I に転記するだけなので変えない。[FR-019](../20_SRS.md#fr-019-html-ビューア機能仕様) は初期値を ※2 から取るので、字句の変更は要らない。
- ビューアで編集した rationale は編集後の値が使われるので、前の世代で編集した根拠にはコル位置の行が足されない。
