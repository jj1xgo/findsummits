# ADR-URD-019: 公開用ビューアを申請エビデンス GeoJSON からの静的ホスティング配信に改める

| 項目 | 内容 |
|---|---|
| 状態 | 採用・未実装 |
| 決定日 | 2026-09-19 |

## Context

現行仕様（[FR-020](../20_SRS.md#fr-020-公開用ビューア配信)・[6.2.7](../20_SRS.md#627-公開用ビューア閲覧専用静的ホスティング配信)）は、
作業用ビューアの「公開用 HTML」ボタンで閲覧専用 HTML を 1 ファイルとしてダウンロードし、持ち主が
GitHub Pages 等の静的ホスティングへ手で配置する方式だった。この方式では次の 3 点を満たせない。

1. **リリース版と開発版の並置**: 手で 1 ファイルを配置する運用では、確定した解析結果（main）と
   開発中の解析結果（devel）を同じ公開先に同時に置き分ける手段が仕様上定義されていない。
2. **公開物と申請物の同一性**: 公開用 HTML は作業用ビューアがその都度生成するもので、
   [申請エビデンス ZIP](../20_SRS.md#fr-021-申請エビデンス-zip-生成) に同梱される GeoJSON とは別の生成経路をたどる。
   両者が同一内容であることを構造的に保証する仕組みがない。
3. **モックアップを本番に近づける手段**: `docs/mockup/viewer_mockup.html` は UI 確定用のプロトタイプ
   （[`docs/CLAUDE.md`](../CLAUDE.md)「モックアップの扱い」）だが、本番の作業用ビューアとはデータの
   埋め込み方式が異なり、テンプレートを共用してデータだけ差し替える構成になっていない。

静的ホスティングが公開用ビューアを配信するには、ブラウザの `localStorage` を実行時に読めないため、
編集済みデータをあらかじめリポジトリに置く経路が必要になる。申請エビデンス ZIP には既に編集反映済みの
分類別 GeoJSON 5 本（`add` / `delete` / `band_change` / `no_change` / `review`）が同梱されているため、
この GeoJSON をそのまま公開用データとして配置すれば、新しい生成経路を増やさずに済む。

**ホスティングの事実（2026-09-19 時点の公式ドキュメントの要旨）**:

- **GitHub Pages**: 公開元は 1 リポジトリにつき 1 サイトで、任意の 1 ブランチのルートか `/docs` フォルダ、
  または GitHub Actions のいずれかを選ぶ（複数ブランチを同時に公開元にはできない）。Actions 方式であれば
  ワークフローが複数ブランチを読み込んでサイトを組み立てられる。サイトを非公開にできるのは
  GitHub Enterprise Cloud の組織のみで、個人・Free/Pro/Team のリポジトリでは Pages サイトは常に公開になる。
- **Cloudflare Workers（静的アセット配信）**: Git 連携で本番ブランチへの push が本番デプロイになり、
  非本番ブランチのビルドを有効にするとブランチごとに固定のプレビュー URL が自動生成される（プレビュー URL は
  常にそのブランチの最新コミットを指す）。Cloudflare Access を使えばプレビュー URL（必要なら本番 URL も）に
  ログインを要求できる。静的アセットの配信はリクエスト数・転送量とも無料・無制限。

どちらのサービスを使うかは HLD で決める（本 ADR・SRS では固定しない）。

## Decision

1. 公開用ビューアは、作業用ビューアの「申請エビデンス」ZIP に同梱される分類別 GeoJSON 5 本
   （編集反映済み）をリポジトリの公開用データ置き場に配置し、静的ホスティングがテンプレートと
   合わせて配信する。配置した 5 本は、ファイル名を変えず内容を改変せずに配信される
   （配置したファイルとバイト単位で同一）。
2. 作業用ビューアの「公開用 HTML」ボタンは廃止し、エクスポートは「申請書」「申請エビデンス」の
   2 つにする。GeoJSON の出口を申請エビデンス ZIP の 1 系統に絞ることで、編集済み GeoJSON を
   別ボタンで単独ダウンロードする経路（2 系統）を持たず、公開物と申請物の同一性確認を構造的に不要にする。
3. リリース版（main、タグ付き）と開発版（devel）を同時に公開でき、閲覧者がどちらかを判別できる
   （判別手段は URL と画面表示。詳細は HLD）。`metadata.software_version`（[ADR-OPS-001](ADR-OPS-001-semver-tagging-and-release-versioning.md)）は
   解析ソフトウェアの版として画面に併記するが、公開区分そのものの判別手段ではない。
4. 配信サービス（GitHub Pages・Cloudflare Workers 等）・組み立て手順・公開用データ置き場のパス・
   プレビューのアクセス制限は SRS に固定せず、HLD と運用手順で決める。
5. 作業用ビューアとモックアップはローカルで開く用途に限り、ホスティングしない。
6. 作業用ビューア（[FR-013](../20_SRS.md#fr-013-html-ビューア生成)）は「固定テンプレート HTML + 別ファイルのデータ
   （`merged_viewer_data.js`）」の 2 ファイル構成に改める（従来の GeoJSON 埋め込み方式から変更）。
   これにより、モックアップ・作業用ビューア・公開用ビューアが同じテンプレート構成を使い、
   データファイルだけを差し替えてモックアップを本番に近づけられる。データファイルの内部形式・
   `file://` での読み込み機構は HLD で実測して決める。

## Alternatives

- **(a) 現状維持（手で配置）**: リリース版と開発版の並置ができず、公開物と申請物の同一性を
  保証する仕組みもない。採用しない。
- **(b) 編集済み `merged_summit.geojson` を単独ダウンロードするボタンを新設**: 申請エビデンス ZIP と
  合わせて GeoJSON の出口が 2 系統になり、両者が食い違っていないかの確認が別途必要になる。
  出口を 1 系統に絞る利点が失われるため採用しない。
- **(c) 公開用 HTML を ZIP に同梱**: 出口は 1 系統になるが、依然として手で配置する運用のままで、
  リリース版と開発版の並置ができない。採用した GeoJSON 直接配信方式に合わせ、HTML の同梱は採らない。
- **(d) 作業用ビューアもホスティングする**: 編集前の `merged_summit.geojson` をもう 1 系統
  リポジトリに置く必要が生じ、手元とサイトで `localStorage` の状態が分かれて混乱を招く。
  作業用ビューアはローカル専用という決定 5 と矛盾するため採用しない。
- **(e) GitHub Pages を SRS に固定する**: GitHub Pages は 1 リポジトリ 1 サイトの制約があり、
  開発版の非公開化は GitHub Enterprise Cloud の組織に限られる。持ち主の希望（開発版を区別して
  公開しつつ非公開にする余地を残す）を満たせるサービスは他にもあり得るため、サービス選定は
  HLD に委ね、SRS では固定しない。
