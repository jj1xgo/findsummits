# ADR-OPS-005: テスト文書の「確定」を仕様の確定とし、テストのコードとの照合（T5）をテストのコードがそろった段から効かせる

| 項目 | 内容 |
|---|---|
| 状態 | 採用・実装済み |
| 決定日 | 2026-10-15 |

---

## Context

テスト文書（単体テスト仕様書 `docs/50_UT.md`、結合テスト仕様書 `docs/60_IT.md`、システムテスト仕様書 `docs/70_ST.md`）のヘッダーの「ステータス」は、ほかの文書と同じ「ドラフト / 確定」の 2 値で（[文書管理ルール「ドキュメントフォーマット標準」](../CLAUDE.md#ドキュメントフォーマット標準)）、テスト文書の「確定」が何を表すかは書かれていなかった。

`tools/lint_trace.py` は、段を `CONFIRMED_STAGES` に入れると、その段の T3（上位の要素にケースが無い）と T5（自動のケースを実装したテストのコードが無い、テストのコードがどのケースも名乗っていない）を同時に効かせていた（[ADR-URD-020](ADR-URD-020-requirement-traceability-and-consistency.md) の Decision 4「T3 と T5 は、下位の段がフェーズゲートを通った後に効かせる」）。[開発ガイド §4](../03_development.md#4-フェーズゲート) は、ゲートの判定が Go か条件付きGo なら段を `CONFIRMED_STAGES` に足すとしていた。

テスト文書は、テストの基になる文書に対応し（[テスト方針書 §1](../02_test_policy.md#1-目的位置づけ) の V 字の対応）、このプロジェクトでは ST を SRS の段、IT を HLD の段で書いた。ケースの中身と上位の文書との対応は設計の段で確かめられるが、テストのコードは製品のコードを書く段（COD）で書くので、それより前にはそろわない。2026-10-15 の版（`2137df8`）で試すと、IT を `CONFIRMED_STAGES` に入れると T5 が 113 件、ST を入れると 287 件出て、T3 はどちらも 0 件だった。このままでは、テスト文書の中身をそろえても、テストのコードを書くまで段を確定にできない。

[テスト方針書 §5.6](../02_test_policy.md#56-開始基準) は、正式な実行の開始基準に、テスト文書のステータスが「確定」であることを入れている。実行の途中で期待値の根拠が変わらないようにするためで、ここで要るのはケースの中身の確定である。正式な実行には自動のケースのテストのコードがそろっていることも要るが、開始基準には書かれていなかった。

ゲート 3（HLD → LLD、2026-10-14）の判定は条件付きGo で、条件の 1 つが、テスト文書のステータスを仕様の確定と実行の段に分ける計画を次のゲートまでに立てることだった（[#247](https://github.com/jj1xgo/findsummits/issues/247)）。持ち主が 2026-10-15 に次のとおり決めた。

## Decision

1. **ステータスの値**: テスト文書のヘッダーのステータスは「ドラフト / 確定」の 2 値のままにする。テスト文書の「確定」は仕様の確定で、ケースの中身（前提条件・手順・期待結果・合否判定基準）と上位の文書との対応がそろったことを表す。ソフトウェア要件仕様書（SRS）や概要設計書（HLD）の「確定」と同じ意味で、テストのコードがそろったことは含めない。
2. **`CONFIRMED_STAGES` に足す時機**: テスト文書の段（UT・IT・ST）は、ゲートの判定ではなく、承認者（メンテナ）がテスト文書の確定を認めてヘッダーのステータスを「確定」にする変更で `CONFIRMED_STAGES` に足す。足す前に、[7.3](../03_development.md#73-レビュー) の多視点のレビューで Critical・Important の指摘が残っていないこと、その段を足した検査で T3 の指摘が 0 件であることを確かめ、承認者の判定を、その文書の進捗を追う Issue（`type:進捗`。[7.1](../03_development.md#71-課題のラベル)）に記録する。ここから T3 と段の順の T1 が効く。設計の文書の段（HLD・LLD）は今までどおり、ゲートの判定が Go か条件付きGo のときに足す。
3. **`IMPLEMENTED_STAGES`**: `tools/lint_trace.py` に、テストのコードがそろったテストのレベルの段の集合 `IMPLEMENTED_STAGES` を置く。テストのコードとテスト文書の T5 は、この集合で効く。自動のケースを実装したテストのコードが無い検査は、そのケースのレベルを入れたときから効く。`tests/src/`・`tests/scripts/` のファイルがどのケースも名乗っていない検査は、ファイルにレベルが無いので、どれか 1 つのレベルを入れたときから `tests/src/`・`tests/scripts/` の全ファイルに効く。そのレベルの自動のケースのテストのコードをそろえる変更で足す。足したことは、その段を足した版で `make lint` が通ることで確かめる。空集合で始める。
4. **集合の関係の検査**: `IMPLEMENTED_STAGES` の段は UT・IT・ST のどれかで、`CONFIRMED_STAGES` にも入っていなければならない。外れると T1 で止め、`EXEMPTIONS` では外せない（ほかの段の指摘と同じ）。
5. **開始基準**: [テスト方針書 §5.6](../02_test_policy.md#56-開始基準) の全レベルに共通の条件に、そのレベルの段が `IMPLEMENTED_STAGES` にあり、T5 が通ることを足す。この条件はレベル全体に掛かるので、§5.6 の表が単位に分けて始めることを許している正式な実行（UT はプログラムごと、IT は内部結合と外部結合のそれぞれ）も、そのレベル全体の自動のケースのテストのコードがそろってから始める（持ち主の判断、2026-10-15。道具で確かめられる条件を 1 つにするため）。
6. **製品のコードの T5 は変えない**: 製品のコード（`src/`・`scripts/`）と詳細設計書（LLD）の T5 は、今までどおり LLD を `CONFIRMED_STAGES` に入れたときから効く。その時機と、コードを HLD の名前にそろえる作業の順は、[ADR-LLD-001](ADR-LLD-001-lld-format-module-granularity-and-t2-timing.md) の Consequences のとおり [#246](https://github.com/jj1xgo/findsummits/issues/246) で決める。

検査が効き始める時期は、次のとおりになる。

| 検査 | 対象 | 効き始める時期 | 根拠 |
|---|---|---|---|
| T1 | `IMPLEMENTED_STAGES` の段が UT・IT・ST のどれかで、`CONFIRMED_STAGES` にもあること | いつでも | 本 ADR の Decision 4 |
| T2 | LLD の「ファイル」のパスの実在 | LLD を `CONFIRMED_STAGES` に入れたとき | ADR-LLD-001 の Decision 10 |
| T2 | 上のほかの参照先の実在（テストのコードが指すケースを含む） | 文書があるとき | ADR-URD-020 |
| T3 | 上位の要素を指す下位が無い | 下位の段を `CONFIRMED_STAGES` に入れたとき（設計の文書はゲートの判定の後、テスト文書はヘッダーを「確定」にしたとき） | ADR-URD-020、本 ADR の Decision 2 |
| T5 | 製品のコードと LLD | LLD を `CONFIRMED_STAGES` に入れたとき | ADR-URD-020、本 ADR の Decision 6 |
| T5 | テストのコードとテスト文書 | そのレベルを `IMPLEMENTED_STAGES` に入れたとき | 本 ADR の Decision 3 |

## Alternatives

- **案 B: ステータスを 3 値にする（ドラフト・仕様の確定・テストのコードがそろった、のような値）**: テスト文書だけ値が増え、ほかの文書と書き方がそろわない。ヘッダーの値と `tools/lint_trace.py` の 2 つの集合を、別々に合わせ続けることになる。テストのコードがそろったかは、ヘッダーではなく検査（T5）で確かめられる。不採用（持ち主の判断、2026-10-15）。
- **案 C: 変えない（T3 と T5 を `CONFIRMED_STAGES` で一緒に効かせる）**: テスト文書を確定にできるのが COD の段の後になり、ケースの中身の確定と被覆の検査（T3）が、テストのコードを書くまで止まる。ゲート 3 の条件を満たさない。不採用。
- **`EXEMPTIONS` で T5 を外す**: `EXEMPTIONS` は構造上の例外を指摘の 1 件ごとに外すもので、ケースが増えるたびに項目を足し、COD の段で 1 件ずつ消すことになる。外す理由は個々の指摘ではなく段にある（ADR-LLD-001 の Alternatives と同じ理由）。不採用。
- **製品のコードの T5 も `IMPLEMENTED_STAGES` で判定する**: LLD の段の時機は、T2 の「ファイル」の検査と一緒に #246 で決める。ここで動かすと ADR-LLD-001 の Decision 10 と別の判定が入り、#246 の前提が変わる。本 ADR の範囲はテスト文書に限る。不採用。

## Consequences

- `tools/lint_trace.py` に `IMPLEMENTED_STAGES`（空集合）を置き、テストのコードの T5 をこの集合で判定し、集合の関係を T1 で検査するように改めた（2026-10-15）。`CONFIRMED_STAGES` は `{'SRS', 'HLD'}` のまま変えていない。
- [開発ガイド §4](../03_development.md#4-フェーズゲート) にテスト文書の段を足す時機の段落を、[§6.2](../03_development.md#62-検査) の表の T1・T3・T5 の行と表の下の箇条に `IMPLEMENTED_STAGES` を、[テスト方針書 §5.6](../02_test_policy.md#56-開始基準) の全レベルに共通の条件に 1 項目を、[文書管理ルール「ドキュメントフォーマット標準」](../CLAUDE.md#ドキュメントフォーマット標準)にテスト文書の「確定」の意味を足した。
- ADR-URD-020 の Decision 4 のうち、テスト文書の段の T3 の時期（ゲートの後 → ヘッダーを「確定」にしたとき）とテストのコードの T5 の時期、同 Consequences の「フェーズゲートの判定のたびに `CONFIRMED_STAGES` を書き換える」、ADR-LLD-001 の Decision 10 の「T3・T5 と同じく `CONFIRMED_STAGES` で行う」のうちテストのコードの T5、同 Alternatives の「`CONFIRMED_STAGES` はフェーズゲートを通った文書の段」（テスト文書の段はヘッダーの確定で入る）は、本 ADR で置き換わる。両 ADR に追記した。
- ST・IT を `CONFIRMED_STAGES` に入れる時機は、本 ADR では決めない。ST は、ゲート 3 の条件の残り（ST のケースの残り）を済ませた後に別に判断する。UT を `CONFIRMED_STAGES` に入れるには、`tools/lint_trace.py` の `STAGE_PARENT` により上位の LLD も入れる必要があり、LLD を入れると製品のコードの T5 と「ファイル」のパスの T2 が効き始める。したがって UT の確定の時機は、[#246](https://github.com/jj1xgo/findsummits/issues/246) の段取りに縛られる。
- あるレベルを `IMPLEMENTED_STAGES` に入れると、そのレベルの自動のケースのテストのコードが無いことが T5 で止まる。どれかのレベルを入れた後は、どのケースも名乗っていない `tests/src/`・`tests/scripts/` のファイルが、レベルを問わず T5 で止まる。そのため、最初のレベルを入れた後に書き始めるほかのレベルのテストのコードは、書き始めの commit から `trace:` のコメントでケースを名乗る。テストのコードを書き進める間は入れず、そろえる変更で入れる。
- 正式な実行の開始基準（Decision 5）はレベル全体に掛かるので、単位に分けた正式な実行も、そのレベル全体の自動のケースのテストのコードがそろうまで始めない。
- `IMPLEMENTED_STAGES` に入れた段のテスト文書に自動のケースを足すときは、同じ変更でそのテストのコードも足す（足りなければ T5 が止める）。本 ADR では、`CONFIRMED_STAGES`・`IMPLEMENTED_STAGES` から段を外す場面を想定しない。確定した文書を改める扱い（ドラフトに戻すかどうか）を決めるときに見直す。

## 追記（2026-10-15）: 段を外す場面

Consequences の最後の箇条の「本 ADR では、`CONFIRMED_STAGES`・`IMPLEMENTED_STAGES` から段を外す場面を想定しない」のうち、ゲートの判定で `CONFIRMED_STAGES` に足す段が再審査で No-Go になったときは、その段と、それを上位に持つ段（下位へたどった先まで。テスト文書の段を含む。たとえば HLD を外すなら LLD・UT・IT も）を `CONFIRMED_STAGES` から外し（`IMPLEMENTED_STAGES` にあれば、そこからも外す）、外した段の文書のヘッダーのステータスを「ドラフト」に戻すことにした（[ADR-OPS-006](ADR-OPS-006-conditional-go-deadlines-and-gate-re-review.md)）。テスト文書自身の再評価による取り消しは決めていないが、上位の段の取り消しに伴う連鎖は対象になる。
