# ADR-OPS-007: テストのケースの自動と手動を、合否をテストのコードが判定するかで分ける

| 項目 | 内容 |
|---|---|
| 状態 | 採用・未実装 |
| 決定日 | 2026-10-17 |

---

## Context

[テスト方針書 3.1](../02_test_policy.md#31-自動テストと手動確認の役割分担) は、C 解析エンジンと Python スクリプトは自動テストを既定とし、HTML ビューアは、ブラウザ内で生成する成果物の中身を固定した入力から自動で照合し、地図の描画と対話操作を対象環境のブラウザで手動確認する、と分けていた。何を「自動」と呼ぶかは書いていなかった。そのため、次の場合の扱いが決まっていなかった。

- 手順の一部を人が行う（ブラウザの操作、手順書に沿った環境構築）。
- 人が入力・基準セット・根拠資料を用意して固定する。
- 全国のデータや動作前提環境のマシンが要り、push ごとの CI で回らない。
- ブラウザの中の値（表示する要素と文字、localStorage、ダウンロードの記録、通信の記録、Canvas の画素の値、応答時間やフレーム時間の実測）を、コードで読んで判定できる。

テストケース ID の直後の `（手動）` の印は、`tools/lint_trace.py` がテストのコードの実装の確認から外す目印である（[テスト方針書 §6](../02_test_policy.md#6-テストケースid命名の大枠)）。印の無いケースは自動のケースとして数えられ、そのレベルを `IMPLEMENTED_STAGES` に入れたときから、テストのコードが要る（[ADR-OPS-005](ADR-OPS-005-test-document-status-and-t5-timing.md) の Decision 3）。

2026-10-17 に[システムテスト仕様書（ST）](../70_ST.md)の全ケースを読み直すと、次のことが分かった。

- `（手動）` の付いたケースの中に、合否判定基準がブラウザの中の値の照合だけで決まるもの（`ST-FR-013-09` の要求の URL と `integrity` の属性、`ST-NFR-010-01` のフレーム時間）や、照合と目視が混じるものがあった。
- 印の無いケースの中に、人の読解や目視が混じるもの（`ST-NFR-011-01` の手順文書のチェックリスト、`ST-UR-008-01` のクリーン環境での一気通貫）があった。

持ち主は 2026-10-17 に、できるだけ自動テストに載せる方針で、次のとおり決めた。

## Decision

1. **自動と手動の定義**: 合否をテストのコードが判定するケースを自動、合否が人の知覚や読解そのもので決まるケースを手動とする。
2. **手動にする理由にしないもの**: 次のことは、ケースを手動にする理由にしない。
   - 手順の一部を人が行うこと（ブラウザの操作、手順書に沿った環境構築など）。
   - 入力・期待値・基準セット・根拠資料を人が用意して固定すること。
   - 全国のデータや動作前提環境のマシンが要り、push ごとの CI で回らないこと。実行の頻度は各テストケースが定める（[テスト方針書 3.2](../02_test_policy.md#32-実データ依存の扱い)）。
   - 合否に効かず記録するだけの値を、人が読んで記録すること。
   - 実測の値を目標値と比べるケースで、目標を外れたときの許容の判断を人が行うこと。許容の判断は合否と別に記録する（[テスト方針書 5.3](../02_test_policy.md#53-既知欠陥の許容基準)）。
3. **ブラウザの中で確かめるもの**: 表示する要素と文字、ブラウザに保存した値、ダウンロードしたファイル、通信の記録（要求の URL・数・順）、Canvas の画素の値、応答時間やフレーム時間の実測のように、ブラウザの中の値をコードで読み、テスト対象の出力とは独立に仕様から導いた期待値や目標値（[テスト方針書 3.3](../02_test_policy.md#33-期待値の根拠)）と照合できるものは、自動とする。手動は、期待が「人にどう見えるか」（線のつながり、欠け、見分けやすさなど）でしか書けない部分に限る。画素の値はたいていコードで読めるので、読めるかどうかではなく、期待を仕様から値として導けるかで分ける。
4. **文書を照らすケース**: リンクの到達や決めた項目の有無のように、テストのコードが照らせる部分は自動とし、記述が足りるかの判断は手動とする。
5. **混じるケースは分ける**: 1 つのケースの中に、テストのコードが判定する部分と、人の知覚や読解でしか判定できない部分が混じるときは、自動のケースと手動のケースに分ける。分けて足すケースには同じ対象の末尾の連番を振り、今のケースの ID は振り直さない。混じったまま `（手動）` を付けない。どちらが今の ID を引き継ぐかはケースごとに決め、今の ID を参照する箇所（SRS §9、ST の表と範囲の書き方、IT の対応表）を同じ変更で直す。
6. **方針書に書く範囲**: 1〜5 をテスト方針書 3.1 に書く。ブラウザを動かす道具は、方針書でも本 ADR でも名指ししない（[#299](https://github.com/jj1xgo/findsummits/issues/299) で決める）。

## Alternatives

- **方針書 3.1 の字句のまま（地図の描画と対話操作は手動）**: ブラウザの中の値をコードで読んで判定できるケースも手動に残り、テストのコードの実装の確認から外れる。持ち主が不採用とした（2026-10-17）。
- **CI で回るものだけを自動と呼ぶ**: 処理時間やメモリを全国のデータで測るケースが手動になり、測定と目標値との比較をコードが行えるのに、テストのコードの実装の確認から外れる。持ち主が不採用とした（2026-10-17）。
- **人の作業が混じるケースを手動のまま残す**: 人の作業が準備や操作に限られ、合否をコードが判定できるケースも手動になる。持ち主は、人の作業とコードの判定に分けて自動に寄せると決めた（2026-10-17）。
- **コードで読める値はすべて自動とする**: 画素の値はたいていコードで読めるので、等高線が欠けずに描かれるかのように、期待が見え方としてしか書けないケースまで自動になり、期待値を仕様から導けないまま照合することになる（[テスト方針書 3.3](../02_test_policy.md#33-期待値の根拠)）。不採用。
- **混じるケースに別の印を作る（`（一部手動）` など）**: `tools/lint_trace.py` の数え方が自動か手動かの 2 つでなくなり、どの部分にテストのコードが要るかを印から決められない。不採用。

## Consequences

- テスト方針書 3.1 に Decision 1〜5 を書き、3.4 の対象外の文と §4 の 2 つの箇条を合わせた。概要設計書（HLD）3.7.3 の「画面」の段落と DEC131 の末尾の文、[結合テスト仕様書（IT）](../60_IT.md) 3.7 の導入の段落と 4.7 の冒頭の段落を、新しい 3.1 に合わせた。古い分け方を決めていた [ADR-IT-001](ADR-IT-001-two-part-it-and-moved-st-cases.md) の Decision 5 と [ADR-LLD-001](ADR-LLD-001-lld-format-module-granularity-and-t2-timing.md) の Decision 3 には、本 ADR で改めたことを追記した（2026-10-17）。
- ST と IT のケースの印と分け方は、まだ本 ADR の決定に合っていない。ST は [#224](https://github.com/jj1xgo/findsummits/issues/224) の下の 3 つの群で、IT は [#300](https://github.com/jj1xgo/findsummits/issues/300) で判定し直す。それまでの印と 3.1 のずれは、本 ADR で意図して許す（[開発ガイド §6.3](../03_development.md#63-変更するときの手順) の 4）。ST と IT を確定にする（ADR-OPS-005 の Decision 2）前に、判定し直しを終える。
- 判定し直しで合否判定基準の文言が変わると、[ソフトウェア要件仕様書（SRS）§9](../20_SRS.md#9-検証) の検証方法（[用語集「要求の検証」](../00_GLOSSARY.md#要求の検証)の決め方で、ST の合否判定基準の文言から決める）が変わることがある。各群の変更で、SRS §9 も同時に直す。[FR-013](../20_SRS.md#fr-013-html-ビューア生成) の検証方法（「試験」）は、本 ADR の前から ST の合否判定基準の文言（`ST-FR-013-07`・`ST-FR-013-08` の「ブラウザでの目視確認」。用語集の決め方では「試験・実演」）と合っていない。その行を判定し直す群（[#303](https://github.com/jj1xgo/findsummits/issues/303)）で直す。
- 自動のケースが増えるので、ブラウザの中で自動で確かめる手段（ブラウザを動かす道具と、対象環境のブラウザのうちどれで回すか）を、CMP7・CMP8 の ST・IT のテストのコードを書き始める前に決める（#299）。
- ST と IT の判定し直しを終えたら、本 ADR の状態を「採用・実装済み」にする。
