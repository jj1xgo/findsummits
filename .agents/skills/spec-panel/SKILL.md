# 多視点パネルレビュー（Codex 版）

指定された仕様文書（URD/SRS/HLD/LLD/ADR/テスト仕様（UTC/ITC/STC）の章・FR 番号など）を、以下の4視点で順にレビューし、指摘を一覧化する。

## 前提ルール

- 仕様優先原則: コードを正として参照しない。仕様書の内容を正とする（`AGENTS.md` 参照）
- 課題登録はしない: 指摘を洗い出して提示するまで
- 根拠主義: grep/Read 等の出力を指摘の根拠にするときは、必ず実出力を引用・照合し、記憶や推測で埋めない

## 4つの視点

1. アーキテクト: モジュール分担・ADR 整合・設計の一貫性・拡張性
2. 仕様レビュアー: URD↔SRS↔HLD↔LLD トレーサビリティ・曖昧さ・抜け漏れ・矛盾。加えて**横串の規約適合**: 入出力テーブルが全外部I/Fを列挙しているか・他 FR と粒度が揃っているか・`docs/CLAUDE.md` の分類規約に適合するか
3. データ/アルゴリズム: 境界条件・NODATA・サンプル代表性・性能/メモリ。特に同一境界値が複数の意味で二重解釈されていないか、条件判定の先後関係が仕様に明示されているか
4. 申請者/エンドユーザー: SOTA 申請 O/P 要件・エビデンス妥当性

**テスト仕様（UTC/ITC/STC）レビュー時の読み替え**: テスト文書を対象とする場合、①台帳の読み替え（「内部データ一覧・外部I/F一覧」の代わりに FR一覧↔テストケース対応表を逆引き）、②視点4の読み替え（カバレッジ観点: 同値分割・境界値分析・NODATAのテスト網羅性）、③仕様レビュアー視点の主眼（上位仕様の各FRがテストケースに対応しているか、両方向で確認）を適用する。

## 手順

1. 対象文書を読む。関連する URD/SRS/HLD/LLD/ADR も必要に応じ参照
2. 各視点で指摘を抽出（根拠主義: 推測でなく文書の記述を引用して指摘）。特に次を能動的に確認する:
   - **横串比較**: 対象の入出力テーブルを兄弟要素の同種テーブルおよび分類規約（`docs/CLAUDE.md`）と相互比較する。「他の要素は載せているのにこの要素だけ載せていない」項目を能動的に探す
   - **台帳逆引きチェック**: 文書内の一覧表（台帳）に、レビュー対象が生成元・参照先として漏れなく登録されているか台帳側から逆引きする（例: SRS の「内部データ一覧」「外部I/F一覧」）
   - **多重定義の整合チェック**: 同一項目が複数箇所（一覧表と詳細仕様など）で矛盾なく定義されているか照合する。ADR が定義する型/座標系/フィールド名と本文の実際の使用形態のズレも確認する
   - **廃止/改訂用語の残存チェック**: ADR で廃止・改訂された用語/決定が文書全体に古いまま残存していないか検査する
   - **値域/enum の参照元↔定義元 完全性チェック**: ある値域について、参照元 FR が N 値を参照し定義元 FR が M 値しか定義しない不整合を検出する
   - **暗黙のフォールバック/デフォルト挙動の明示化**: 暗黙のデフォルト挙動が不備ゲート条件等と対応付けて明示されているか確認する
3. 指摘を「視点 / 重要度（高・中・低）/ 種別 / 内容 / 該当箇所 / 推奨対応」の表に集約する。`種別` は `仕様検討`（複数解釈が成り立つ・トレードオフの評価が必要）か `作業実行`（推奨対応が一意・機械的）のいずれか
4. 視点横断の総評（最大の論点・トレードオフ）を3〜5行で
5. 出力を2セクション（仕様検討・判断が必要な指摘／そのまま作業実行できる指摘）に分けて提示する
6. `.claude/` ディレクトリがこのチェックアウトに存在する場合は、指摘記録ファイルを `.claude/spec-findings/<対象識別子>.md`（存在しなければ `mkdir -p` してから作成、1対象1ファイル・上書き方式）へ自分で書き込む。`<対象識別子>` は対象ファイルの basename（拡張子除く。例: `20_SRS.md` の FR-013 なら `20_SRS-FR-013`）。`.claude/` が存在しない（public clone 等）場合はこの手順を省略し、指摘表だけを応答に含める
