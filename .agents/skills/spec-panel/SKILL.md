# 多視点パネルレビュー

指定された仕様文書（URD/SRS/HLD/LLD/ADR/テスト仕様（UTC/ITC/STC）の章・FR 番号など）を、以下の 4 視点で順にレビューし、実行者と違うモデルの外部視点（視点5）と合わせて、指摘を一覧化する。引数で対象を受け取る（例: `FR-013`）。

このファイルが観点・手順・出力形式の正本。実行環境ごとの補足（視点5 の起動方法、記録の置き場）がチェックアウトにあれば、それも読む。`.claude/AGENTS.md` があれば、記録の置き場と書式はその案内に従う。無ければ記録ファイルは書かず、指摘表と視点5 の出力を応答に含める。

## 前提ルール（厳守）

- 仕様優先原則: コードを正として参照しない。仕様書の内容を正とする（`AGENTS.md` 参照）
- 4 視点は実行者が自分でインラインに順に行う。実行者が Claude Code なら、`Agent`/`Task` ツールで Claude のサブエージェントを起動しない（並列は持ち主の明示指示があるときだけ）。視点5 は別モデルの CLI を起動するだけで、この禁止の対象外
- 課題登録はしない: 指摘を洗い出して提示するまで。tracker 登録は持ち主の承認後
- 根拠主義: 指摘の根拠にする grep/Read 等の出力は、実出力を引用・照合する。記憶や推測で埋めない
- 起動場所: 本体 checkout のルート（`git rev-parse --show-toplevel`）。視点5 の相手がプロジェクトの規則を本体ルートからの相対パスで読むため

## 4つの視点

1. アーキテクト: モジュール分担・ADR 整合・設計の一貫性・拡張性
2. 仕様レビュアー: URD↔SRS↔HLD↔LLD トレーサビリティ・曖昧さ・抜け漏れ・矛盾。加えて
   **横串の規約適合**: 入出力テーブルが全外部I/F を列挙しているか・他 FR と粒度（記載項目の細かさ）が
   揃っているか・`docs/CLAUDE.md` の分類規約（外部I/F／ユーザー入力／内部データ等）に適合するか
   （具体的なチェック動作は手順2を参照）
3. データ/アルゴリズム: 境界条件・NODATA・サンプル代表性・性能/メモリ。特に同一境界値が
   複数の意味（判定境界と変換境界など）で二重解釈されていないか、条件判定の先後関係
   （どちらが先行・除外か）が仕様に明示されているかを確認する
4. 申請者/エンドユーザー: SOTA 申請 O/P 要件・エビデンス妥当性

## 外部視点（視点5）

4 視点は実行者 1 人の自己レビューなので、同じ枠組みの見落としが残りやすい。視点5 は実行者と違うモデルに頼む。Claude Code が実行者なら Codex、Codex が実行者なら Claude。

- **頼むこと**: 次の 2 問と、この上の 4 視点、手順2 のチェック群。2 問と 4 視点は 1 本の依頼にまとめる（2 本に分けると範囲が重なり、利用枠がほぼ倍になる）。
  - (a) この計画・仕様は利用者の目的を満たすか。
  - (b) より簡単な選択肢を見落としていないか。
- **依頼文**: 次を含める。
  - 対象のパス（本体ルートからの相対パス）と、関連文書のパス
  - 既決事項があれば列挙し「蒸し返し禁止」
  - 2 問、4 視点、手順2 のチェック群。このファイル `.agents/skills/spec-panel/SKILL.md` を読ませ、「## 4つの視点」と「## 手順」の手順2 を観点として使うよう書く
  - 修正履歴の横展開チェックの材料: 読める過去のレビュー記録のパス（兄弟要素の記録など）があれば渡す。相手がコマンドを実行できない（`git log` を読めない）ときに材料が無ければ、このチェックは「未確認」と書かせる。Codex が実行者のとき（相手の Claude に内容が API で送られる）は、`.claude/` 配下の非公開の記録を、持ち主が許可したときだけ含める。含めないときも、このチェックは「未確認」と書かせる。依頼に含めなくても、自動で読み込まれる設定と、Claude が自分で読める範囲は残るので、「Codex が実行者のとき」の手順3 の承認の依頼文には、その範囲も書く
  - 読み方: 相手が Codex なら「sandbox は read-only です。`cat`・`sed -n`・`rg` などの読み取りのコマンドで読んでください。ファイルの書き込みはできません。」、Claude なら「Read / Grep / Glob で読めます。書き込みとコマンド実行はできません。」（Codex に「コマンド実行はできません」と書くと、何も読まずに終わる）
  - 出力: 「観測」（客観的に確認できる事実）と「判定」（それが問題かどうかの評価）を分けた箇条書き。各指摘に番号、視点（(a)・(b)・1〜4）、重要度（高・中・低）を付ける
  - 実行者の 4 視点の結果は入れない（独立に見てもらうため）
- **確認限定巡**: 依頼文の問いを次に差し替える。2 回目以降は、初回の出力の指摘のうち、直前の確認限定巡で未反映とされたものを基準にする。「確認限定。前回の視点5 の出力 {前回の出力のパス} の指摘 {番号} と、次に挙げる指摘 {一覧} が、対象 {対象のパス} に反映されているかだけを見てください。新規の論点は不要です。反映された項目と反映されていない項目を番号で列挙してください。」相手が Claude なら `--resume` で前回の会話に継ぎ足す。
- **重大度の扱い**: 視点5 は読み取り専用で実行を伴わないので、推測の重大度が高く出やすい。判定は「観測」から独立に採否を決めず、4 視点や実機確認と突き合わせてから種別（仕様検討/作業実行）を付ける。
- **失敗の扱い（fail-soft）**: 視点5 が失敗・空出力・タイムアウトなら、成功と書かず `not run` と理由を記録して先へ進む。視点5 の可否で spec-panel 全体を止めない。

### Codex が実行者のとき（視点5: Claude）

1. 出力先を決める。`.claude/AGENTS.md` に保存先の案内があればその置き場、無ければ `mktemp -d` の一時ディレクトリ。ファイル名は初回が `<対象識別子>-claude.json`、確認限定巡が `<対象識別子>-claude-confirm<N>.json`。Codex のシェルは呼び出しごとに状態（変数）を持ち越さないことがあるので、以下の各ブロックの先頭で `out` を同じ値で書き直す（変数に頼らず、確認限定巡の `session_id` も初回のファイルから読む）。出力先のディレクトリが無ければ作る。

   ```bash
   out="<出力先>/<対象識別子>-claude.json"
   mkdir -p "$(dirname "$out")"
   rm -f "$out" "${out%.json}.md"
   ```

2. 4 視点より先に、前景で起動する。プロンプトは `-p` の直後に置く（`--disallowedTools` は可変長引数で、後ろに置くとツール名として読まれる）。stdin は `< /dev/null` で閉じる。Claude のレビューは 25 分ほどかかることがあるので、シェルツールのタイムアウトを `timeout` の値（3600 秒）以上にして起動する。

   ```bash
   out="<出力先>/<対象識別子>-claude.json"
   env -u CLAUDECODE timeout 3600 claude -p "<依頼文>" \
     --model opus \
     --allowedTools "Read,Grep,Glob" \
     --disallowedTools "Bash,Edit,Write,NotebookEdit,Agent,Task" \
     --output-format json < /dev/null > "$out"
   echo "rc=$?"
   ```

   確認限定巡は、同じコマンドに `--resume "$(jq -r '.session_id // empty' <初回の json のパス>)"` を足し、`out` を確認限定巡の名前にする。

3. sandbox: sandbox の中でこのコマンドが、sandbox の制約（ネットワークの遮断、ホームにある Claude の設定ディレクトリへの書き込みの拒否）で失敗したら、承認つきで sandbox の外での実行を求める。承認の依頼文には、送る範囲を次の 3 つに分けて書き、宛先（Anthropic の API。`claude -p` が送る）も具体的に書く。(i) 依頼文が指すファイルのパスの一覧、(ii) Claude Code が起動時に自動で読み込む設定（プロジェクトとユーザーの `CLAUDE.md` とその import、対象に当たる rules）、(iii) 読み取りのツール（Read / Grep / Glob）で、チェックアウトの中の任意のファイルを読みうること。自動承認のレビューや持ち主に拒否された、または承認を求められないときは、昇格を繰り返さず、視点5 は `not run` と理由を書いて先へ進む。持ち主が送信範囲と宛先を明示して承認したときだけ、再試行する。認証の不備（未ログインなど）や原因の分からない失敗では昇格を求めず、`not run` とエラーの末尾を書いて先へ進む。
4. 起動が返ってから 4 視点を行う。Claude の出力は 4 視点を終えるまで読まない（4 視点の独立のため）。
5. 回収する。起動の `rc` が 0 以外、`.result` が空、`session_id` が空のどれかなら失敗。

   ```bash
   out="<出力先>/<対象識別子>-claude.json"
   jq -r '.result // empty' "$out" > "${out%.json}.md"
   jq -r '.session_id // empty' "$out"
   jq -r '.modelUsage | keys[]' "$out"
   ```

費用: 1 回ごとに Claude の 5 時間枠を使う。重さの大半は前置き（システムプロンプト・読んだファイル）のキャッシュ書き込みで、確認限定巡を `--resume` にすると軽くなる。

## 手順

**テスト仕様（UTC/ITC/STC）レビュー時の読み替え**: テスト文書を対象とする場合は以下を読み替えて適用する。①**台帳の読み替え**——「内部データ一覧・外部I/F一覧」の代わりに **FR一覧 ↔ テストケース対応表**（または網羅性マトリクス）を台帳として逆引きし、各 FR がテストケースに対応しているかを確認する。②**視点4の読み替え**——「申請者/エンドユーザー」視点は **カバレッジ観点**（同値分割・境界値分析・NODATA のテスト網羅性）に読み替える。③**仕様レビュアー視点の主眼**——上位仕様（SRS/LLD）の各 FR がテストケースに対応しているか（上→下）と、テストケースに対応する仕様 FR が存在するか（下→上の逆引き）を両方向で確認する。

1. 対象文書（引数）を読む。関連する URD/SRS/HLD/LLD/ADR も必要に応じ参照。依頼文を確定したら、手順2 の前に視点5 を起動する
2. 各視点で指摘を抽出（根拠主義: 推測でなく文書の記述を引用して指摘）
   - **横串比較（必須）**: 単一の要素（FR・モジュール・章など）が対象でも、その入出力テーブルを
     **兄弟要素の同種テーブル**および分類規約（要件文書なら `docs/CLAUDE.md`）と相互比較する。
     失敗モードに注意——単一要素を閉じて読むと、抜けている項目も説明欄や別セクションに記載があるため
     自己完結して見え、見落とす。「他の要素は載せているのにこの要素だけ載せていない」項目を能動的に探すこと
   - **台帳逆引きチェック（必須）**: 文書内にデータ・インターフェース等の一覧表（台帳）があるなら、
     レビュー対象がその台帳に生成元・参照先として漏れなく登録されているかを台帳側から逆引きする
     （「対象から外を見る」に加えて「台帳から対象を逆引き」する。台帳の漏れは実装時の見落としリスクになる）。
     例：SRS なら「内部データ一覧」（§7.2.1 等）・「外部I/F一覧」（§6.1 等）
   - **修正履歴の横展開チェック（必須）**: 兄弟要素で過去に同種欠陥（台帳登録漏れ等）が修正されているなら、
     その修正履歴（git log や過去のレビュー記録）を参照し、レビュー対象に同じ欠陥が残っていないか確認する。
     横串比較が「現在の兄弟」を見るのに対し、これは「過去に直した欠陥の再発」を見る
   - **多重定義の整合チェック**: 同一の項目が複数箇所（一覧表と詳細仕様、横断的な分類表など）で
     定義・分類されているなら、それらが矛盾していないかを照合する（参照形態によって分類が変わりうる
     点に注意）。例：SRS なら「外部I/F一覧」（§6 等）と各 FR 入出力テーブルの分類。矛盾を検出したら
     **正本（canonical）を1箇所に定め、他は参照に統一**することを推奨対応として提示する。また
     **ADR が定義する型/座標系/フィールド名**（例: ADR で「ピクセル座標」と定義 vs 本文で緯度経度フィールド名を使用）と
     本文での実際の使用形態のズレも照合する
   - **手順と終了条件の分断チェック**: 実行フロー（手順1〜N）と、終了条件・パラメータ管理・例外処理が
     記述上分断されていないかを確認する（分断は読者の混乱を招く）
   - **廃止/改訂用語の残存チェック（必須）**: ADR で廃止・改訂された用語/決定が文書全体に古いまま
     残存していないかを `grep` で能動的に検査する。修正履歴の横展開が *兄弟要素の同種欠陥の再発* を
     見るのに対し、これは *廃止決定の追従漏れ（古い用語の残骸）* を文書横断で見る点が異なる
   - **値域/enum の参照元↔定義元 完全性チェック（必須）**: ある値域（例: `stability` の取りうる値）について、
     参照元 FR が N 値を参照し定義元 FR が M 値しか定義しない不整合を検出する。参照元・定義元の
     **両方**を開かないと値域の完全性は検証できない
   - **暗黙のフォールバック/デフォルト挙動の明示化**: 暗黙のデフォルト挙動（例: フォールバック処理）が
     不備ゲート条件等と対応付けて明示されているかを確認し、合意境界の曖昧さを顕在化させる
3. 指摘を「視点 / 重要度（高・中・低）/ 種別 / 内容 / 該当箇所 / 推奨対応」の表に集約。
   各指摘に以下の基準で `種別` を付与する:
   - `仕様検討`: 複数解釈が成り立つ・トレードオフの評価が必要・ビジネス判断が必要なもの
   - `作業実行`: 推奨対応が一意・機械的（名称統一・台帳追記・整合修正・誤記訂正など）なもの
   - **視点5 の回収**: 視点5 の出力を読み、「観測」「判定」を記録の「視点5」見出しへ逐語転記する。実害に直結すると判断したものだけ上の表にも合流させる。失敗なら `not run` と理由を書く
4. 視点横断の総評（最大の論点・トレードオフ）を 3〜5 行で
5. 出力を2セクションに分けて提示する:
   - **セクション1「仕様検討・判断が必要な指摘」**: `仕様検討` のもの（詳細表示・確認を求める）
   - **セクション2「そのまま作業実行できる指摘」**: `作業実行` のもの（簡易一覧・確認不要）
   - 記録ファイルを書く場合の対象識別子は、引数の文字列ではなく、レビュー対象と判断した実ファイルの
     basename（拡張子除く）を先頭に用いる（例: `docs/30_HLD.md` の §3.1 なら `30_HLD-§3.1`、ADR なら
     `ADR-SRS-010`）。同じ章番号・セクション番号がステージをまたいで再利用される（SRS→HLDの§3.1継承等）ため、
     ステージ横断での衝突を避ける目的。HLD は 2026-10-05 に章を付け替えた（ADR-HLD-002）。プログラム構造の章
     （第 3 章）の節は、節番号の後にコンポーネントの ID を付ける（`30_HLD-§3.5-C5`、共通部品は
     `30_HLD-§3.9-common`）。付け替える前の FR の節の記録（`30_HLD-§3.5` など）を上書きしないため
6. tracker 登録要否を確認し、持ち主の承認後に登録する（1 論点 1 課題）

### 視点5

視点5 の出力の逐語。失敗なら `not run` と理由。
